# **システム統合・シナリオテスト計画書 (SCENARIO_TEST_PLAN.md)**

- **主担当エージェント**: 🛡️ 品質・テスト & QA (`qa-engineer`)
- **副担当・統括**: 👑 プロジェクトコンダクター (`conductor`)
- **承認ゲート**: 👤 ユーザーによる明示的承認必須

## **1. 概要と目的**

本ドキュメントは、「<プロジェクト名>」における各機能の自律実装・単体テストの完了を受け、システム全体の画面操作を自動化して網羅的な E2E（End-to-End）統合シナリオテストを実施する **システム統合・シナリオテストフェーズ** の進め方、必要なテスト環境、およびテストシナリオ案を定義するものである。

本フェーズの主たる目的は以下の通りである：

1. **画面操作の自動化による網羅検証**: ユーザーの操作フローに沿ったシナリオテストを画面自動化ツール（E2Eテストツール）で完全に自動化し、フロントエンドUI、バックエンドAPI、データベース、外部API連携が統合状態で正しく動作することを保証する。
2. **品質評価とレポート化**: テスト実行結果、合格率、失敗箇所の画面キャプチャ・ログエビデンスを自動出力し、開発チームおよびユーザーへ可視化する。
3. **AI自律デバッグ・スクリプト自動修復 & ユーザー承認サイクルの確立**:
   - テスト失敗やAbendが発生した際、AI（Antigravity）がエラー原因を「**テストスクリプトの不具合**」と「**システムの不具合**」の2つに自律分類する。
   - **Wiki Maintainer 連携 (RCA即時記録)**: 不具合や環境トラップが発生した際、🛡️ `qa-engineer` が `wiki-maintainer` 手順に基づき根本原因分析 (RCA) を行い、プロジェクトローカルの `./wiki/patterns/` (Tier 1 `local/`, Tier 2 `universal/`) へ即時記録する。
   - **テストスクリプトの不具合**の場合、🛡️ `qa-engineer` が自律的にテストコードを修復し、**DB自動復元を経て最大5回までリトライ**を行う（ユーザー承認不要）。
   - **システムの不具合**の場合、🛡️ `qa-engineer` は**プログラムコード本体を直接改変せず**、原因調査結果と修正Diff案を提示してコンダクターに報告し、**人間の承認を獲得した上でエンジニアがシステムコードを修正**する（二重防御ガードレール）。
   - **修正後のコンテナ再構成**: コードや環境修正後は、必ず `docker compose down` および `docker compose up --build -d` を実行してコンテナを再構成する。

## **2. シナリオテスト全体プロセスフロー**

シナリオテストフェーズは、テストシナリオの作成から**DB復元・データ初期化**、自動テスト実行、不具合の原因追跡・自動修復・Wiki知見永続化、ユーザー承認に基づくシステム修正、そして再テスト（回帰テスト）までを1つのイテレーティブ（反復型）なサイクルとして運用する。

```mermaid
flowchart TD
    Start([シナリオテストフェーズ開始]) --> Step1[1. シナリオ作成・自動化<br/>Playwright E2Eコード構築]

    subgraph IterativeCycle [自動テスト・デバッグ・修復サイクル]
        Step2A[2-A. DB全ドロップ & 復元<br/>data-backup/ から初期化] --> Step2B[2-B. 自動テスト実行<br/>ヘッドレスブラウザ E2E]
        Step2B --> Judge{全テストパス？}

        Judge -- はい --> StepReport[最終テスト結果レポート作成<br/>docs/plans/scenario-test/ 配下]

        Judge -- いいえ (Fail/Abend) --> Step3[3. 原因分類・追跡 & RCA記録<br/>log_id & ログ解析 & wiki-maintainer]

        Step3 --> CauseBranch{エラーの原因種別}

        CauseBranch -- A. テストスクリプトの不具合<br/>(DOM変更/待機不備/アサーションミス) --> Step3A[3-A. テストコード自律自動修復<br/>(ユーザー承認 不要)]
        Step3A --> RetryCheck{リトライ回数 <= 5回？}
        RetryCheck -- はい --> Step2A
        RetryCheck -- いいえ (5回超過) --> Step3A_Fail[スクリプト修復不能通知<br/>ユーザーへエラー報告]

        CauseBranch -- B. システムの不具合<br/>(バックエンド/フロントエンド/DBバグ) --> Step4[4. エラー原因・解決案提示<br/>根本原因 & コードDiff提示 (QA)]
        Step4 --> Step5[5. ユーザー承認 & システム修正<br/>(BE/UIがコード修正 ──► コンテナ再ビルド)]
        Step5 --> Step2A
    end

    StepReport --> End([シナリオテストフェーズ完了])
```

## **3. 自動テスト環境・構成要件**

シナリオテストを安全かつ高速に反復実行するための自動化基盤および各種モック構成を以下に定義する。

```
+-----------------------------------------------------------------------------------+
|                        E2E Test Runner (Playwright)                               |
+-----------------------------------------------------------------------------------+
    │                                 │                                 │
    ▼ (1. HTTP API & SPA)             ▼ (2. DB Restore)                 ▼ (3. Logger API)
+------------------------+   +------------------------+   +------------------------+
| Frontend (React / Vite)|   | Test DB (SQLite)       |   | Backend (FastAPI)      |
|  - IAP Mock Header     |   |  - Full Drop & Restore |   |  - POST /internal/logger|
|  - GCS Canvas Compress |   |    from data-backup/   |   |  - log_id (UUIDv4)     |
+------------------------+   +------------------------+   +------------------------+
```

### **3.1. 自動テストツール・フレームワーク**

- **採用ツール**: **Playwright (Node.js / TypeScript)**
- **選定理由**:
  - 最新の React SPA（Vite）との親和性が高く、高速な並列実行・ヘッドレスブラウザ実行に対応。
  - デバイスエミュレーション機能により、**デスクトップ表示（768px以上）** と **モバイル表示（767px以下）** の切り替えテストが容易。
  - テスト失敗時に自動的にスクリーンショット (PNG)、画面録画 (WebM)、および DOM トレース (Trace Viewer) を保存可能。

### **3.2. テスト専用データベース Drop & Restore（全テーブル自動復元）方針**

- **課題・目的**:
  - システム修正に伴う反復的なテスト実行時、以前のテストによってデータの挿入・更新・削除が行われた状態のままだと、後続のテスト結果に影響（データの不均衡・件数不一致・重複エラー等）を及ぼす。
- **データ復元メカニズム (Restoration Mechanism)**:
  1. **実行タイミング**: Playwright の `globalSetup`（テスト実行前のグローバル前処理フック）にて自動トリガー。
  2. **テーブル全ドロップ**: テスト用データベース (`backend/data/app.test.db` / `app.db`) の全テーブルおよびインデックスをドロップ（または DB ファイルを削除・リセット）。
  3. **`data-backup/` からの復元**:
     - `data-backup/app.db` のバイナリコピー、または `data-backup/app_dump.sql` / `data-backup/schema.sql` から最新の確定済みマスタ・基準データを完全リロード。
  4. **決定論的再現性の担保**: 各テスト実行（ステップ2）は常に 100% 同一の初期データ状態から開始されるため、反復テストによるデータドリフトや不均衡が完全に排除される。

### **3.3. Cloud Run IAP 認証モック環境**

- **対抗策**:
  - テスト実行時、Playwright の `extraHTTPHeaders` または `browserContext.setExtraHTTPHeaders` にて IAP 認証ヘッダー (`x-goog-authenticated-user-email: testuser@example.com`) を付与。
  - バックエンドおよびフロントエンドの認証ミドルウェアが正常にユーザーコンテキストを読み込めることをアサーション。

### **3.4. 画像ストレージ (Google Cloud Storage) モック環境**

- **課題**: 実際に GCS バケットへアクセス・画像送信を行うと、テスト実行コストの肥大化やテスト速度低下が生じる。
- **対抗策**:
  - **GCS 画像APIモック**: バックエンドの GCS 連携エンドポイント (`GET /api/storage/images`) および画像参照 URL 返却ロジックをテスト用ローカル画像ディレクトリへの参照にモックマッピング。
  - **フロントエンド事前圧縮検証**: 画像選択・アップロード時、ブラウザ側（Canvas API）で 700px × 700px 正方形 WebP 形式 (画質 80%) に正常圧縮されて送信されるか、および画面上の表示が 1:1 正方形 (`aspect-square object-cover`) でレイアウト維持されているかをアサーション検証。

### **3.5. AI駆動構造化ロギングおよびデバッグ連携基盤**

- **ログ回収**: バックエンドの標準出力（`sys.stdout`）に出力される JSON 構造化ログ（JSTタイムスタンプ付き）をテストランナーがリアルタイム監視。
- **`log_id` 自動トラッキング**: テスト実行中に HTTP 500 やエラーレスポンスが返却された場合、レスポンス内の `log_id` (UUIDv4) を自動抽出してテストログにバインド。
- **動的ログレベル切替**: エラー発生時、テストランナーまたは AI が即座に `POST /api/internal/logger/level` (`x-ai-token` 認証, `{"level": "DEBUG"}`) を呼び出し、コンテナ再起動なしでバックエンドを DEBUG モードに移行して再現実験を行う。

## **5. 不具合原因追跡・自動修復・承認プロセスの詳細設計**

テスト実行で失敗（Fail）またはAbend（異常終了）が発生した場合、以下のルールに基づいて自律デバッグ・自動修復・ユーザー承認・再テストを実施する。

### **5.1. 不具合発生時のエビデンス自動収集**

テスト失敗検知時、 Playwright テストランナーおよびテスト基盤は以下のエビデンスを自動生成・保管する：

1. **画面スクリーンショット**: 失敗直前の画面状態 (`docs/reports/evidences/screenshot_{test_id}.png`)
2. **ブラウザコンソールログ**: フロントエンドの JavaScript エラー・スタックトレース
3. **バックエンド構造化ログ**: HTTP レスポンスに含まれる `log_id` に紐づく JSON エラーログ

---

### **5.2. エラー原因の2大分類と自律対処分岐**

AI (Antigravity) は収集されたエビデンスおよび `log_id` を解析し、エラーの根本原因を「**テストスクリプトの不具合**」と「**システムの不具合**」の2つに自律分類する。

```
                       【不具合検知・ログ解析】
                                  │
                 ┌────────────────┴────────────────┐
                 │                                 │
    [A. テストスクリプトの不具合]             [B. システムの不具合]
                 │                                 │
                 ▼                                 ▼
   +---------------------------+     +---------------------------+
   | ・ユーザー承認 不要       |     | ・ユーザー承認 必須       |
   | ・AIがテストコード自律修復|     | ・AIが原因とDiff案を提示  |
   | ・DB復元後自律リトライ    |     | ・人間承認後にシステム修正|
   | ※ 最大 5 回リトライまで   |     | ・DB復元後再テスト        |
   +---------------------------+     +---------------------------+
```

#### **5.2.1. A. テストスクリプトの不具合（自律自動修復 & 最大5回リトライ）**

- **定義・適用条件**:
  - UIデザイン変更やコンポーネント改修に伴う DOM セレクター（data-testid, クラス名）の不一致。
  - 非同期処理・アニメーション完了前の操作によるタイムアウトや待機条件（`waitForSelector`, `page.waitForLoadState`）の不備。
  - テストコード内のアサーション記述誤り、またはテスト用ダミーデータの指定ミス。
- **自律修復 & リトライ手順**:
  1. **ユーザー承認スキップ**: 人間の確認・承認を待たずに、AIが自律的にテストコード (`tests/e2e/`) を修正・修復する。
  2. **DB自動再復元 (ステップ2-A)**: テストデータの整合性を保つため、データベースを `data-backup/app.db` から再初期化する。
  3. **自動リトライ実行**: 修正したテストスクリプトでテストを自動再実行する。
  4. **上限回数設定**: **リトライは1タスクにつき最大5回まで**とする。5回のリトライを繰り返しても不具合が解消しない場合は、テストスクリプト修復不能または隠れたシステム不具合として処理を停止し、エビデンスとともにユーザーへ通知する。

#### **5.2.2. B. システムの不具合（原因・Diff提示 ➔ ユーザー承認 ➔ コード修正）**

- **定義・適用条件**:
  - FastAPI バックエンドにおける例外発生（500 Internal Server Error, SQL制約違反, 型バリデーションエラー等）。
  - React フロントエンドの表示ロジック、状態管理（State）、コンポーネント挙動のバグ。
  - テーブルスキーマ、APIエンドポイント、ビジネスロジック仕様との不一致。
- **承認・修正手順**:
  1. AIが `log_id` およびスタックトレースから根本原因を特定。
  2. ユーザー（人間）に対し、後述のフォーマットで原因・影響範囲・コード修正Diff案を提示。
  3. **ユーザーからの「承認」を獲得した後**に、実際のソースコードを修正する。未承認の修正は一切行わない。
  4. ステップ2-A（DB復元）を経て、再テスト・回帰テストを実行する。

### **5.3. システム不具合発生時のユーザー（人間）提示フォーマット**

システム不具合と判定された場合、AIは自律的にシステムコードを修正する前に、必ず以下のフォーマットで原因と修正案を提示し、**ユーザーの承認を獲得**する。

> ### 📋 システム不具合分析 & 修正提案レポート
>
> **【失敗ケース】**: シナリオ 3.4「データ履歴追加」  
> **【エラー概要】**: HTTP 500 Internal Server Error (log_id: `c4e6c1b8-cd43-4863-ac3f-17899ec23456`)  
> **【根本原因】**: `entity_logs` レコード挿入時、リクエストの `performed_at` タイムスタンプに含まれるタイムゾーンオフセット表記のフォーマットがバックエンドの日時バリデータで正しくパースできず `ValueError` が発生した。  
> **【修正範囲】**:
>
> - `backend/app/schemas/entity_log.py`: `performed_at` の ISO 8601 (JST) パースロジックを拡充
> - `frontend/src/components/DetailModal.jsx`: 日時ピッカーからの送信フォーマットを JST `YYYY-MM-DDTHH:MM:SS+09:00` に統一  
>   **【コード修正Diff案】**:
>
> ```diff
> - performed_at: datetime = Field(...)
> + performed_at: datetime = Field(..., description="JST datetime ISO 8601 string")
> ```
>
> **上記修正案でコード修正および再テストを実行してよろしいでしょうか？ [(承認) / (修正指示)]**

---

### **5.4. 承認後の修正・再テスト（回帰テスト）フロー**

1. **ユーザー承認**: ユーザーから「承認」を得たら、該当コードの修正を行う。
2. **ステップ2-A (DB自動復元) の実行**: システム修正後の自動テスト実行前に、データベースの全テーブルをドロップし `data-backup/app.db` から初期データを完全復元。
3. **単体再テスト & 回帰テスト**: 失敗したテストケースの再確認に加え、全シナリオ（01〜08）を一括自動再実行し、他機能への影響（エンバグ）が無いことを検証。
4. **合格レポート出力**: 全ケース合格を確認後, 最終テスト結果レポートを出力してシナリオテストフェーズを完了とする。
