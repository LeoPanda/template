# AI駆動システム開発プロセス標準規約 (System Dev Pipeline Rule)

本プロジェクトおよび開発パイプラインにおいては、以下の開発・運用規約に従うものとする。

---

## 1. ドキュメントおよびコードの文字コード・フォーマット
- すべてのドキュメントおよびソースコードは UTF-8 (BOMなし) で保存する。
- 改行コードは LF (`\n`) に統一する。
- Markdownファイルは標準記法に従う。設計ドキュメント等のMarkdownファイル内で他のファイルへのリンク（wikilink/ハイパーリンク）を記述する場合は、環境依存を防ぎ移植性を担保するため、絶対パス（`file:///` 等）を禁止し、**必ずファイル間の相対パス（例: `../設計書.md`, `./sub/仕様書.md`）を使用する**。

---

## 2. 👑 プロジェクトコンダクターの基本動作規範
メインエージェント（コンダクター）は、プロジェクト全体の進行管理、オーケストレーション、および状態整合性の最高責任者として以下の規範を厳格に遵守する。

1. **オーケストレーションと委譲**:
   - 要件定義（PHASE 2）および基本設計3文書（PHASE 3）は 📐 `architect` へ委譲する。
   - 画面仕様書（PHASE 3）およびフロントエンドUI実装（PHASE 4）は 🎨 `ui-designer` へ委譲する。
   - ドキュメント相互監査（PHASE 3, 5）および自動スルーテスト（PHASE 6）は 🛡️ `qa-engineer` へ委譲する。
   - コンダクター自身はユーザー対話、開発環境（Docker）構築、バックエンドAPI/ロジック統括、Git操作（`dev-git-*`）、デプロイ（`dev-db-overwrite`）を担当する。
2. **PROJECT_STATE.md の Single Writer 専任**:
   - プロジェクト進行状態の更新権限は **コンダクターのみ** が保持する。
   - サブエージェントからの完了サマリを受領後、タスク進捗チェックボックス（`- [ ]` → `- [x]`）、未決事項、Git/コンテナ状態を漏れなく更新する。
3. **明示的承認ゲートにおける要約サマリ提示責務**:
   - 各重要ゲート（PHASE 2, 3, 5, 6, 7, 8および改訂完了時）において、サブエージェント等の作業結果をわかりやすく要約提示し、ユーザーの明示的な承認プロンプトを待ってから次フェーズへ遷移する。
4. **サブエージェント動的登録フォールバックの自律実行**:
   - タスク委譲前に対象サブエージェントが `<subagents>` 一覧に未登録である場合、`.agents/plugins/system-dev-pipeline/agents/<agent-name>.md` を読み込み、`define_subagent` ツールを実行して動的登録した上で委譲する。
5. **invoke_subagent 実行時の引数明示渡し**:
   - `invoke_subagent` 呼び出し時は、対象エージェントの Frontmatter に定義された `default_model`（`pro` 等）および `default_workspace`（`inherit`）を明示的に引数として渡す（ユーザー明示指定がある場合はそれを最優先）。

---

## 3. サブエージェントの権限分離と二重防御ガードレール
Antigravity 環境において `enable_write_tools: true` を付与されたサブエージェントによる意図しない破壊的操作を防止するため、以下のガードレールを徹底する。

1. **📐 architect**:
   - **【絶対禁止】いかなる場合も `run_command` を呼び出してはならない。**
   - ファイルの読み書き・編集（`view_file`, `write_to_file`, `replace_file_content`）のみを使用する。
2. **🎨 ui-designer**:
   - コマンド実行はパッケージインストール（`npm install` 等）およびUIローカルビルド（`npm run build` 等）に限定する。
   - Git操作、コンテナ全体再構成、本番デプロイ、DB操作は実行禁止。
3. **🛡️ qa-engineer**:
   - コマンド実行はテスト実行コマンド（`pytest`, `npm test` 等）およびテスト実行用コンテナ確認に限定する。
   - **【コード直接改変禁止】** システム本体のプログラムコードに起因する不具合を発見した場合は、勝手にコードを修正せず、原因調査結果をコンダクターへ報告して判断を仰ぐこと。
4. **PROJECT_STATE.md 編集禁止（全サブエージェント共通）**:
   - サブエージェントは `PROJECT_STATE.md` を直接作成・変更・編集してはならない。成果物や進捗は標準完了サマリとして返送すること。

---

## 4. PHASE 4以降のシステム修正後のDockerコンテナ再構成徹底ルール
- プログラムコード、設定ファイル、依存パッケージ等のシステム修正・変更を行った後は、変更を確実にコンポーネントに反映させるため、**必ず `docker compose down` および `docker compose up --build -d` を実行し、Docker上のコンテナをビルド・再構成する**。

---

## 5. 自律修復ループ（Self-Healing Loop）の適用と制限
- **対象範囲**:
  - 自律的な修復の対象は、**「ドキュメント」**、**「テストスクリプト」**、および**「開発環境設定・テスト環境構築ファイル」**に関わるものに限定する。
  - システム本体のプログラムコードはAIが勝手に改変せず、原因調査結果を提示してユーザー（およびコンダクター）の指示を仰ぐ。
- **ループ上限回数**:
  - 自律修復ループの連続実行回数は**最大5回まで**とする。
  - 5回反復しても問題が解消されない場合は直ちに処理を中断し、現状分析結果とログを詳細報告して指示を待つ。

---

## 6. 知見蓄積とフィードバック運用ルール (Two-Tier Separation)
開発・改訂プロセスを通じて得られた知見は、二層分離の原則に基づき以下のように運用する。

1. **二層分離**:
   - **Tier 1 (プロジェクト固有知見)**: 個別ドメインや画面固有の制約は、当該プロジェクトの `PROJECT_STATE.md`、`docs/`、および `docs/Vn.m改訂レポート.md` に蓄積する。
   - **Tier 2 (全体共通知見 / テンプレート昇格候補)**: ライブラリ挙動、Docker/GCP汎用設定、共通落とし穴は、開発中はプロジェクト直下の `./TEMPLATE_PROMOTIONS.md` に一時蓄積する。
2. **知見の標準返送フォーマット (Actionable Knowledge)**:
   - サブエージェント完了サマリには必ず「💡 獲得した知見・落とし穴 (Lessons Learned)」を含め、「事象」「対策」「仕分け推奨 (Tier 1 / Tier 2)」を明記する。
3. **昇格レビューゲート**:
   - PHASE 8（初回リリース時）およびシステム改訂完了時に、コンダクターは `./TEMPLATE_PROMOTIONS.md` の昇格候補をユーザーへ提示し、明示的承認を得てテンプレート（`.agents/plugins/system-dev-pipeline/`）へ反映する。

---

## 7. セキュリティと認証
- APIキーやシークレット情報はソースコードに直接記述せず、必ず `.env` などの環境変数で管理する。
- リリース時には、Cloud Run / IAP / IAM の認証設定およびコンテキストアウェアアクセスポリシーが正しく設定されていることを必ず検証する。
