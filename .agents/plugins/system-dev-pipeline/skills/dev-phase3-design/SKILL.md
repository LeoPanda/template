# PHASE 3: 基本設計書の作成とドキュメント整合性チェック

- **主担当エージェント**: 📐 設計・立案スペシャリスト (`architect`)（※画面仕様書はコンダクターより 🎨 `ui-designer` へ独立委譲、整合性監査は 🛡️ `qa-engineer` が主担当）
- **委譲元 / 統括**: 👑 プロジェクトコンダクター (`conductor`)
- **承認ゲート**: 👤 ユーザーによる明示的承認必須

要件定義書に基づき、以下の3大基本設計書を作成および精査してください。

## 1. 担当設計書雛形の作成
プラグインの `templates/` から以下の3ドキュメントを `docs/` に保存・作成してください。
- `技術要件定義書.md`
- `ビジネスロジック仕様書.md`
- `テーブルスキーマ定義書.md`

`docs/要件定義書.md`、`docs/AI駆動ロギングシステム仕様書.md`、`docs/APIキー安全管理・一元化設計書.md` の情報を踏まえ、各設計ドキュメントを本プロジェクト用に完全な記述として完成させてください。

> [!IMPORTANT]
> 要件定義書に表された機能を実現するための技術要件が要件定義書にも技術要件定義書にも不足している場合は、そのことを完了サマリの残課題に明示してコンダクターの指示を仰いでください。
> 画面仕様書（`docs/画面仕様書.md`）は 🎨 `ui-designer` が作成するため、テーブルスキーマ定義書のエンティティ名・カラム名・型定義を明確にし、画面側のフォーム項目と整合するように配慮してください。

## 2. 標準完了サマリの返却

作業完了後、呼び出し元エージェント（コンダクター）に対して、所定のフォーマットで完了サマリを返送してください。

```markdown
## 作業完了サマリ
- **担当エージェント**: architect
- **実施フェーズ / タスク**: PHASE 3 基本設計書作成 (技術・スキーマ・ロジック)
- **ステータス**: SUCCESS / PENDING_USER_INPUT / FAILED
- **生成・更新ファイル一覧**:
  - docs/技術要件定義書.md
  - docs/テーブルスキーマ定義書.md
  - docs/ビジネスロジック仕様書.md
- **設計の要点・特記事項**:
  - [設計の決定理由、考慮したエッジケース]
- **💡 獲得した知見・落とし穴 (Lessons Learned)**:
  - **事象**: [発生した課題・落とし穴（あれば、なければ「特になし」）]
  - **対策**: [回避策・推奨ルール]
  - **仕分け推奨**: Tier 1 (プロジェクト固有) / Tier 2 (全プロジェクト共通)
- **残課題 / Open Questions**:
  - [ユーザー確認が必要な事項（あれば）]
```
