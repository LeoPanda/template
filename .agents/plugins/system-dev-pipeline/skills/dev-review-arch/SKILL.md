# 基本設計レビュー (Basic Design Review) スキル

- **主担当エージェント**: 🛡️ 品質・テスト & 監査・QAスペシャリスト (`qa-engineer`) (Model: `pro`)
- **委譲元 / 統括**: 👑 プロジェクトコンダクター (`conductor`)
- **適用フェーズ**: PHASE 3 完了ゲート
- **合否判定ゲート**: `PASS` または `CONDITIONAL PASS` で PHASE 4 へ進行可能。`REJECT` の場合は 📐 `architect` へ是正差し戻し。

---

## 1. 入力ドキュメント
監査対象として以下のドキュメントを読み込みます：
- `docs/要件定義書.md`（特に選定されたシステム展開プロファイル: Profile A〜D）
- `docs/技術要件定義書.md`
- `docs/テーブルスキーマ定義書.md`
- `docs/ビジネスロジック仕様書.md`
- `docs/画面仕様書.md`

---

## 2. 監査観点（二層型レビューアーキテクチャ）

### 第1層: 定常的観点 (Universal Core Criteria - 全システム共通)
1. **データ破壊・不整合リスク**:
   - トランザクション境界の欠落、外部キー制約の不備、同時更新競合対策の有無。
2. **クラッシュ・稼働停止リスク (SPOF)**:
   - 例外ハンドリングの漏れ、外部APIタイムアウト対策、リトライ暴走の危険性。
3. **過剰設計 / YAGNI原則違反**:
   - 要件にない過度な抽象化、不要なマイクロサービス化、複雑すぎる状態管理。

### 第2層: 可変的観点 (Context-Adaptive Profiles - プロファイル別)
要件定義書で選定されたプロファイルに応じて監査項目を適用します：
- **Profile A (クラウド公開・Webサービス型)**:
  - 水平スケーラビリティ、ステートレス設計、IAM/IAP認証認可、Cold Start対策。
- **Profile B (ローカル常駐・閉鎖環境型)**:
  - ローカルリソース消費（メモリ/CPU）、ホストポート競合、オフライン動作耐性。
- **Profile C (個人利用・小規模・プロトタイプ型)**:
  - 構成のシンプルさ、不要なインフラ依存の排除、最小設定での即時起動性。
- **Profile D (モバイル・エッジクライアント型)**:
  - オフライン同期、バッテリー・通信量配慮、バックグラウンド制約。

---

## 3. レビュー結果の作成と判定

監査結果を `docs/plans/基本設計レビュー結果報告書.md` に出力します。

### 合否判定基準:
- **`PASS`**: 重大欠陥（Critical / High）が0件、かつMediumが軽微。
- **`CONDITIONAL PASS`**: Medium以下の指摘のみで、実装フェーズ中の対応方針が明確である場合。
- **`REJECT`**: Critical（設計破綻、致命的データ欠損リスク、SPOF）または High（主要要件未達、重大な性能懸念）が1件以上存在。

---

## 4. 標準完了サマリの返却

コンダクターへ以下の形式でサマリを返送してください。万一重大な設計課題やトラップを発見した場合は、`wiki-maintainer` によるRCA記録も検討してください。

```markdown
## 作業完了サマリ
- **担当エージェント**: qa-engineer
- **実施フェーズ / タスク**: PHASE 3 基本設計レビュー (`dev-review-arch`)
- **判定結果**: PASS / CONDITIONAL PASS / REJECT
- **生成ファイル**: docs/plans/基本設計レビュー結果報告書.md
- **指摘概要**:
  - Critical: X件
  - High: Y件
  - Medium/Low: Z件
- **主な指摘事項**:
  - [指摘内容と修正推奨案]
- **💡 獲得した知見・落とし穴 (Lessons Learned)**:
  - **事象**: [設計上のアンチパターンや落とし穴（あれば）]
  - **対策**: [推奨ルール]
  - **仕分け推奨**: Tier 1 / Tier 2
- **次のアクション**: [PASSならPHASE 4着手、REJECTならarchitect是正]
```
