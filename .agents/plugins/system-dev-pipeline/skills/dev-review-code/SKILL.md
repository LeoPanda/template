# コード品質・整合性レビュー (Code Quality & Consistency Review) スキル V2.4

- **主担当エージェント**: 🛡️ 品質・テスト & 監査・QAスペシャリスト (`qa-engineer`) (Model: `pro`)
- **委譲元 / 統括**: 👑 プロジェクトコンダクター (`conductor`)
- **適用フェーズ**: PHASE 5.5 完了ゲート (ウォークスルー完了後、テスト本格実行前)
- **重要規約**: **レビュアーはプログラムコードを直接改変してはならない。** 指摘内容およびUnified Diffを報告書にまとめ、コンダクター経由で `backend-engineer` または `ui-designer` へ是正を委譲する。

---

## 1. 入力成果物
監査対象として以下のコード・設定群を走査します：
- `src/` 配下のフロントエンドおよびバックエンド全実装コード
- `Dockerfile`, `docker-compose.yml`, 各種設定ファイル (`tsconfig.json`, `package.json`, `pyproject.toml` 等)
- 自動生成された型定義ファイル (`src/types/api.generated.ts` 等)
- モック定義 (`src/mocks/handlers.ts`, `src/mocks/browser.ts`)
- 設計書群（`docs/テーブルスキーマ定義書.md`, `docs/ビジネスロジック仕様書.md`, `docs/バックエンドAPI仕様書.md`, `docs/画面仕様書.md` 等）

---

## 2. 監査観点（定量的・定性的メトリクス）

### 2.1 【最重要】ファイル規模制限（Anti-God Component / Anti-God Module & DTO・パーサー分離）
- **フロントエンド UI/Hooks/Services**: 原則 **1ファイル最大250行以下**（JSDoc/コメント・空行含む総行数）。
  - 超過したファイルは問答無用で `REFACTOR RECOMMENDED` または `BLOCKED` とする。
  - 巨大コンポーネントは、プレゼンテーション部品、カスタムHooks (`useXxx`)、APIサービスクライアント (`services/`)、定数/型定義へと責務分解させること。
- **バックエンド コントローラ/サービス/モデル**: 原則 **1ファイル最大400行以下**（推奨250〜300行以内）。
  - DTO（Data Transfer Object）構造体および型変換関数は独立モジュール（`schemas/`, `*_dto.rs` 等）へ物理分離されているか。
  - パーサー本体が純粋なアルゴリズムとバリデーションに責務限定され、データ型定義と同居していないか。
  - ハンドラー内にダミーデータや直書きモックを保持せず、DBアクセス層または動的生成ヘルパーに委譲しているか。

### 2.2 【最重要】直書きモックデータの完全排除
- **コンポーネント内直書きモックの禁止**:
  - React/Vue等のコンポーネント内やHooks内に、ハードコードされたダミー配列・オブジェクト（`const mockUsers = [...]` 等）が残存していないか厳格チェック。
  - テスト・開発用ダミーデータはすべて MSW (`src/mocks/handlers.ts`) に集約され、環境変数 `VITE_ENABLE_MOCK=true` でのみ注入される構造になっているか確認。
  - 直書きモックを発見した場合は `BLOCKED` 判定とし、APIクライアント経由の取得 + MSWハンドラーへの移行を指示する。

### 2.3 型安全性とスキーマ同期
- **OpenAPI / スキーマ同期**:
  - `src/types/api.generated.ts` とバックエンド Pydantic/スキーマが整合しているか。
  - フロントエンド側で API レスポンスやリクエストに `any` 型や手動定義の重複型を使用せず、生成型を適切に import してバインドしているか。
- **型アサーション・バイパスの排除**:
  - 不正な `as any`, `as unknown as T`, `!` (Non-null assertion) の濫用がないか。

### 2.4 日時処理の Aware UTC 徹底
- フロントエンドおよびバックエンドで、タイムゾーンなしの素の `new Date().toISOString()` や Naive datetime が直接乱用されていないか。
- 共通日時ユーティリティ（フロント: `src/utils/dateTime.ts`、バック: `datetime.now(timezone.utc)` 等）が徹底されているか。

### 2.5 DRY原則違反・デッドコード
- 重複ロジック、コピペコード、共通化可能なユーティリティの放置。
- 呼び出されていない関数・変数・未使用インポート、不要なCSSクラスの残存。

### 2.6 【最重要】UIデイライトモード視認性担保 (V2.4)
- **ダーク前提淡色・透過カラー単独直書きの排除**:
  - コンポーネント内の文字色や背景色に、ダークモード前提の淡色・透過カラー（`text-blue-200`, `bg-blue-950/40` 等）が単独で直書きされていないか。
  - セマンティックデザイントークン（CSS変数一元制御）またはTailwindの明暗ペア（例: `bg-blue-50 text-blue-800 dark:bg-blue-950/40 dark:text-blue-300`）が指定され、ライトモード下でも十分な視認性とコントラストが確保されているか。

## 3. レビュー結果の作成と判定

監査結果を `docs/plans/コード品質レビュー及びリファクタリング提案書.md` に出力します。指摘箇所には必ず具体的な **Unified Diff 形式の改善コード案** を添付してください。

### 合否判定基準:
- **`CLEAN`**: 指摘事項なし、または極めて軽微なコメントのみ。250行超過なし、直書きモックなし。PHASE 6 へ進行。
- **`REFACTOR RECOMMENDED`**: リファクタリング推奨事項（軽微な重複排除、一部モジュール分割等）が存在するが、直書きモックや重大な型破壊はない。コンダクターが判断して修正を委譲。
- **`BLOCKED`**: フロント250行超過の放置、直書きモックデータの残存、重大な型安全性崩壊、設計乖離が存在。PHASE 6 への進行を阻止し、修正必須。
