# コード品質・整合性レビュー (Code Quality & Consistency Review) スキル

- **主担当エージェント**: 🛡️ 品質・テスト & 監査・QAスペシャリスト (`qa-engineer`) (Model: `pro`)
- **委譲元 / 統括**: 👑 プロジェクトコンダクター (`conductor`)
- **適用フェーズ**: PHASE 5.5 完了ゲート (ウォークスルー完了後、テスト本格実行前)
- **重要規約**: **レビュアーはプログラムコードを直接改変してはならない。** 指摘内容およびUnified Diffを報告書にまとめ、コンダクター経由で `backend-engineer` または `ui-designer` へ是正を委譲する。

---

## 1. 入力成果物
監査対象として以下のコード・設定群を走査します：
- `src/` 配下のフロントエンドおよびバックエンド全実装コード
- `Dockerfile`, `docker-compose.yml`, 各種設定ファイル (`tsconfig.json`, `package.json`, `pyproject.toml` 等)
- 設計書群（`docs/テーブルスキーマ定義書.md`, `docs/ビジネスロジック仕様書.md`, `docs/バックエンドAPI仕様書.md` 等）

---

## 2. 監査観点（定量的・定性的メトリクス）

1. **DRY原則違反 (重複コード)**:
   - 同一・類似ロジックの重複、コピペコード、共通化可能なユーティリティの放置。
2. **単一責任原則 (SRP) とファイル規模制限**:
   - モジュール全体のファイル行数: 原則 **400行以下**。
   - UIコンポーネントの行数: 原則 **300行以下**。肥大化した神クラス/神コンポーネントの分割。
3. **デッドコード・未使用依存の排除**:
   - 呼び出されていない関数・変数・未使用インポート、不要なCSSクラスの残存。
4. **型安全性の徹底**:
   - `any` 型の乱用、型アサーションによるバイパス、null/undefined 安全性の欠落。
5. **設計書との整合性**:
   - スキーマ定義のカラム名・型とコードの実装が一致しているか。

---

## 3. レビュー結果の作成と判定

監査結果を `docs/plans/コード品質レビュー及びリファクタリング提案書.md` に出力します。指摘箇所には必ず具体的な **Unified Diff 形式の改善コード案** を添付してください。

### 合否判定基準:
- **`CLEAN`**: 指摘事項なし、または極めて軽微なコメントのみ。PHASE 6 へ進行。
- **`REFACTOR RECOMMENDED`**: リファクタリング推奨事項（重複排除、行数超過分割など）が存在するが、ブロッキングではない。コンダクターが判断して修正を委譲。
- **`BLOCKED`**: 重大な保守性阻害、型安全性崩壊、重篤な設計乖離が存在。PHASE 6 への進行を阻止し、修正必須。
