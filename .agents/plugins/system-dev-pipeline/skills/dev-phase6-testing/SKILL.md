# PHASE 6: スルーテスト環境の構築と自動テスト実施

- **主担当エージェント**: 🛡️ 品質・テスト & QA (`qa-engineer`)
- **委譲元 / 統括**: 👑 プロジェクトコンダクター (`conductor`)
- **承認ゲート**: 👤 ユーザーによる明示的承認必須

自動テストスイートおよびシナリオテストを構築・実行し、すべてのテストがPassするまで修復ループを実行してください。

## 作業手順

1. **シナリオテスト計画書の作成**:
   - プラグインの `templates/シナリオテスト計画書.md` を `docs/plans/シナリオテスト計画書.md` に保存してください。
   - `docs/` 配下の仕様に基づき、テストシナリオ・評価基準を完成させてください。

2. **テスト環境およびテストコードの構築**:
   - テストフレームワーク（E2E / Integration / Unit）をセットアップし、シナリオに基づいたテストコードを作成してください。

3. **自動テストの実行と修復ループ（Self-Healing Loop）**:
   - テストを非同期・自動実行してください。
   - 自律修復の対象は**「テストスクリプト」**および**「テスト・開発環境設定」**に関わる不具合に限定します。
   - **コンテナ再構成の徹底**: テスト環境設定やコードの修復・変更を行った後は、**必ず `docker compose down` および `docker compose up --build -d` を実行して Docker コンテナをビルド・再構成**した上でテストを再実行してください。
   - **【重要】「システムのプログラムコード」の直接改変禁止**:
     システム本体のプログラムコードに起因する不具合・エラーを発見した場合は、**勝手にコード修正を行わず**、原因調査レポートを完了サマリの「残課題・プログラム起因のエラー」に明記してコンダクターへ報告してください。コンダクター（およびユーザー）の指示によってコードが修正された後、テストを再実行します。
   - 修復ループの反復は**最大5回まで**とし、5回を超えてもテストが成功しない場合は処理を中断し、状況を報告してください。

4. **最終ドキュメント整合性レビュー**:
   - テスト完了後、`dev-doc-reviewer` を実行し、修正コードとドキュメント間の整合性を最終確認・補正してください。

5. **標準完了サマリの返却**:
   - テスト結果サマリをコンダクターへ返送してください。コンダクターはこれを受領して `PROJECT_STATE.md` を更新し、ユーザーへ承認ゲート確認を求めます。

## 標準完了サマリ返却フォーマット

```markdown

- **実施フェーズ / タスク**: PHASE 6 スルーテスト実行

  - docs/plans/シナリオテスト計画書.md
  - tests/e2e/test_main.py
- **修復済み項目**:
  - tests/e2e/test_main.py: 待機セレクタ修正
- **💡 獲得した知見・落とし穴 (Lessons Learned)**:
  - **事象**: [テスト実行時のトラップや環境起因のエラー（あれば、なければ「特になし」）]
  - **対策**: [回避策・推奨ルール]
  - **仕分け推奨**: Tier 1 (プロジェクト固有) / Tier 2 (全プロジェクト共通)
- **残課題・プログラム起因のエラー (User Action Required)**:
  - [エラー内容、スタックトレース要約、推定原因、推奨修正案（あれば）]
- **反復回数**: [1〜5] / 5
```
