# PHASE 2: 要件定義書の作成および清書

- **主担当エージェント**: 📐 設計・立案スペシャリスト (`architect`)
- **委譲元 / 統括**: 👑 プロジェクトコンダクター (`conductor`)
- **承認ゲート**: 👤 ユーザーによる明示的承認必須

本スキルは、`docs/要件定義書.md` の精査・詳細化および清書を支援・自動実行します。

## 作業手順

1. **ドキュメントの読み込み**:
   - `docs/要件定義書.md` および `docs/` 配下の背景知識ドキュメントを読み込んでください。
2. **要件定義書の清書・構造化**:
   - 目的、システムの概要、機能要件、非機能要件、外部インターフェース要件、制約事項について漏れや抽象的な表現がないか検証し、具体的に清書してください。
3. **レビューと未決事項（Open Questions）の抽出**:
   - 曖昧な仕様やユーザー確認が必要な事項がある場合は、標準完了サマリの「残課題 / Open Questions」に明記してください。
4. **標準完了サマリの返却**:
   - 作業完了後、呼び出し元エージェント（コンダクター）に対して、所定のフォーマットで完了サマリを返送してください。
   - コンダクターはサマリを受領後、`PROJECT_STATE.md` を更新し、ユーザーへ承認確認（承認ゲート）を提示します。

## 標準完了サマリ返却フォーマット

```markdown
## 作業完了サマリ
- **担当エージェント**: architect
- **実施フェーズ / タスク**: PHASE 2 要件定義
- **ステータス**: SUCCESS / PENDING_USER_INPUT / FAILED
- **生成・更新ファイル一覧**:
  - docs/要件定義書.md
- **設計の要点・特記事項**:
  - [要件の具体化内容、明確化したエッジケース]
- **💡 獲得した知見・落とし穴 (Lessons Learned)**:
  - **事象**: [発生した課題・落とし穴（あれば、なければ「特になし」）]
  - **対策**: [回避策・推奨ルール]
  - **仕分け推奨**: Tier 1 (プロジェクト固有) / Tier 2 (全プロジェクト共通)
- **残課題 / Open Questions**:
  - [ユーザー確認が必要な事項（あれば）]
```
