# 共通ドキュメント相互整合性チェッカー（Self-Healing Reviewer）

- **主担当エージェント**: 🛡️ 品質・テスト & QA (`qa-engineer`)
- **副担当・呼び出し元**: 📐 設計・立案スペシャリスト (`architect`), 👑 プロジェクトコンダクター (`conductor`)

`docs/` 配下に存在するすべてのドキュメントを精査し、文書間の誤植、説明不足、互いの矛盾点を抽出・自動修復してください。
※プロジェクトルート直下の `PROJECT_STATE.md` および `TEMPLATE_PROMOTIONS.md` は状態管理・知見用のため、本スキルの検査対象から除外されます。

## チェック観点マトリクス

1. **要件 vs 設計**: `要件定義書.md` に記載された機能要求が `技術要件定義書.md` や `ビジネスロジック仕様書.md` に漏れなく反映されているか。
2. **画面 vs データ**: `画面仕様書.md` の入力項目・表示項目が `テーブルスキーマ定義書.md` のカラムと型・制約において一致しているか。
3. **ロジック vs テーブル**: `ビジネスロジック仕様書.md` で扱うエンティティ操作が `テーブルスキーマ定義書.md` と整合しているか。
4. **共通標準 vs 各設計**: `AI駆動ロギングシステム仕様書.md` および `APIキー安全管理・一元化設計書.md` の規約が守られているか。

## 実行フロー

1. `docs/` 配下の全ドキュメントを読み込み、上記マトリクスに基づき多角的に精査する。
2. 矛盾点や問題点が発見された場合、標準完了サマリに修復内容または要確認事項として出力する。
3. 不整合が解消されるまでドキュメントの記載を自動補正し、反復検証を行います。ただし自律修復ループの反復は**最大5回まで**とし、5回を超えても不整合が解消されない場合は処理を中断し、未解決箇所の分析サマリをコンダクターに報告して指示を仰いでください。

## 標準完了サマリ返却フォーマット

```markdown
## 作業完了サマリ
- **担当エージェント**: qa-engineer
- **実施タスク**: ドキュメント相互整合性チェック (dev-doc-reviewer)
- **ステータス**: SUCCESS (エラー0件) / PENDING_USER_INPUT / FAILED (MAX_LOOPS_REACHED)
- **修復済み項目**:
  - [修復したファイル名と不整合解消内容]
- **💡 獲得した知見・落とし穴 (Lessons Learned)**:
  - **事象**: [ドキュメント間の典型的な不整合パターン（あれば、なければ「特になし」）]
  - **対策**: [回避策・推奨ルール]
  - **仕分け推奨**: Tier 1 (プロジェクト固有) / Tier 2 (全プロジェクト共通)
- **残課題 / 未解決事項**:
  - [手動判断が必要な事項（あれば）]
- **反復回数**: [1〜5] / 5
```
