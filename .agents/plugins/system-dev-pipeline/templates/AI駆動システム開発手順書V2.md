# AI駆動システム開発手順書V2（サブエージェント協調・PROJECT_STATE一元管理版）

本文書は、Antigravityプラグイン `system-dev-pipeline` における **メインエージェント（コンダクター）、専門サブエージェント（architect, ui-designer, qa-engineer）、および決定論的スキル群** が協調し、プロジェクト進行状態（`PROJECT_STATE.md`）を一元管理しながらシステム開発およびシステム改訂を推進するための具体的な手順、役割分担、および投入プロンプトを定義するものである。

---

## 1. 前提条件とエージェント協調体制

### 1.1 前提条件
1. Antigravity環境において、プラグイン `system-dev-pipeline`（v1.1.0以上）が有効化されていること。
2. 新規開発を行うプロジェクト用ディレクトリ（例: `template/<プロジェクト名>`）をAntigravityで開いていること。

### 1.2 役割分担アーキテクチャ
- 👑 **プロジェクトコンダクター (`conductor` / メインエージェント / Model: `pro`)**: 全体進行統括、ユーザー対話、タスク委譲、`PROJECT_STATE.md` の一元更新（Single Writer）、BE統括、Git/デプロイスキル実行。
- 📐 **設計・立案スペシャリスト (`architect` / サブエージェント / Model: `pro`)**: 要件定義書、3大基本設計書（技術・スキーマ・ロジック）作成、API同期。※`run_command` 禁止。
- 🎨 **UI/UXデザイナー / FE (`ui-designer` / サブエージェント / Model: `flash` または `pro`)**: `画面仕様書.md` 作成、モダンフロントエンド画面・コンポーネント実装、UI微調整。
- 🛡️ **品質・テスト & QA (`qa-engineer` / サブエージェント / Model: `pro`)**: ドキュメント相互整合性監査（`dev-doc-reviewer`）、シナリオテスト計画書作成、自動テスト実行・修復ループ（プログラムコード直接改変禁止）。
- ⚙️ **決定論的スキル群 (`system-dev-pipeline`)**: `dev-phase1-setup` 〜 `dev-phase8-rules`, `dev-git-init`, `dev-git-release`, `dev-db-overwrite`。

---

## 2. 開発フェーズと実行手順 (PHASE 1〜8)

### 2.1 PHASE 1: プロジェクトの準備
新規開発プロジェクトの初期ディレクトリ構造、`.env`、ドキュメント雛形、および状態管理ファイル（`PROJECT_STATE.md`, `TEMPLATE_PROMOTIONS.md`）を自動展開・初期化します。

#### 投入プロンプト
```text
dev-phase1-setup スキルを実行し、本プロジェクトの環境初期化を行ってください。
```

#### 主な作成・配置物
- ディレクトリ: `./docs/`, `./docs/plans/`, `./rules/`
- 状態管理: `./PROJECT_STATE.md`, `./TEMPLATE_PROMOTIONS.md`
- 設定ファイル: `.env`, `<プロジェクト名>.code-workspace`
- ドキュメント雛形: `docs/要件定義書.md`, `docs/AI駆動システム開発フェーズ定義書.md`, `docs/APIキー安全管理・一元化設計書.md`, `docs/AI駆動ロギングシステム仕様書.md`
- **Antigravity IDE GUI設定の提示** (`Settings → Projects → <プロジェクト名>` での権限案内)

---

### 2.2 PHASE 2: 要件定義
👑 コンダクターが 📐 `architect` にタスクを委譲し、`docs/要件定義書.md` を精査・構造化します。

#### 投入プロンプト
```text
dev-phase2-requirements スキルを実行し、docs/要件定義書.md を精査して要件定義書の清書と詳細化を行ってください。
```

#### 承認ゲート
- 📐 `architect` の完了サマリと未決事項（Open Questions）を 👑 コンダクターが確認し、ユーザーへ提示します。
- **【承認ゲート】ユーザーが「要件定義書の内容を承認します」と明示指示**することで、👑 コンダクターが `PROJECT_STATE.md` を更新し PHASE 3 へ進みます。

---

### 2.3 PHASE 3: 基本設計書の作成と整合性チェック
要件定義書に基づき、基本設計書4種を作成し、相互矛盾を自動監査・修復します。
- 📐 `architect`: `技術要件定義書.md`, `テーブルスキーマ定義書.md`, `ビジネスロジック仕様書.md` 作成
- 🎨 `ui-designer`: `画面仕様書.md` 作成
- 🛡️ `qa-engineer`: `dev-doc-reviewer` による多次元クロスチェック・自動修復ループ（最大5回）

#### 投入プロンプト
```text
dev-phase3-design スキルを実行し、基本設計書を作成した上でドキュメント相互の整合性チェックを行ってください。
```

#### 承認ゲート
- ドキュメント整合性エラー0件を確認後、👑 コンダクターが主要設計判断を提示。
- **【承認ゲート】ユーザーが「基本設計書の内容を承認します」と明示指示**することで、`PROJECT_STATE.md` を更新し PHASE 4 へ進みます。

---

### 2.4 PHASE 4: 開発環境とシステム構築
設計書に基づき、ローカル開発環境（Docker）の構築、BE/FEソースコード実装、Gitリポジトリ初期化を行います。
- 👑 コンダクター: Docker環境構築・バックエンドAPI/ロジック統括実装
- 🎨 `ui-designer`: フロントエンド画面・UIコンポーネント実装
- ⚙️ `dev-git-init`: Gitリポジトリ初期化 (`main` 初回コミット、`feature` 作業ブランチ作成)

> [!IMPORTANT]
> **【徹底ルール】PHASE 4以降のシステム修正後のDockerコンテナ再構成**  
> 本フェーズ以降、プログラムコードや設定等を修正した後は、変更を確実にコンポーネントへ反映させるため、**必ず `docker compose down` および `docker compose up --build -d` を実行して Docker コンテナをビルド・再構成する**。

#### 投入プロンプト
```text
dev-phase4-env-build スキルを実行し、docs/配下の設計ドキュメントに基づいて開発環境構築とシステム実装を行ってください。
```

---

### 2.5 PHASE 5: ウォークスルー動作確認とデバッグ
実際の画面操作による動作検証、指摘不具合の修正、および最新コードを正としたAPI仕様書の同期を行います。
- 👤 ユーザー: 画面操作・機能疎通検証
- 👑 コンダクター: 不具合修正統括、修正後のコンテナ再構成 (`docker compose down` → `up --build -d`)
- 📐 `architect`: 実装コードを正としたAPI仕様同期
- 🛡️ `qa-engineer`: ドキュメント整合性の再確認

#### 投入プロンプト
```text
dev-phase5-walkthrough スキルを実行し、設計ドキュメントのファイナライズと同期を行ってください。
```

#### 承認ゲート
- **【承認ゲート】ユーザーが「ウォークスルー動作確認を承認します」と明示指示**することで、PHASE 6 へ進みます。

---

### 2.6 PHASE 6: スルーテスト環境の構築と実施
🛡️ `qa-engineer` がシナリオテスト計画書を作成し、自動テストスクリプト構築、テスト自動実行、修復ループを実行します。
- **自律修復の制限**: ドキュメント、テストスクリプト、テスト環境設定に限定。
- **プログラムコード起因のエラー**: 🛡️ `qa-engineer` はコード本体を直接修正せず、原因調査結果をコンダクターに報告して指示を仰ぎます。
- **修正後のコンテナ再構成**: 修正後は必ず `docker compose down` → `up --build -d` を実行。

#### 投入プロンプト
```text
dev-phase6-testing スキルを実行し、シナリオテスト計画書の作成と自動テスト修復ループを実行してください。
```

#### 承認ゲート
- テスト成功率100%を確認後、**【承認ゲート】ユーザーが「リリース準備移行を承認します」と明示指示**することで、PHASE 7 へ進みます。

---

### 2.7 PHASE 7: 本番リリース
本番環境（Cloud Run等）へ初回デプロイを行い、本番セキュリティ設定を検証します。
- 👑 コンダクター: `docs/plans/本番適用作業手順書.md` 作成、本番デプロイ実行
- 🛡️ `qa-engineer`: IAM / IAP / Cloud Run セキュリティ監査

#### 投入プロンプト
```text
dev-phase7-release スキルを実行し、本番適用作業手順書の作成、リリース実行、および本番セキュリティ設定の検証を行ってください。
```

#### 承認ゲート
- **【承認ゲート】ユーザーが「本番稼働確認を承認します」と明示指示**することで、PHASE 8 へ進みます。

---

### 2.8 PHASE 8: ドキュメント改訂管理の開始と知見昇格
本番運用移行に伴う改訂ルール適用、知見昇格レビュー、およびGit本番リリースを実行します。

#### 実行手順
1. **知見昇格レビュー**: コンダクターが `./TEMPLATE_PROMOTIONS.md` の内容を整理して提示。
2. **【承認ゲート】ユーザーが知見昇格を承認**: 汎用知見をテンプレート側（`.agents/plugins/system-dev-pipeline/`）へ反映。
3. **GitHub本番リリース**: ⚙️ `dev-git-release` により `feature` を `main` へ Squash Merge（`Release v1.0.0`）、Push、次期 `feature` ブランチを切り直し。
4. **改訂ルール適用**: ⚙️ `dev-phase8-rules` により `rules/システム改訂ルール.md`, `AGENTS.md`, `GEMINI.md` を適用。
5. **ステータス更新**: 👑 コンダクターが `PROJECT_STATE.md` を `PRODUCTION_ACTIVE` へ更新。

#### 投入プロンプト
```text
dev-phase8-rules スキルを実行し、今後のシステム改訂ルールおよび運用設定ファイルをプロジェクトに適用してください。
```

---

## 3. 随時実行用ユーティリティプロンプト

#### ドキュメント相互整合性チェックの実行（🛡️ `qa-engineer` 主担当）
```text
dev-doc-reviewer スキルを実行し、docs/ 配下の全ドキュメント間の整合性を精査・修正してください。
```

#### 本番適用後のデータベース上書き・再デプロイ（👑 コンダクター主担当）
```text
dev-db-overwrite スキルを実行し、データベースを含む開発環境のコンテナを本番環境へデプロイしてください。
```
