# AI駆動システム開発手順書（Antigravityスキル活用版）

本文書は、Antigravityプラグイン `system-dev-pipeline` に含まれる各種カスタムスキルを活用し、システム開発を行うための具体的な開発フェーズ、手順、および投入プロンプトを定義するものである。

---

## 1. 前提条件と準備

1. Antigravity環境において、プラグイン `system-dev-pipeline` が有効化（`~/.gemini/config/plugins/` または `.agents/plugins/` に配置）されていること。
2. 新規開発を行うプロジェクト用ディレクトリ（例: `/Users/sakyo/Documents/workspace/AI/<プロジェクト名>`）を作成し、Antigravityで当該ディレクトリを開いていること。

---

## 2. 開発フェーズと実行手順

### 2.1 PHASE 1: プロジェクトの準備

新規開発プロジェクトの初期ディレクトリ構造、`.env`、および `docs/` 配下の各種ドキュメント雛形を自動配置・初期化します。

#### 実行手順

1. Antigravityのチャット画面で以下のプロンプトを入力します。
2. 作成されたディレクトリおよび雛形ファイル群の配置を確認します。

#### 投入プロンプト

```text
dev-phase1-setup スキルを実行し、本プロジェクトの環境初期化を行ってください。
```

#### 主な作成・配置物および提示事項

- ディレクトリ: `./docs/`, `./docs/plans/`, `./rules/`
- 設定ファイル: `.env`
- ドキュメント雛形: `docs/要件定義書.md`, `docs/AI駆動システム開発フェーズ定義書.md`, `docs/APIキー安全管理・一元化設計書.md`, `docs/AI駆動ロギングシステム仕様書.md`
- **Antigravity IDE GUI設定の提示** (`Settings → Projects → <本プロジェクト名>` での各種推奨ポリシーおよび Permission Grants の手動設定案内)

---

### 2.2 PHASE 2: 要件定義

`docs/要件定義書.md` を編集してプロジェクト固有の要件を記述し、AIによって要件定義書を清書・構造化します。

#### 実行手順

1. `docs/要件定義書.md` を開き、背景・目的・作りたいシステムの概要を追記します。
2. 以下のプロンプトを投入し、AIに要件の精査・補完・構造化を行わせます。
3. Artifacts に「要件定義確認事項」が表示された場合は質問に回答し、要件定義書を確定させます。

#### 投入プロンプト

```text
dev-phase2-requirements スキルを実行し、docs/要件定義書.md を精査して要件定義書の清書と詳細化を行ってください。
```

---

### 2.3 PHASE 3: 基本設計書の作成と整合性チェック

要件定義書に基づき、基本設計書4種を作成し、ドキュメント相互の矛盾や技術要件の不足を自動チェックします。

#### 実行手順

1. 以下のプロンプトを入力し、基本設計書の生成とドキュメント相互チェック（Self-Healing Loop）を開始します。
2. **要件不足時の対応**: 要件定義書に記載された機能を実現するための技術要件が要件定義書または技術要件定義書に不足している場合、AIはArtifactsにその旨を明示して一時停止します。内容を確認して指示を与えてください。
3. 矛盾点が0件になるまでAIが自動的にドキュメント補正と再検証を反復実行します。

#### 投入プロンプト

```text
dev-phase3-design スキルを実行し、基本設計書を作成した上でドキュメント相互の整合性チェックを行ってください。
```

#### 主な作成・更新物

- `docs/技術要件定義書.md`
- `docs/ビジネスロジック仕様書.md`
- `docs/画面仕様書.md`
- `docs/テーブルスキーマ定義書.md`

### 2.4 PHASE 4: 開発環境とシステム構築

設計書に基づき、ローカル開発環境の構築、必要パッケージのインストール、ソースコードの初版実装、Git運用基準書の配置、およびGit管理の初期化を行います。

> [!IMPORTANT]
> **【徹底ルール】PHASE 4以降のシステム修正後のDockerコンテナ再構成**  
> 本フェーズで開発環境とシステムを構築した後は、ソースコードの変更が確実にコンポーネントに反映されるようにするため、コードや設定等の修正・変更を行うたびに、**必ず `docker compose down` および `docker compose up --build -d` を実行し、Docker上のコンテナをビルド・再構成するルール**を徹底してください。

#### 実行手順

1. Dockerを起動します。
2. 以下のプロンプトを入力します。
3. Artifacts に技術的な確認事項が表示された場合は回答を入力します。
4. 開発サーバーがローカルで起動し、初期システムが機能することを確認します。
5. `templates/Git運用基準書.md` から `docs/Git運用基準書.md` が配置され、`dev-git-init` によりGit初期化（`main` 基点コミット作成および `feature` ブランチへの切り替え）が行われたことを確認します。

#### 投入プロンプト

```text
dev-phase4-env-build スキルを実行し、docs/配下の設計ドキュメントに基づいて開発環境構築とシステム実装を行ってください。
```

#### 主な作成・成果物

- `docs/Git運用基準書.md` の配置
- バックエンド / フロントエンドのソースコード一式
- 依存ライブラリのインストールと環境構築
- Gitリポジトリ初期化 (`git init`)、初回基点コミット（`main`）、および開発ブランチ（`feature`）の作成

### 2.5 PHASE 5: ウォークスルー動作確認とデバッグ

動作確認テストを実行し、発生した不具合のデバッグ修正と、修正に伴う設計ドキュメントの再同期を行います。

#### 実行手順

1. 起動したシステム上で画面操作や機能疎通のウォークスルーを行います。
2. 以下のプロンプトを入力してデバッグ修正を指示します。
3. **コード修正適用後、AIは必ず `docker compose down` および `docker compose up --build -d` を実行して Docker コンテナをビルド・再構成した上で動作検証を行います。**
4. コード修正完了後、AIが自動的にドキュメント相互チェックを実行し、設計書との乖離を補正します。

#### 投入プロンプト

```text
dev-phase5-walkthrough スキルを実行し、設計ドキュメントのファイナライズと同期を行ってください。
```

---

### 2.6 PHASE 6: スルーテスト環境の構築と実施

シナリオテスト計画書を作成し、自動テストコードの構築、テストの自動実行、エラー自動解析・修復ループを実行します。

#### 実行手順

1. 以下のプロンプトを投入します。
2. `docs/plans/シナリオテスト計画書.md` が生成されるので、テストシナリオを確認・確定します。
3. AIがテストコードを作成・バックグラウンド実行し、テスト修復ループを実行します。
   - **自律修復の対象**: ドキュメント、テストスクリプト、テスト/開発環境設定に関わるものに限定されます。
   - **修正後のコンテナ再構成**: 環境設定やテストに関わる修正を行った後は、**必ず `docker compose down` および `docker compose up --build -d` を実行してコンテナをビルド・再構成**した上でテストを再実行します。
   - **プログラムコード起因のエラー**: システムのプログラムコード自体に起因する不具合が発生した場合は、AI自身でコード修正を行わず、原因調査結果を Artifacts に明記してユーザーの指示を仰ぎます。
   - **ループ上限回数**: 自律修復ループの反復は**最大5回まで**とし、5回を超えた場合は処理を中断して詳細レポートを出力します。
4. テスト完了後、ドキュメントの整合性が自動維持されることを確認します。

#### 投入プロンプト

```text
dev-phase6-testing スキルを実行し、シナリオテスト計画書の作成と自動テスト修復ループを実行してください。
```

#### 主な作成・成果物

- `docs/plans/シナリオテスト計画書.md`
- 自動テストコード（Unit / Integration / E2E）
- 全件PASSのテスト実行ログ

### 2.7 PHASE 7: 本番リリース

完成したシステムを本番環境へデプロイし、本番インフラのアクセス権限・セキュリティ設定（Cloud Run / IAM / IAP）を自動検証します。

#### 実行手順

1. 以下のプロンプトを入力し、最終矛盾チェックと `docs/本番適用作業手順書.md` の作成を行わせます。
2. 手順書に基づき本番デプロイを実行します。
3. デプロイ後、AIが提供するセキュリティ検証チェックリスト（IAM/IAPアクセス設定、AllUsers権限削除など）を確認します。
4. 本番URLにアクセスし、疎通・動作確認を行います。

#### 投入プロンプト

```text
dev-phase7-release スキルを実行し、本番適用作業手順書の作成、リリース実行、および本番セキュリティ設定の検証を行ってください。
```

#### 主な作成・確認事項

- `docs/本番適用作業手順書.md`
- 本番デプロイの完了
- IAM / IAP コンテキストアウェアアクセスポリシーの自動検証結果

## 4. 本番適用後のテーブルスキーマの変更

テーブルに新しい項目を加えるなどスキーマに変更を加える場合、データの保全をするため以下の手順に従うこと。

1. **本番データベースのバックアップ**:
   本番のデータベースをローカルの開発環境にバックアップする。
2. **本番データのローカル適用**:
   ローカルの開発環境にバックアップした本番データを適用する。
3. **改修作業の実施**:
   開発環境でデータベーススキーマの変更を伴うシステムの改修作業を行う。
4. **データ移行（マイグレーション）**:
   必要なら、開発環境内で既存データから新しいデータベースへの移行作業を行う。
5. **テストの実行**:
   開発環境でテストを行う。
6. **本番環境へのデプロイ**:
   `dev-db-overwrite` スキルを用いてデータベースを含む開発環境のコンテナを本番環境へデプロイする。

#### 投入プロンプト

```text
dev-db-overwrite スキルを実行し、データベースを含む開発環境のコンテナを本番環境へデプロイしてください。
```
