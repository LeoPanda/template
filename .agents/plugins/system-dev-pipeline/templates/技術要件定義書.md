# **技術要件定義書 (TECHNICAL_REQUIREMENTS)**

- **主担当エージェント**: 📐 設計・立案スペシャリスト (`architect`)
- **実装担当**: 💻 バックエンドエンジニア (`backend-engineer`), 🎨 UI/UXデザイナー (`ui-designer`)
- **副担当・監査**: 🛡️ 品質・テスト & QA (`qa-engineer`)
- **承認ゲート**: 👤 ユーザーによる明示的承認必須

## **1. システム全体アーキテクチャ**

本システムは、選定された**システム展開プロファイル（Profile A〜D）**に基づき、ローカル環境での自律開発・検証および本番運用環境へのデプロイ・配布を行うハイブリッドホスティング戦略を採用する。

### **システム展開プロファイル別の構成方針**
- **Profile A (クラウド公開・Webサービス型 - 例: Cloud Run + Litestream + IAP)**:
  - **ローカル開発環境 (Docker Compose)**: フロントエンド (`frontend`: React / Vite 3000ポート) とバックエンド (`backend`: FastAPI 8000ポート) を独立したコンテナとして動作させ、高速な HMR (Hot Module Replacement) とデバッグ環境を提供する。
  - **本番運用環境 (Cloud Run + Litestream + IAP)**:
    - フロントエンド (React ビルド成果物) とバックエンド (FastAPI) を同一の Dockerfile（マルチステージビルド）で単一コンテナイメージへパッケージ化し、Cloud Run 上で単一統合サービスとして稼働させる。
    - **ログイン認証とアクセス制限**: Cloud Run の Identity-Aware Proxy (IAP) により、ユーザーのログイン認証およびアクセス制御を行う。
    - **データベース構成 (SQLite + Litestream)**: 低コストかつ高信頼な **SQLite + Litestream** 方式を採用し、バックグラウンドで SQLite の変更ログ（WAL）を GCS (Google Cloud Storage) バケットへリアルタイムレプリケーション・自動復元する。
    - **Litestream 運用の留意事項**:
      - **インスタンス制限**: 複数コンテナによる Litestream の書き込み衝突および WAL データ不整合を防ぐため、Cloud Run の最大インスタンス数を `max-instances=1` に制限設定する。
      - **バックアップ用バケット名のユニーク化**: 同一 GCP プロジェクト上で複数のサービスを稼働させるため、バックアップ用 GCS バケット名には Docker コンテナ名を含めてユニーク化を図る（例: `<project-id>-litestream-<container-name>`）。
- **Profile B (ローカル常駐・閉鎖環境型)**:
  - Docker Compose によるローカルホスト常駐。データ永続化はホストボリュームマウントで完結。外部クラウド通信を最小化または排除。
- **Profile C (個人利用・小規模・プロトタイプ型)**:
  - 単一コンテナまたはローカル軽量プロセス。最小限の依存関係とゼロ運用オーバーヘッド。
- **Profile D (モバイル・エッジクライアント型)**:
  - クライアント完結またはオフライン同期を前提とした省電力・マルチプラットフォーム構成。

- **E2Eテスト環境（Playwright）**: 本システム全体の統合テストおよびシナリオテストを自動実行するため、`tests/e2e/` に Playwright テスト環境を整備する。

## **2. 各レイヤの採用技術（技術スタック）**

### **2.1. タイムゾーン運用方針 (System Timezone Policy)**

- **標準タイムゾーン**: システム内で保持、出力、表示されるすべての記録日時、ログタイムスタンプ、API レスポンスの日付文字列は **日本標準時 (JST, UTC+9 / Asia/Tokyo)** を適用する。
- **コンテナ環境**: コンテナ起動時の環境変数 `TZ=Asia/Tokyo` を統一適用する。

### **2.2. データベースレイヤ (Database Layer)**

- **採用技術**: SQLite (単一ファイル型組み込み RDB) + [選定プロファイルに応じたバックアップ機構]
- **データ保存・永続化方針**: コンテナ内部の `/app/data/app.db` で管理。Profile A の場合は本番環境で Litestream サービスが起動時に GCS バケットから最新の `app.db` をリストアし、稼働中はリアルタイムで WAL 変更ログを GCS へ非同期書き込みすることで、データ損失ゼロと高速アクセスを両立する。
- **Litestream 運用要件 (Profile A選定時)**:
  - **Cloud Run 最大インスタンス制限**: 複数コンテナ（マルチインスタンス）による同データファイルへの同時競合書き込みを防ぐため、Cloud Run のスケール設定で最大インスタンス数を `max-instances=1` に固定制限する。
  - **バックアップバケットのユニーク化**: 他サービスとのバケット衝突を避けるため、バックアップ用 GCS バケット名には Docker コンテナ名を入れて命名する（例: `<project-id>-litestream-<container-name>`）。

### **2.3. バックエンド・サーバーレイヤ (Backend Layer)**

- **主担当**: 💻 バックエンドエンジニア (`backend-engineer`)
- **採用言語**: Python 3.11+
- **採用フレームワーク**: FastAPI
- **採用周辺技術**:
  - `pydantic-settings` (Pydantic ベースの環境変数バリデーション・ロード)
  - `google-cloud-storage` (Google Cloud Storage SDK 連携・画像オブジェクト一覧取得およびアップロード/参照)
  - `AI駆動構造化JSONロギング (logging, sys.stdout)`: JST, UUIDv4 `log_id` 自動バインド, 動的ログレベル変更 API (`POST /api/internal/logger/level`, 認証キー: `INTERNAL_AI_TOKEN`)。
- **主要バックエンド API エンドポイント**: 各エンティティの CRUD 操作、検索・フィルター API、ファイルストレージ連携 API 等。

### **2.4. フロントエンド・プレゼンテーションレイヤ (Frontend Layer)**

- **主担当**: 🎨 UI/UXデザイナー (`ui-designer`)
- **採用技術**: React (Vite ビルド環境) + Tailwind CSS + `Lucide React`
- **構成要素**:
  - SPA（シングルページアプリケーション）構造。1コンポーネントあたり300行以下の設計を厳守。
  - **表示モード切替（マルチテーマ）**: `light` / `dark` / `system` (OS設定追従) の切り替え状態管理および DOM への `dark` クラス動的連動。
  - GCP Cloud Run IAP ヘッダー (`x-goog-authenticated-user-email` / `x-goog-iap-jwt-assertion`) によるシームレスな自動ログイン・アクセス制限・ユーザー識別。

## **3. 画像ストレージ (Google Cloud Storage) 連携仕様**

### **3.1 連携方式およびアクセス権限**

- 本システムでは画像保存方式に **Google Cloud Storage (GCS)** を採用する。
- バックエンドは GCP サービスアカウントまたは ADC (Application Default Credentials) を用いて GCS API / SDK 経由で対象バケットにアクセスする。

### **3.2 オブジェクト管理および入力インターフェース**

- 画像は指定の GCS バケット内に一括管理し、用途や種類ごとのディレクトリ/プレフィックスによるフォルダ分割管理は行わない（すべての画像オブジェクトを一元的に一覧取得・選択可能とする）。
- 画面上の画像入力・変更時には、GCS バケット内の全画像オブジェクトを **アップロード/更新日時 (`updated`) の降順** で取得し、サムネイル一覧モーダルとして画面に表示する。
- ユーザーは一覧から画像を選択（または新規アップロード）し、該当画像の参照 URL をデータベースに保存する。

### **3.3 フロントエンド画像事前圧縮・最適化仕様**

- GCS のストレージ容量節約およびアップロード/表示時の転送速度向上のため、画像のアップロードは**フロントエンド（ブラウザ側）で事前に自動変換・圧縮**してから送信する。
- **最適化パラメータ**:
  - **解像度 (リサイズ & クロップ)**: 中央クロップ (Center Crop) により **700px × 700px 正方形** にリサイズ・加工。
  - **画質 (Quality)**: **80%** (0.8) に圧縮設定。
  - **フォーマット (Format)**: **WebP形式 (`image/webp`)** へ自動変換。
- **UI表示方針**: システム上のすべての画像表示要素（メイン外観、サブ画像、一覧サムネイル等）は、統一された **1:1 正方形 (`aspect-square object-cover`)** でレイアウト表示する。
- **実装形態**: HTML5 Canvas API (`canvas.toBlob`) を用い、外部ライブラリを追加することなくクライアントサイドで完結する軽量処理とする。

## **4. セキュリティおよび認証方針**

- **認証方式 (GCP Cloud Run IAP 認証)**:
  - ログイン認証およびアクセス制御には **GCP Cloud Run IAP (Identity-Aware Proxy)** を採用する（Profile A選定時）。
  - Cloud Run 前段で Google ログイン認証が行われ、アプリへは注入された `x-goog-authenticated-user-email` / `x-goog-iap-jwt-assertion` ヘッダー経由でユーザー識別情報を取得・検証・連携する。ローカル開発環境では自動フォールバックを行う。
- **API キー・サービスアカウント・ストレージ安全管理方針**:
  - フロントエンドコード内に GCS や GCP のクレデンシャルを一切含めず、すべて FastAPI バックエンドがプロキシ通信する。
  - ソースコードリポジトリ (Git) から `.env` や認証鍵 JSON、`app.db` を完全除外する。
- **環境変数注入**:
  - **開発環境 (ローカルDocker)**: `docker-compose.yml` で `backend/.env` から環境変数をコンテナ内へ注入する。
  - **本番環境 (Google Cloud / Cloud Run)**: GCP `Secret Manager` 上にシークレットを安全に登録し、Cloud Run のサービス起動時に動的に環境変数として注入する。

## **5. AI駆動開発（Antigravity 2.0）コントロール要件**

- **エージェント協調・オーケストレーション**:
  - 👑 コンダクターが全体統括および `PROJECT_STATE.md` を一元更新（Single Writer）。
  - 各サブエージェントは標準完了サマリをコンダクターへ返送し、コンダクターが成果物と進捗を統括する。
  - 🛡️ `qa-engineer` はコード品質レビューおよびテスト修復時にプログラムコード本体を直接書き換えず、Unified Diff提案書を作成してコンダクターに反映を委ねる（二重防御ガードレール）。
- **コンテナ再構成の徹底ルール**:
  - システムコードや設定を変更した後は、必ず `docker compose down` および `docker compose up --build -d` を実行してコンテナを再構成する。
- **自律実行の制約**: 1タスクにつき自律デバッグ試行回数は最大5回までとし、ファイル変更確定前に必ず Diff を提示する。
- **自律デバッグ & ログ照会プロトコル**:
  - HTTP 500エラー発生時、レスポンスに含まれる一意の `log_id` (UUIDv4) をキーにして標準出力の構造化JSONログを検索。
  - 動的ログ変更エンドポイント (`POST /api/internal/logger/level`) を活用し、コンテナを再起動することなく DEBUG モードへ切り替えて調査を行う。
