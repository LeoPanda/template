# **本番適用作業手順書 (PRODUCTION DEPLOYMENT GUIDE)**

- **主担当エージェント**: 👑 プロジェクトコンダクター (`conductor`)
- **副担当・セキュリティ監査**: 🛡️ 品質・テスト & QA (`qa-engineer`)
- **承認ゲート**: 👤 ユーザーによる明示的承認必須

## **1. 概要と単一統合コンテナアーキテクチャ**

本ドキュメントは、「<プロジェクト名>」を Google Cloud 上の本番環境 (Cloud Run) へ移行・適用するための、人間と AI 共同開発エージェント（Antigravity）の共同作業手順書である。

本システムは、個人利用における「極低コスト運用」と「データの高信頼な安全保管」を両立するため、**フロントエンド (React / Vite ビルド成果物)、バックエンド (FastAPI)、および SQLite 変更ログ非同期同期ツール (Litestream) を同一の Docker イメージ（単一統合コンテナ）にパッケージ化し、Cloud Run 上で単一サービスとして稼働させるアーキテクチャ**を採用する。

また、本番環境の初期構築時には、`data-backup/` 配下の既存データベース（`app.db` / `app_dump.sql`）およびマスタ登録スクリプトから初期データを全自動ロードする。

```
 [ インターネット (PC / スマホ) ]
        │ (HTTPS / GCP Cloud Run IAP (Identity-Aware Proxy) 認証)
        ▼
   [ Cloud Run (単一統合コンテナ) ]     <-- 最小インスタンス=0 / 最大インスタンス=1 (書き込み競合防止)
   │  - FastAPI (8000ポート / REST API + 静的SPA配信 `/app/static`)
   │  - React SPA (フロントエンド静的ビルド成果物)
   │  - Litestream (バックグラウンドレプリケーションプロセス)
   │    │                                     │
   │    │ (WAL 変更ログ非同期同期)            │ (画像一元管理・アップロード/参照)
   │    ▼    ▼                                     ▼
 [ Cloud Storage (Litestream用GCS) ]    [ Cloud Storage (画像用GCS) ]
   (gs://[PROJECT_ID]-<APPLICATION_ID>-litestream-        (gs://[PROJECT_ID]-<APPLICATION_ID>-images)
    backend)
```

## **2. ローカル `.env` から本番環境変数への移行チェック**

ローカル環境（`backend/.env` / `.env`）に設定されている環境変数を精査し、本番環境への適用区分（Cloud Run 環境変数 vs Secret Manager シークレット vs GCP サービスアカウント）を以下のように定義する。

| 環境変数名                           | ローカル設定値例             | 本番移行区分           | 本番適用方法 / 説明                                                                         |
| :----------------------------------- | :--------------------------- | :--------------------- | :------------------------------------------------------------------------------------------ |
| **`TZ`**                             | `Asia/Tokyo`                 | **Cloud Run 環境変数** | `TZ=Asia/Tokyo`（全コンテナ内タイムゾーン統一）                                             |
| **`LOG_LEVEL`**                      | `DEBUG`                      | **Cloud Run 環境変数** | `LOG_LEVEL=INFO`（本番ログレベル。動的変更可能）                                            |
| **`APP_VERSION`**                    | `1.0.0`                      | **Cloud Run 環境変数** | `APP_VERSION=1.0.0`（SemVer 3桁厳格管理。先頭vなし）                                        |
| **`VITE_ENABLE_MOCK`**               | `true`                       | **ビルド時環境変数**   | `VITE_ENABLE_MOCK=false`（本番モック排除二重防御 & Fail-Fast原則厳格化）                    |
| **`DATABASE_URL`**                   | `sqlite:////app/data/app.db` | **Cloud Run 環境変数** | `DATABASE_URL=sqlite:////app/data/app.db`                                                   |
| **`GCS_BUCKET_NAME_IMAGES`**         | `app-images`                 | **Cloud Run 環境変数** | `[PROJECT_ID]-<APPLICATION_ID>-images`（各種画像保存用バケット）                            |
| **`GCS_LITESTREAM_BACKUP_BUCKET`**   | `litestream-backend`         | **Cloud Run 環境変数** | `[PROJECT_ID]-<APPLICATION_ID>-litestream-backend`（Litestream同期先バケット）              |
| **`INTERNAL_AI_TOKEN`**              | `ai_agent_secret...`         | **Secret Manager**     | Secret Manager より動的注入 (`INTERNAL_AI_TOKEN`)                                           |
| **`GOOGLE_APPLICATION_CREDENTIALS`** | `/app/credentials/...`       | **Cloud Run IAM 権限** | Cloud Run サービスアカウント (ADC) に GCS アクセス権限 (`roles/storage.objectAdmin`) を付与 |

### **PHASE 3. 認証鍵・機密情報の安全な構築（ハイブリッド担当）**

`APIキー安全管理・一元化設計書.md` に基づき、ローカル `.env` で保持している機密情報を Secret Manager に登録し、Cloud Run のサービスアカウントに必要な権限を付与する。

```bash
# 1. AI駆動ロギング・自律デバッグ用内部認証トークン
echo -n "[YOUR_INTERNAL_AI_TOKEN]" | gcloud secrets create INTERNAL_AI_TOKEN --data-file=- --replication-policy="automatic"

# 2. Cloud Run デフォルトサービスアカウントへの GCS / Secret Manager 権限付与
PROJECT_NUMBER=$(gcloud projects describe [PROJECT_ID] --format='value(projectNumber)')

# GCS オブジェクト操作権限 (画像アップロードおよびLitestream同期)
gcloud projects add-iam-policy-binding [PROJECT_ID] \
    --member="serviceAccount:${PROJECT_NUMBER}-compute@developer.gserviceaccount.com" \
    --role="roles/storage.objectAdmin"

# Secret Manager アクセス権限
gcloud secrets add-iam-policy-binding INTERNAL_AI_TOKEN \
    --member="serviceAccount:${PROJECT_NUMBER}-compute@developer.gserviceaccount.com" \
    --role="roles/secretmanager.secretAccessor"
```

### **PHASE 4. フロント＆バック統合パッケージング・Litestream 設定・デプロイ（Antigravity担当）**

#### **1. Litestream 設定ファイル (`litestream.yml`)**

```yaml
dbs:
  - path: /app/data/app.db
    replicas:
      - type: gcs
        bucket: "${GCS_LITESTREAM_BACKUP_BUCKET}"
        path: db
```

#### **2. フロントエンド＋バックエンド単一統合 Dockerfile (`Dockerfile.prod`)**

フロントエンド (React / Vite) をビルドし、バックエンド (FastAPI) の `/app/static` に配置。また初期データロード用に `data-backup/` を含めて単一コンテナ化する。

```dockerfile
# --- Stage 1: Build Frontend (React / Vite SPA) ---
FROM node:20-slim AS frontend-builder
WORKDIR /app/frontend
COPY frontend/package*.json ./
RUN npm install
COPY frontend/ ./
ENV VITE_API_URL=""
RUN npm run build

# --- Stage 2: Litestream Downloader ---
FROM litestream/litestream:0.3.13 AS litestream

# --- Stage 3: Integrated Production Image (Frontend + Backend + Litestream) ---
FROM python:3.11-slim
ENV TZ=Asia/Tokyo \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential tzdata sqlite3 ca-certificates \
    && ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone \
    && rm -rf /var/lib/apt/lists/*

COPY --from=litestream /usr/local/bin/litestream /usr/local/bin/litestream

COPY backend/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY backend/ .
# フロントエンドのビルド成果物を static へコピー (FastAPIが直接配信)
COPY --from=frontend-builder /app/frontend/dist ./static
# 初回データロード用に data-backup およびサンプルデータをコピー
COPY data-backup/ ./data-backup/
COPY samples/ ./samples/
COPY scripts/ ./scripts/
COPY litestream.yml /etc/litestream.yml
COPY entrypoint.sh /app/entrypoint.sh
RUN chmod +x /app/entrypoint.sh

EXPOSE 8000
ENTRYPOINT ["/app/entrypoint.sh"]
```

#### **3. コンテナ起動エントリポイント (`entrypoint.sh`)**

GCSからのリカバリを行い、存在しない場合は `data-backup/` 配下の既存データから全自動ロードする。

```bash
#!/bin/sh
set -e

# データディレクトリの作成
mkdir -p /app/data

# GCSから既存のデータベースをリカバリ（二回目以降起動時）
litestream restore -if-replica-exists /app/data/app.db

# リカバリ後も DB ファイルが存在しない場合（初回本番デプロイ時）、data-backup 等から初期データをロード
if [ ! -f /app/data/app.db ]; then
  if [ -f /app/data-backup/app.db ]; then
    echo "Database file not found in GCS. Loading initial database from data-backup/app.db..."
    cp /app/data-backup/app.db /app/data/app.db
  elif [ -f /app/data-backup/app_dump.sql ]; then
    echo "Database file not found in GCS. Loading initial dump from data-backup/app_dump.sql..."
    sqlite3 /app/data/app.db < /app/data-backup/app_dump.sql
  elif [ -f /app/data/schema.sql ]; then
    echo "Database file not found in GCS. Initializing schema from schema.sql..."
    sqlite3 /app/data/app.db < /app/data/schema.sql
  fi
fi

# Litestreamの監視下でFastAPI(uvicorn app.main:app)を実行
exec litestream replicate -exec "uvicorn app.main:app --host 0.0.0.0 --port 8000"
```

#### **4. イメージのビルド・プッシュ・Cloud Run デプロイ**

```bash
# Docker 認証の設定
gcloud auth configure-docker asia-northeast1.pkg.dev

# ビルド
docker build -f Dockerfile.prod -t asia-northeast1.pkg.dev/[PROJECT_ID]/<APPLICATION_ID>-repo/app:latest .

# プッシュ
docker push asia-northeast1.pkg.dev/[PROJECT_ID]/<APPLICATION_ID>-repo/app:latest

# Cloud Run デプロイ (単一統合コンテナ / max-instances=1 固定)
gcloud run deploy app \
    --image=asia-northeast1.pkg.dev/[PROJECT_ID]/<APPLICATION_ID>-repo/app:latest \
    --region=asia-northeast1 \
    --platform=managed \
    --allow-unauthenticated \
    --max-instances=1 \
    --min-instances=0 \
    --set-env-vars=DATABASE_URL=sqlite:////app/data/app.db,TZ=Asia/Tokyo,LOG_LEVEL=INFO,GCS_BUCKET_NAME_IMAGES=[PROJECT_ID]-<APPLICATION_ID>-images,GCS_LITESTREAM_BACKUP_BUCKET=[PROJECT_ID]-<APPLICATION_ID>-litestream-backend \
    --set-secrets=INTERNAL_AI_TOKEN=INTERNAL_AI_TOKEN:latest
```

## **5. 運用のガバナンスとマイグレーション**

1. **`data-backup/` 初期データロード**: 初回本番コンテナ起動時、GCS 上にバックアップデータが存在しない場合は `entrypoint.sh` が `data-backup/app.db` (または `data-backup/app_dump.sql`) を全自動でロードし、既存データ・マスタ定義をすべてリストアした状態で稼働を開始する。
2. **リアルタイム同期とレプリケーション**: リストア完了後、すべての書き込み変更（データの登録・更新、アクティビティ記録追加・削除、画像コメント変更等）は、Litestream により WAL 変更ログとして GCS バケット (`gs://[PROJECT_ID]-litestream-backend`) へリアルタイム非同期同期される。次回起動時は GCS から自動復元されるため、データ損失が発生しない。
3. **複数インスタンス書き込み衝突の防止 (`max-instances=1`)**: SQLite + Litestream アーキテクチャの整合性を維持するため、Cloud Run のスケール設定で最大インスタンス数を `max-instances=1` に厳格制限する。
4. **GCS 画像一元管理**: 各種外観写真や撮影写真は、すべてクライアント（ブラウザ）側で 700x700px 正方形 WebP 形式に自動圧縮された上で GCS バケット (`gs://[PROJECT_ID]-app-images`) に保存される。
5. **GCP Cloud Run IAP 設定**: 本番環境デプロイ後、GCP コンソールにて Cloud Run サービスに対する Identity-Aware Proxy (IAP) を有効化し、アクセス権限（IAP-secured Web App User）を構成することで、本番環境での安全な Google 認証・アクセス制御が機能する。
6. **AI駆動ロギングと動的ログレベル調整**: 本番環境で障害発生時やデバッグ時は、`POST /api/internal/logger/level` に対し `INTERNAL_AI_TOKEN` を付与してリクエストを送信することで、コンテナを再起動することなくリアルタイムにログレベルを `DEBUG` へ変更し調査可能である。
