# AI駆動システム開発フェーズ定義書 V2（サブエージェント協調・状態一元管理・システム改訂統合版）

## 1. 目的と位置付け

本文書は、Antigravity環境におけるAI駆動システム開発ライフサイクル（新規開発 PHASE 1〜8、および本番リリース後の継続的システム改訂プロセス）において、**メインエージェント（コンダクター）、3つの専門サブエージェント、決定論的スキル群、およびユーザー（開発者/PO）** が協調して開発・改訂を完遂するためのフェーズ定義と役割分担を規定するものである。

本ドキュメントは、「検討課題2: プロジェクト状態（State）の一元管理機構（`PROJECT_STATE.md`）」の設計仕様および運用基盤となるものであり、各フェーズ・各改訂ターンの実行主体、入出力、完了判定条件（明示的承認ゲート）、およびプロジェクト状態への反映ルールを網羅する。

## 2. 採用された基本方針（ユーザー決定事項）

| 検討項目 | 採択方針 | 詳細内容 |
| :--- | :--- | :--- |
| **1. フェーズ移行ゲート** | **明示的承認ゲート方式** | 各重要フェーズ（PHASE 2, 3, 6, 7等）および改訂ターンの完了時、判定条件を満たした上で必ずユーザーに確認を求め、ユーザーの明示的な「承認」プロンプトを受けて次フェーズ・次工程へ移行する。 |
| **2. BE実装担当スコープ** | **コンダクター直轄** | PHASE 4の開発において、👑 コンダクターが開発環境構築（Docker）およびバックエンド実装（API・ロジック）を統括・直接実行し、🎨 `ui-designer` にフロントエンド画面実装を委譲する。 |
| **3. 状態管理ファイル形式** | **Markdown形式 (`PROJECT_STATE.md`)** | 人間がVSCode等で直感的に確認・編集しやすいMarkdown形式を採用。チェックリスト（`- [x]`, `- [ ]`）や未決事項（Open Questions）、改訂履歴を管理する。 |
| **4. 状態ファイルの更新責任** | **👑 コンダクター一元管理** | 状態管理ファイルへの書き込みはコンダクターのみが集中実行（Single Writer）。サブエージェントは親へ標準完了サマリを返すのみとし、ファイルの競合や破損を防止する。 |
| **5. テンプレート反映** | **全検討課題完了後一括反映** | 本検討課題（課題1〜4）の設計・レビューが完全に完了した段階で、`.agents/plugins/system-dev-pipeline/`（`templates/`, `agents/`, `skills/`）を一括更新する。 |

## 3. エージェントおよびユーザーの役割体系

開発パイプラインおよびシステム改訂プロセスは、以下の5つのアクター（人間1名＋エージェント4名）と決定論的スキル群によって運用される。

```
                    ┌────────────────────────────────────────┐
                    │               👤 ユーザー              │
                    │      (要件提示 / ゲート承認 / 操作検証) │
                    └──────────────────┬─────────────────────┘
                                       │ 対話 / 指示 / 明示的承認
                                       ▼
                    ┌────────────────────────────────────────┐
                    │ 👑 1. プロジェクトコンダクター (Main)    │
                    │      (全体進行 / BE統括 / 状態一元管理) │
                    └──────────────────┬─────────────────────┘
                                       │ 委譲 (invoke_subagent)
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
┌──────────────────────────┐  ┌──────────────────────────┐  ┌──────────────────────────┐
│ 📐 2. 設計・立案          │  │ 🎨 3. UI/UX              │  │ 🛡️ 4. 品質・テスト       │
│    スペシャリスト        │  │    デザイナー / FE       │  │    & QA (監査・検証)     │
│ (architect)              │  │ (ui-designer)            │  │ (qa-engineer)            │
│ [Model: pro]             │  │ [Model: flash / pro]     │  │ [Model: pro]             │
└────────────┬─────────────┘  └────────────┬─────────────┘  └────────────┬─────────────┘
             │                             │                             │
             └─────────────────────────────┼─────────────────────────────┘
                                           ▼ 成果物反映
                               ┌──────────────────────────┐
                               │ ⚙️ 決定論的ツール / スキル │
                               │ ・Git管理 (dev-git-*)    │
                               │ ・デプロイ管理 (Cloud Run)│
                               │ ・DB反映 (dev-db-overwrite)│
                               └──────────────────────────┘
```

### 3.1 アクター詳細

1. **👤 ユーザー (`user` / 人間)**:
   - システム要求の提示、設計・仕様のレビュー承認、ウォークスルーでのUI操作検証、本番リリースの最終判断、改訂依頼の発行。
2. **👑 プロジェクトコンダクター (`conductor` / メインエージェント / Model: `pro`)**:
   - ユーザーとの直接対話窓口。全体進捗管理、`PROJECT_STATE.md` の一元更新（Single Writer）、サブエージェントへのタスク委譲、Docker環境構築およびBE実装統括、Git/デプロイスキルの呼び出し。
3. **📐 設計・立案スペシャリスト (`architect` / サブエージェント / Model: `pro`)**:
   - 要件定義書、基本設計書3種（技術要件・テーブルスキーマ・ビジネスロジック）、API仕様書の同期、改訂時の影響範囲調査およびImplementation Plan策定。
4. **🎨 UI/UXデザイナー (`ui-designer` / サブエージェント / Model: `flash` または `pro`)**:
   - `画面仕様書.md` の作成、フロントエンド画面実装（HTML/CSS/コンポーネント）、UI微修正に伴う試行錯誤トークンの隔離。
5. **🛡️ 品質・テスト & QA (`qa-engineer` / サブエージェント / Model: `pro`)**:
   - `dev-doc-reviewer` を用いた多次元ドキュメント整合性チェック・自律修復、シナリオテスト計画策定、自動テスト実行・ログ解析・修復ループ、改訂時のテスト結果レポート作成。※プログラムコード自体の勝手な修正は行わずコンダクターへ報告する。
6. **⚙️ 決定論的スキル (`system-dev-pipeline`)**:
   - `dev-phase1-setup` 〜 `dev-phase8-rules`, `dev-git-init`, `dev-git-release`, `dev-db-overwrite`, `dev-doc-reviewer` 等の手続き的処理。

## 4. 新規開発フェーズ定義（PHASE 1 〜 PHASE 8）

新規プロジェクト立上げから初回本番リリースまでの8フェーズを定義する。

### 4.1 PHASE 1: プロジェクトの準備
- **目的**: ディレクトリ構成、`.env`、各種ドキュメント雛形の自動展開および状態管理の初期化。
- **主担当**: 👑 コンダクター（ツール: `dev-phase1-setup`）
- **ユーザーの役割**: プロジェクト名決定、初期プロンプト投入、IDE GUI権限設定の確認。
- **完了判定条件（ゲート）**:
  - [x] ディレクトリ構造（`docs/`, `.env`, `rules/`）が正常配置されていること。
  - [x] 👑 コンダクターにより `PROJECT_STATE.md` が初期化（Status: `PHASE_1_COMPLETED`）されていること。
  - [x] ユーザーへの準備完了案内が完了していること。

### 4.2 PHASE 2: 要件定義
- **目的**: ユーザー要求を精査し、`docs/要件定義書.md` を作成・構造化・確定する。
- **主担当**: 📐 `architect`（委譲元: 👑 コンダクター）
- **ユーザーの役割**: システム要求・背景のドラフト記入、Open Questionsへの回答、確定版の承認。
- **完了判定条件（明示的承認ゲート）**:
  - [x] `docs/要件定義書.md` に機能・非機能・ユースケースが網羅されていること。
  - [x] 未決事項（Open Questions）がすべて解決済みであること。
  - [x] **【ゲート】ユーザーによる「要件定義完了」の明示的承認プロンプトを受領していること。**

### 4.3 PHASE 3: 基本設計書の作成と整合性チェック
- **目的**: 基本設計書4種（技術・スキーマ・ロジック・画面）を作成し、相互矛盾をゼロにする。
- **主担当**:
  - 技術 / スキーマ / ロジック: 📐 `architect`（ツール: `dev-phase3-design` ※3文書生成に特化）
  - 画面仕様: 🎨 `ui-designer`（👑 コンダクターより独立委譲）
  - 相互監査・自動修復: 🛡️ `qa-engineer`（ツール: `dev-doc-reviewer`）
- **ユーザーの役割**: 主要な設計判断（技術選定・DB構造）の確認と承認。
- **完了判定条件（明示的承認ゲート）**:
  - [x] 4大設計書が作成され、要件定義書を満たしていること。
  - [x] 🛡️ `qa-engineer` によるドキュメント相互整合性チェックのエラーが0件であること。
  - [x] **【ゲート】ユーザーによる「基本設計完了」の明示的承認プロンプトを受領していること。**

### 4.4 PHASE 4: 開発環境とシステム構築
- **目的**: ローカル開発環境（Docker）の構築、BE/FEソースコード実装、Gitリポジトリ初期化。
- **主担当**:
  - 環境構築・Docker・BE実装: 👑 コンダクター（直轄）
  - FE画面実装: 🎨 `ui-designer`
  - Git初期化: ⚙️ `dev-git-init`
- **ユーザーの役割**: Dockerデスクトップ起動確認、初期起動確認。
- **完了判定条件（ゲート）**:
  - [x] `docker compose up` によりコンテナ群が正常起動すること。
  - [x] 初期画面およびAPIが疎通可能であること。
  - [x] Git管理が初期化され、`main` 初回コミットおよび `feature` 作業ブランチが作成されていること。

> [!IMPORTANT]
> **【徹底ルール】PHASE 4以降のシステム修正後のDockerコンテナ再構成**  
> 本フェーズ以降、プログラムコードや設定ファイルを修正した後は、変更を確実にコンポーネントに反映するため、**必ず `docker compose down` および `docker compose up --build -d` を実行してコンテナをビルド・再構成する**。

### 4.5 PHASE 5: ウォークスルー動作確認とデバッグ
- **目的**: 実際の画面操作による動作確認、不具合修正、および設計書への逆同期。
- **主担当**:
  - 操作検証: 👤 ユーザー
  - デバッグ修正統括・BE修正: 👑 コンダクター
  - UI微調整: 🎨 `ui-designer`
  - API仕様同期: 📐 `architect`
  - ドキュメント整合性確認: 🛡️ `qa-engineer`
- **完了判定条件（明示的承認ゲート）**:
  - [x] ユーザーによるウォークスルーが完了し、指摘不具合が改修されていること。
  - [x] 最新コードに基づきAPI仕様書および設計書が更新されていること。
  - [x] 修正後のコンテナ再構成（`docker compose down` → `up --build -d`）が完了していること。
  - [x] **【ゲート】ユーザーによる「ウォークスルー完了」の明示的承認を受領していること。**

### 4.6 PHASE 6: スルーテスト環境の構築と実施
- **目的**: 自動テストコードを構築し、全テストケースがPASSするまで自律修復ループを実行する。
- **主担当**: 🛡️ `qa-engineer`（ツール: `dev-phase6-testing`）
- **ユーザーの役割**: シナリオテスト計画書の承認、根本欠陥発生時の修正方針指示。
- **完了判定条件（明示的承認ゲート）**:
  - [x] `docs/plans/シナリオテスト計画書.md` の全テストがPASS（成功率100%）していること。
  - [x] テスト実行ログが保存されていること。
  - [x] プログラム起因の未解決エラーが0件であること。
  - [x] **【ゲート】ユーザーによる「テスト完了・リリース準備移行」の明示的承認を受領していること。**

### 4.7 PHASE 7: 本番リリース
- **目的**: 本番適用作業手順書を作成し、本番環境（Cloud Run等）へ初回デプロイ、IAM/IAPセキュリティ検証を実施。
- **主担当**: 👑 コンダクター（ツール: `dev-phase7-release`）、最終監査: 🛡️ `qa-engineer`
- **ユーザーの役割**: 本番手順書の承認、GCPセキュリティ設定の確認、本番初期アクセステスト。
- **完了判定条件（明示的承認ゲート）**:
  - [x] 本番デプロイが正常完了していること。
  - [x] IAM/IAPのアクセス制御（AllUsers権限削除等）が検証されていること。
  - [x] **【ゲート】ユーザーによる「本番稼働確認完了」の明示的承認を受領していること。**

### 4.8 PHASE 8: ドキュメント改訂管理の開始（保守運用移行）
- **目的**: 初回リリースのGitHub本番反映（Squash Merge）、改訂運用規約ファイル群の適用、知見昇格レビュー、状態管理を保守モードへ移行。
- **主担当**: 👑 コンダクター（ツール: `dev-git-release`, `dev-phase8-rules`）
- **完了判定条件（ゲート）**:
  - [x] **【ゲート】ユーザーによる知見昇格レビュー（`./TEMPLATE_PROMOTIONS.md` の Tier 2 知見のテンプレート昇格判定）が完了・承認されていること。**
  - [x] `dev-git-release` により `feature` が `main` へ Squash Merge され、`Release v1.0.0` のタグ付きPushが完了していること。
  - [x] 新たな `feature` ブランチが切り直されていること。
  - [x] `rules/システム改訂ルール.md`, `AGENTS.md`, `GEMINI.md`, `.agents/rules/system-revision.md` が配置されていること。
  - [x] `PROJECT_STATE.md` が「本番稼働中 / 保守・改訂運用モード（Production / Maintenance）」へ更新されていること。

### 5.1 改訂ライフサイクルの詳細ステップ

#### ステップ 1: 改訂依頼開始と番号採番
1. ユーザーが改訂プロンプトを入力し、改訂作業の開始を宣言する（例: 「バージョン1.1の改訂を開始します。〜〜の機能を追加してください」）。
2. バージョン番号が明示された場合は `.env` の `APP_VERSION` を更新。明示されない場合は現行バージョンを維持。
3. 👑 コンダクターが改訂ターン番号（`xxx`: 001, 002...）および**改訂依頼番号（`n.m.xxx`）**を自動採番し、`PROJECT_STATE.md` に記録。

#### ステップ 2: 改訂ターンの実施（Revision Turn）
改訂作業は「1ターン」単位で進行し、必要に応じて複数ターン繰り返される。
1. **Implementation Planの作成**: 👑 コンダクター（または 📐 `architect`）が影響範囲を調査し、変更プランを作成。
2. **Planのレビューと承認**: 👤 ユーザーがPlanを確認し、承認を与える（明示的承認ゲート）。
3. **改訂実行**:
   - バックエンド/環境設定: 👑 コンダクターが修正。
   - 画面/UIコンポーネント: 🎨 `ui-designer` が修正。
   - 設計ドキュメント: 📐 `architect` または 👑 コンダクターが修正。
   - **【重要】コード修正後、必ず `docker compose down` → `docker compose up --build -d` を実行してコンテナを再構成・動作確認する。**
4. **改訂履歴の追記（全ドキュメント共通ルール）**:
   - 変更が加わったドキュメントの末尾に、必ず以下の表形式で改定履歴を追記する。
     ```markdown
     | バージョン | 改定日 | 改訂依頼番号 | 改定内容 |
     | :--- | :--- | :--- | :--- |
     | 1.1.0 | 2026-10-02 | 1.1.001 | ユーザー一覧画面にCSVエクスポート機能を追加 |
     ```
5. **改訂ターンの文書化**:
   - ディレクトリ `/revise-log/Vn.m/` 配下に `Vn.m_revise-review_xxx.md` を作成。
   - 記録項目: ①改訂依頼番号 (`n.m.xxx`), ②依頼日, ③依頼内容, ④変更プランの概要。
6. 次の改訂要望があればターン番号をインクリメント（`xxx + 1`）して繰り返す。

#### ステップ 3: 改訂ターンの完了宣言とシナリオテスト
1. ユーザーが改訂ターンの完了を宣言。
2. 👑 コンダクターが 🛡️ `qa-engineer` にシナリオテストの実行を委譲。
3. 🛡️ `qa-engineer` がスルーテストを実行し、`/tests/Vn.mシナリオテスト結果レポート.md` を作成（同一バージョン内は上書き・更新）。
   - ※軽微な修正でテストを実施しない場合は、その旨を記録。
4. 全テストPASSを確認後、ユーザーが本番デプロイを承認（明示的承認ゲート）。

#### ステップ 4: 本番デプロイ
1. **通常デプロイ**: 👑 コンダクターが本番環境へコンテナをデプロイ。
2. **テーブルスキーマ変更を伴う場合**:
   - データの保全を行うため、`dev-db-overwrite` スキルの規約に従う。
   - 本番DBバックアップ → 開発環境へ適用 → 改修・マイグレーション確認 → `dev-db-overwrite` によりDBを含むコンテナを本番環境へデプロイ。

#### ステップ 5: 改訂作業完了レポートの作成とクリーンアップ
1. 👑 コンダクターが `docs/` 配下に `docs/Vn.m改訂レポート.md` を作成（または同一バージョン内に追記）。
2. レポートへの転記構成:
   - `/revise-log/Vn.m/` 配下の `Vn.m_revise-review_xxx.md` の内容を転記。
   - `/tests/Vn.mシナリオテスト結果レポート.md` からテストサマリーを転記。
   - 本番適用結果を `{サービス名, リージョン, 最新リビジョン, 本番URL}` の形式で記載。
3. レポート作成完了後、一時ファイルである `/revise-log/Vn.m/` 配下の `Vn.m_revise-review_xxx.md` を削除。

#### ステップ 6: テンプレート知見昇格レビュー（知見昇格レビューゲート）
1. 👑 コンダクターが `./TEMPLATE_PROMOTIONS.md`（テンプレート昇格候補ログ）を集約し、ユーザーへ Artifacts で昇格レビューを提案。
2. 👤 ユーザーが内容をレビューし、テンプレート（`.agents/plugins/system-dev-pipeline/`）への昇格を承認（明示的承認ゲート）。
3. 承認された知見はプラグイン側の `rules/`, `agents/`, `templates/` へ反映される。

#### ステップ 7: GitHub本番公開とブランチ刷新
1. 👑 コンダクターが `dev-git-release` スキルを実行。
2. `feature` ブランチの全変更を `main` へ Squash Merge し、バージョン番号を含むコミットメッセージ（`Release v${APP_VERSION}`）で commit & push を実行。
3. 旧 `feature` ブランチを破棄し、最新の `main` から次期改訂用の新規 `feature` ブランチを自動作成。
4. 👑 コンダクターが `PROJECT_STATE.md` を更新し、改訂完了を記録。

## 6. フェーズ & 改訂プロセス別 役割分担マトリクス (RACI)

| フェーズ / プロセス | 👤 ユーザー | 👑 コンダクター | 📐 設計 (architect) | 🎨 UI (ui-designer) | 🛡️ QA (qa-engineer) | ⚙️ スキル / ツール |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **PHASE 1: 準備** | **A** | **R** | I | I | I | R (`dev-phase1-setup`) |
| **PHASE 2: 要件定義** | **A (承認)** | C | **R** | C | C | - |
| **PHASE 3: 基本設計** | **A (承認)** | C | **R** (3文書) | **R** (画面) | **R** (監査・修復) | R (`dev-phase3-design`, `dev-doc-reviewer`) |
| **PHASE 4: 環境・実装** | **A** | **R** (BE/環境) | C | **R** (FE実装) | - | R (`dev-git-init`, `docker compose`) |
| **PHASE 5: ウォークスルー** | **A / R (操作)** | **R** (統括/修正) | R (API同期) | R (画面修正) | R (監査) | R (`dev-phase5-walkthrough`) |
| **PHASE 6: スルーテスト** | **A (承認)** | C | - | - | **R** (テスト・修復) | R (`dev-phase6-testing`) |
| **PHASE 7: 本番リリース** | **A (承認)** | **R** (手順・実行) | - | - | R (最終監査) | R (`dev-phase7-release`) |
| **PHASE 8: 改訂管理開始**| **A** | **R** | I | I | I | R (`dev-phase8-rules`, `dev-git-release`) |
| **REV: 改訂Plan・承認** | **A (承認)** | **R** | R (設計調査) | C | - | - |
| **REV: 改訂実装・履歴追記** | - | **R** (BE/環境) | R (ドキュメント) | **R** (FE) | - | `docker compose` 再構成 |
| **REV: 改訂ターン文書化** | I | **R** (ログ生成) | - | - | - | `/revise-log/` 生成 |
| **REV: シナリオテスト** | **A (承認)** | C | - | - | **R** (テスト実行) | `Vn.mシナリオテスト結果レポート.md` |
| **REV: 本番デプロイ** | **A (承認)** | **R** (デプロイ) | - | - | - | `dev-db-overwrite` (DB変更時) |
| **REV: 完了レポート作成** | I | **R** (レポート集約) | - | - | - | - |
| **REV: 知見昇格レビュー** | **A (承認)** | **R** (集約・提案) | - | - | - | `./TEMPLATE_PROMOTIONS.md` |
| **REV: Git公開・ブランチ刷新** | I | **R** (リリース実行) | - | - | - | `dev-git-release` |

- **R (Responsible)**: 実際の作業を担当・実行する。
- **A (Accountable)**: 成果物の最終承認・意思決定責任を持つ（主にユーザー）。
- **C (Consulted)**: 助言・協調して情報提供を行う。
- **I (Informed)**: 完了報告や状態更新を受け取る。

## 7. プロジェクト状態の一元管理機構（`PROJECT_STATE.md`）連携仕様

### 7.1 基本原則
1. **Single Writer 原則**:
   - `PROJECT_STATE.md` への書き込み・更新権限は **👑 プロジェクトコンダクターのみ** が保持する。
   - サブエージェントは親へ標準完了サマリを返すのみとし、状態ファイルを直接編集しない。
2. **明示的承認ゲートの記録**:
   - ユーザーが承認を与えた日時、コミット、承認ステータスを状態ファイルに明記する。
3. **改訂プロセスのステータス管理**:
   - 本番稼働後は、現在進行中の改訂ターン番号、改訂依頼番号（`n.m.xxx`）、テスト結果、未解決課題がリアルタイムに更新される。
