# システム改訂ルール

最初のDockerコンテナの本番環境デプロイ（PHASE 8完了）に伴い、今後のシステム改訂および運用に関わる手続きとルールを以下の通り定める。

---

## 1. システムのバージョン管理について

- **バージョン管理場所**: `.env` ファイル内に環境変数 `APP_VERSION` を設定し、システム全体のバージョンを統一管理する。フォーマットは公式セマンティックバージョニング（SemVer 2.0.0: `MAJOR.MINOR.PATCH`、数値3桁、先頭に `v` は付けない。例: `1.0.0`）を厳格に遵守する。
- **プロジェクト状態管理 (`PROJECT_STATE.md`)**:
  - プロジェクトルート直下の `PROJECT_STATE.md` において、現行バージョン（`vMAJOR.MINOR.PATCH`、小文字 `v` ＋ 3桁、例: `v1.0.0`）、改訂ステータス（IDLE / PLANNING / EXECUTING / TESTING / DEPLOYED）、改訂依頼番号、ターン番号、直近改訂レポートを一元追跡する。
  - `PROJECT_STATE.md` への書き込み権限は **👑 プロジェクトコンダクター専任 (Single Writer)** とする。
- **バージョンの変更**:
  - バージョン番号の変更は、プロンプト（ユーザー）からの明示的な指定か、環境変数を手動で更新することで行う。
  - 指定を受けた場合は、環境変数 `APP_VERSION` を更新する。
  - 環境変数 `APP_VERSION` を更新した場合は、フロントエンドの画面上に表示されるバージョン番号も自動的に連動して変更される。

---

## 2. システム改訂のプロセス

システムの改訂作業は、以下のプロセスに従って行うものとする。

### 2.1. 改訂作業プロセスの定義

- システムの改訂プロセスは以下の流れで進行するものとする。
  1. 改訂依頼開始の宣言（👑 コンダクターが改訂依頼番号 `MAJOR.MINOR.xxx` を採番し `PROJECT_STATE.md` を更新）
  2. 改訂ターンの実施（詳細は後述。💻 BE / 🎨 UI 改訂実行 ＋ 🛡️ コード品質レビュー `dev-review-code` 組み込み）
  3. 改訂ターンの完了宣言（ユーザー）
  4. シナリオテストの実施と完了（🛡️ `qa-engineer`。不具合・トラップ時は `wiki-maintainer` によるRCA即時記録）
  5. システム総合レビューの実施（🛡️ `qa-engineer` が `dev-review-system` を実行し `RELEASE APPROVED` 判定を確認）
  6. 改定内容の本番デプロイ（👑 コンダクター専任実行）
  7. 改定作業完了レポートの作成（`docs/vn.m改訂レポート.md`）
  8. 知見昇格レビューと承認（`./TEMPLATE_PROMOTIONS.md` の確認・ユーザー明示的承認）
  9. WikiSkill型自己進化サイクルの実行（👑 `wiki-proposer` 提案 ──► 🛡️ 複合検証ゲート Gating ──► 👑 `wiki-compactor` 統合、`EXECUTION_MODE` に応じたルーティング）
  10. 定量メトリクス集計（👑 コンダクターによる `dev-metrics-collector` 実行）
  11. GitHubへの本番公開と開発ブランチ刷新（`dev-git-release` スキルの発動）
  12. 改定作業の完了（`PROJECT_STATE.md` を `IDLE` / `PRODUCTION_ACTIVE` へ更新）

### 2.2. ユーザーの変更要求の起点

- ユーザーの変更要求は、プロンプト（ユーザー）からの明示的な指定によって行うものとする。
- 変更要求を行う場合は、改訂作業プロセスの開始を宣言し、システムに改訂を要求する。
- ユーザーが改訂要求を行う際に、システムのバージョンを明示する。明示されない場合は現行バージョンでの改訂とみなし、改訂ターン番号を自動採番して、改訂作業プロセスを開始する。

### 2.3. 改訂ターンの定義

- ユーザーの変更要求を受け、システムの改訂作業プロセスを開始する単位を **1改訂ターン** とする。
- 改訂ターンは完了宣言を行うまで繰り返し実施されることがある。
- 改訂ターンが繰り返されるたびに改訂ターン番号（xxx）を1つずつ増やす。

#### 2.3.1. 改訂ターンのプロセス定義

- 改訂ターンのプロセスは以下の流れで進行し、これを **1ターン** として定義する。
  1. 改定内容のプロンプト入力。改訂依頼の開始宣言と共に入力されることもある。（ユーザー）
  2. Implementation Planの作成（👑 コンダクター / 📐 `architect`）
  3. Planのレビュー（ユーザー）
  4. Planの改訂（AI）
  5. 承認（ユーザー）
  6. 改訂実行（💻 `backend-engineer` BE実装 / 🎨 `ui-designer` FE実装 / 👑 コンダクター統括）
  7. コード品質レビュー & Diff適用（🛡️ `qa-engineer` が `dev-review-code` により差分を監査し、DRY/不要コード排除/行数制限遵守を確認。コンダクターがDiff適用）
  8. コンテナ再構成の徹底（コード修正後は必ず `docker compose down` および `docker compose up --build -d` を実行）
  9. 手戻り・エラー発生時のRCA即時記録（不具合発生時は 🛡️ `qa-engineer` が `wiki-maintainer` により `./wiki/patterns/` へ即時記録）
  10. 文書化および履歴追記（`/revise-log/` 配下に記録）

#### 2.3.2. 改訂ターンの文書化

- 各改訂ターンの内容は、改訂実行およびコード品質レビューが完了した時点で以下の形式で文書化する。
- ディレクトリ: `/revise-log/vn.m/`（※大文字 `V` は廃止し小文字 `v` 統一）
- 文書名: `vn.m_revise-review_xxx.md`
- `xxx`: ターン番号（連番、例: 001, 002...）
- **改訂依頼番号の採番**:
  - 1ターンごとに改訂依頼番号を自動採番する。
  - 番号フォーマット: `MAJOR.MINOR.xxx`
    - `MAJOR.MINOR`: システムのメジャー・マイナーバージョン番号（例: `1.0`, `2.0`）
    - `xxx`: 通し番号（連番3桁、例: 001, 002...）
    - 例: `1.0.001`, `1.0.002`, `2.0.001`
- **記録項目**:
  revise-reviewには以下の情報を整理して記録する。
  1. 改訂依頼番号 (`MAJOR.MINOR.xxx`)
  2. 依頼日
  3. 依頼内容
  4. 変更プランの概要
  5. コード品質レビュー結果（判定: CLEAN / 指摘事項）

#### 2.3.3. 改定履歴の記載（全ドキュメント共通）

- 改訂実行時には、システムの改訂とともに関連設計書・仕様書の改訂も行うものとする。
- この際、以下の形式で改定履歴を記載する。
- 文書の末尾に必ず**改定履歴を表形式**で記載する。
- **適用除外**: `PROJECT_STATE.md` はプロジェクトの現在状態を示すインジケータであり、本改定履歴表の記載対象外とする（改訂履歴は `/revise-log/` および改訂レポートで一元管理）。
- 改定履歴の記載項目は以下の通りとする。

| バージョン | 改定日 | 改訂依頼番号 | 改定内容 |
| :--- | :--- | :--- | :--- |
| （システムのバージョン: 例: 1.0.0） | （YY-MM-DD） | （MAJOR.MINOR.xxx） | （変更内容の簡潔な説明） |

---

### 2.4. シナリオテスト結果レポートについて

- **作成場所・ファイル名**:
  - `docs/plans/scenario-test/`（または `/tests`）配下に `vn.mシナリオテスト結果レポート.md` の形式で作成する（小文字 `v` 統一）。
- **同一バージョン内での更新**:
  - システムのバージョンが同一の間は、同じファイルに結果レポートを上書き・更新する。
- **作成の義務化**:
  - シナリオテストが実施される際には、必ず本レポート文書を作成・更新するものとする。
- **エラー発生時の Wiki RCA 記録**:
  - テスト失敗や環境トラップが発生した場合は、🛡️ `qa-engineer` が `wiki-maintainer` を用いて `./wiki/patterns/` へ即時記録する。

---

### 2.5. 改訂作業完了レポートの作成

改定内容が本番デプロイされた後、改訂作業の最終完了として、作業レポートの文書化を行う。

- **記録場所とファイル名**:
  - システムのバージョンが変わるまでは、同一の文書（`docs/vn.m改訂レポート.md`）内に改訂依頼を追記・記録する（小文字 `v` 統一）。
- **記録内容と操作**:
  - レポートの内容は、`/revise-log/vn.m/` 配下の `vn.m_revise-review_xxx.md` を転記する形で行う。
  - `vn.m_revise-review_xxx.md` が複数ある場合、または同一バージョンの改訂依頼の場合はレポートに追記する形で行う。
  - `revise-review` の後に `vn.mシナリオテスト結果レポート.md` からテストの実施サマリーを転記する。
  - 軽微な修正の場合はシナリオテストが実施されない場合もある。このときはシナリオテストのサマリーは記載せず、シナリオテストの実施は行わなかった旨を記載する。
  - シナリオテストのサマリーの後に、本番適用結果を記載する。記載内容は `{サービス名, リージョン, 最新リビジョン, 本番URL}` の形式とする。
  - 定量メトリクス集計結果（`dev-metrics-collector` により更新された `docs/plans/metrics/development-metrics-summary.json`）をサマリに反映する。
  - レポートの作成が終わったら、`/revise-log/vn.m/` 配下の `vn.m_revise-review_xxx.md` を削除する。

## 3. GitおよびGitHubブランチ運用ルール

システムの改訂および本番公開時のGit運用は、[Git運用基準書](../docs/Git運用基準書.md) に準拠し、以下の通り行う。

- **作業ブランチ**: 改訂作業はすべて `feature` ブランチ上で行う。本番ブランチ `main` への直接コミット・編集は禁止する。
- **コミットのタイミング**: 開発中のコミットは随時行ってよい。
- **本番反映（Squash Merge）**:
  - 本番デプロイおよび改訂レポート作成完了後、`dev-git-release` スキルを発動する。
  - `feature` ブランチの全変更を `main` へ squash merge し、コミットメッセージにバージョン番号（`Release v${APP_VERSION}`）を明記して commit & push（SSH経由）を実行する。
- **ブランチの刷新**:
  - 本番 push 完了後、旧 `feature` ブランチは自動破棄され、最新の `main` から新たな `feature` ブランチが切り直される。
  - 次の改訂作業は、必ずこの新しく生成された `feature` ブランチ上で行う。
