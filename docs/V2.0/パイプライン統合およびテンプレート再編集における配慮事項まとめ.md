# パイプライン統合およびテンプレート再編集における配慮事項まとめ

本ドキュメントは、[サブエージェント活用の検討課題.md](template/docs/検討課題/V2.0/サブエージェント活用の検討課題.md)におけるすべての課題（課題1〜4）の検討完了後、既存の開発パイプライン（`.agents/plugins/system-dev-pipeline/`）およびプロジェクトテンプレート一式を統合・再編集する際に考慮・徹底すべき事柄を体系的にまとめた技術仕様書・作業指針である。

## 1. 目的と位置付け

これまでの検討により、以下の3つの基盤設計が確定している。
1. **[エージェント設計書.md](template/docs/V2.0/エージェント設計書.md)**: 4つの役割（`conductor`, `architect`, `ui-designer`, `qa-engineer`）の責務・権限・入出力形式。
2. **[AI駆動システム開発フェーズ定義書V2.md](template/docs/V2.0/AI駆動システム開発フェーズ定義書V2.md)**: PHASE 1〜8 および本番改訂における各エージェントの作業スコープ、明示的承認ゲート。
3. **[状態管理機構設計書.md](template/docs/V2.0/状態管理機構設計書.md)**: プロジェクトルート直下 `PROJECT_STATE.md` のSingle Writer（コンダクター専任）による進行管理。

これらを実際のプラグイン構成ファイル群（`skills/`, `templates/`, `rules/`, `plugin.json`）に反映・再編集する際には、単なるファイルの追加にとどまらず、**「実行主体の整合性」「権限分離と安全対策」「ランタイム起動互換性」「既存資産からの移行性」** など、多角的な整合性を確保する必要がある。

### 配慮事項 1: 既存スキルの実行主体（Who）とプロンプトフローの整合性再定義

#### 背景と課題
従来の各スキル（`dev-phase1-setup` 〜 `dev-phase8-rules`）は、**「メインエージェントがユーザーと直接対話し、単独でタスクを完結させる」** 前提で記述されている。
サブエージェント体制においては、スキルの実行主体がサブエージェント（例: `dev-phase2-requirements` は `architect`、`dev-phase6-testing` は `qa-engineer`）へ移行するため、スキルの指示文とエージェントの動作に乖離が生じる。

#### 配慮・対応方針
- **各 `SKILL.md` のメタデータと手順書の改訂**:
  - 各スキルの冒頭に「**主担当エージェント**」を明記する。
  - スキル完了時の出力先について、「ユーザー向けArtifacts出力」と記述されていた箇所を、**「呼び出し元エージェント（コンダクター）に対する標準完了サマリの返却」** へ改訂する。
- **コンダクター専用スキルと委譲スキルの分類**:
  - `dev-phase1-setup`, `dev-phase4-env-build`（環境・BE統括）, `dev-phase5-walkthrough`（対話ウォークスルー・修正統括 ※API仕様同期は `architect` と連携）, `dev-phase7-release`, `dev-phase8-rules`, `dev-git-*`, `dev-db-overwrite`: **コンダクター主担当手順**として整理。
  - `dev-phase2-requirements`, `dev-phase3-design`（※技術・スキーマ・ロジックの3文書生成に特化。画面仕様書はコンダクターより `ui-designer` へ独立委譲）: **`architect` 主担当手順**として整理。
  - `dev-phase6-testing`, `dev-doc-reviewer`: **`qa-engineer` 主担当手順**として整理。

### 配慮事項 2: プラグイン仕様に基づくエージェント定義と動的ロード保証

#### 背景と課題
`.agents/plugins/system-dev-pipeline/` に `agents/` ディレクトリを新設し、`plugin.json` にエージェント名を登録した際、Antigravity の実行環境やセッション状態によってはサブエージェントが自動的に利用可能（Available Subagents）として認識されない、あるいは定義内容の更新が反映されないリスクがある。

#### 配慮・対応方針
- **二重担保（プラグイン登録 ＋ 動的登録フォールバック）の組み込み**:
  1. `plugin.json` への `"agents": ["architect", "ui-designer", "qa-engineer"]` の正規記述。
  2. メインエージェント（コンダクター）の初期動作ルールに、**「セッション開始時または委譲時に、該当サブエージェントが未定義の場合は `.agents/plugins/system-dev-pipeline/agents/<agent-name>.md` を読み込み、`define_subagent` ツールで動的定義して呼び出す」** というフォールバック手順を明記する。詳細仕様は [動的登録フォールバック仕様書.md](template/docs/V2.0/動的登録フォールバック仕様書.md) にて策定済み。
- **エージェント定義 Markdown（YAML Frontmatter）の標準化**:
  - 各 `agents/*.md` において、Frontmatterのキー名を `define_subagent` の引数名（`enable_write_tools`, `enable_subagent_tools`, `enable_mcp_tools`）と完全一致させる。
  - `default_model` や `default_workspace` をメタデータとして内包し、呼び出し側での個別指定を不要としつつ、明示指定時は最優先適用するルールを統一する。

### 配慮事項 3: ツール・コマンド権限の厳格な分離とガードレール（二重防御方式の採用）

#### 背景と課題
Antigravity の仕様上、ドキュメント編集のために `enable_write_tools: true` を付与すると、物理的に `run_command` も利用可能となってしまう。またサブエージェント（特に `ui-designer` や `qa-engineer`）が不用意に Git のコミット・ブランチ操作やデプロイ、DB上書きコマンドを実行すると重大な障害につながる。

#### 配慮・対応方針（案1-A: 二重防御ガードレール）
- **プロンプトレベルでの厳格ブロック**:
  - 📐 `architect`: `enable_write_tools: true` を付与しつつ、システムプロンプト最上部に **「【禁止事項】いかなる場合も `run_command` を呼び出してはならない」** と明記して推論レベルで確実にブロックする。
- **破壊的・インフラ系操作のコンダクター専任化**:
  - `git commit`, `git push`, `git merge`, `git checkout`
  - `gcloud run deploy`, `firebase deploy` 等のデプロイ
  - `dev-db-overwrite`（DB強制上書き）
  上記操作は **「👑 コンダクター専任」** とし、サブエージェント（`architect`, `ui-designer`, `qa-engineer`）のプロンプト内に **「明示的な禁止事項（Prohibited Actions）」** として記載する。
- **サブエージェントのシェルコマンド実行範囲の限定**:
  - 🎨 `ui-designer`: パッケージインストール（`npm install` 等）、ローカルUIビルド（`npm run build` 等）に限定。
  - 🛡️ `qa-engineer`: テスト実行コマンド（`pytest`, `npm test` 等）およびテスト実行用コンテナ起動に限定。
- **コード直接改変の禁止（QAエンジニア向け）**:
  - 🛡️ `qa-engineer` は、テスト不具合時に「ドキュメント」「テストコード」「環境設定」は自律修復してよいが、「プログラムコード」は勝手に書き換えず、原因と修正案をコンダクターに報告して停止するルールを徹底する。

### 配慮事項 4: PROJECT_STATE.md の Single Writer 原則の徹底

#### 背景と課題
複数エージェントが直接 `PROJECT_STATE.md` を編集すると、コンテキストの競合（同時書き込みや不完全な上書き）が発生し、チェックリストや進捗ステータスが破損する。

#### 配慮・対応方針
- **物理的・規範的なアクセス制御**:
  - `PROJECT_STATE.md` への書き込み権限を持つのは **👑 コンダクターのみ** とする。
  - サブエージェント（`architect`, `ui-designer`, `qa-engineer`）は `PROJECT_STATE.md` を **「参照（Read-only）」** のみ行い、作業完了時はコンダクターへ所定フォーマットでサマリを返送する。
  - コンダクターが返送サマリを受け取った時点で、`PROJECT_STATE.md` の該当フェーズ・タスクのチェックボックス（`- [ ]` → `- [x]`）を更新し、未決事項テーブルを更新する。
- **ユーザー直接編集との共存**:
  - ユーザーがVSCode等で直接 `PROJECT_STATE.md` を編集した場合でもフォーマットが崩れないよう、Markdownのセクション構造をシンプルに保つ。

### 配慮事項 5: テンプレート雛形とルールファイル（rules/）のクロスリファレンス整合性

#### 背景と課題
現在 `templates/` にあるドキュメント雛形（`AI駆動システム開発手順書V2.md` など）や `rules/dev-process-standards.md` は、旧来の「スキル単体実行」をベースに記載されている。
サブエージェント体制および `PROJECT_STATE.md` を導入したにもかかわらず、プロジェクト展開後のドキュメント内に旧仕様の記述が残っていると、ユーザーやエージェントが混乱する。

#### 配慮・対応方針
- **`templates/` 配下ドキュメントの改訂**:
  - `AI駆動システム開発手順書V2.md`: 「サブエージェント協調・PROJECT_STATE一元管理版」として全面刷新する。
  - 各設計書テンプレート（要件定義書、画面仕様書、テスト計画書など）の冒頭に、どのサブエージェントが主作成者であるかを明記する。
  - `templates/PROJECT_STATE.md.template` を新規作成し、`dev-phase1-setup` で自動展開されるようにする。
- **`rules/` 配下の改訂とコンダクター動作規範のビルトイン指針**:
  - `rules/dev-process-standards.md` および `.agents/rules/dev-process-standards.md` に、「サブエージェント協調ルール」「Single Writer原則」「PHASE 4以降のシステム修正後のDockerコンテナ再構成ルール（`docker compose down` → `up --build -d`）」を明確に反映する。
  - **コンダクターの基本動作規範のビルトイン**: メインエージェント（コンダクター）はプロジェクトの進行管理・オーケストレーションの最高責任者であるため、その基本動作規範（①オーケストレーションと委譲、②`PROJECT_STATE.md` の Single Writer 専任、③承認ゲートでの要約サマリ提示責務、④動的登録フォールバックの自律実行、⑤`invoke_subagent` 実行時の `Model` / `Workspace` 明示引数渡し）を、プラグイン側ルール（`.agents/rules/dev-process-standards.md`）、プロジェクト側ルール（`rules/dev-process-standards.md`）、および共通プロンプト定義（`AGENTS.md`, `GEMINI.md`）に確実にビルトインする。

### 配慮事項 6: 既存プロジェクト（旧方式）からの段階的移行・後方互換性

#### 背景と課題
新テンプレートが完成した後、すでに旧パイプライン方式で進行しているプロジェクトや、既存のレガシーリポジトリに新方式を適用したいケースが発生する。

#### 配慮・対応方針
- **途中フェーズからの導入（マイグレーション）対応**:
  - `dev-phase1-setup` が走っていない既存プロジェクトでも、`PROJECT_STATE.md` を後から配置・初期化できるようにする。
  - メインエージェント（コンダクター）は、プロジェクト直下に `PROJECT_STATE.md` が存在しない場合、既存の `docs/` や Git ログを走査して「現在のフェーズ（例: PHASE 5 など）」を推定し、`PROJECT_STATE.md` を動的生成して追随できる運用手順を確立する。
- **下位互換性の維持**:
  - サブエージェント機能が無効化されている環境や単一エージェントモードで動作させる場合でも、既存のスキル手順（`dev-phase1-setup` 〜 `dev-phase8-rules`）単体で開発を続行できるようにフォールバックパスを残す。

---

### 配慮事項 7: 知見蓄積（ナレッジフィードバック）の二層分離とループ構造の組込み

#### 背景と課題
課題4（ナレッジフィードバック）で扱う内容と密接に関連するが、パイプライン再編集時に「知見をどこに記録し、次回以降どう活かすか」の格納場所を明確にしておかないと、知見が散逸して再利用されない。

#### 配慮・対応方針
- **「プロジェクト固有知見」と「全体共通知見（テンプレート側）」の二層分離**:
  1. **プロジェクト固有知見 (Tier 1)**:
     - 当該プロジェクトの `PROJECT_STATE.md` 内「未決事項・決定事項ログ」および `docs/` 配下に蓄積。
     - 本番改訂時の `docs/Vn.m改訂レポート.md` に課題・対策を記録。
  2. **全体共通知見（テンプレートへの還元 / Tier 2)**:
     - 開発進行中は、プロジェクトルート直下の `./TEMPLATE_PROMOTIONS.md`（一時バッファ）に蓄積。
     - PHASE 8（初回リリース時）および改訂完了時のユーザー昇格レビュー承認を経て、テンプレート側の `.agents/plugins/system-dev-pipeline/rules/` や各エージェントの `agents/*.md` のシステムプロンプトへ昇格・マージする。
- **再編集時のファイル配置準備**:
  - 知見蓄積ルールを `rules/システム改訂ルール.md` およびプラグイン内ルールに明文化しておく。
