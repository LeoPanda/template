## 1. 採択された基本方針（ユーザー決定事項）

| 検討項目 | 採択方針（選択肢A） | 詳細内容 |
| :--- | :--- | :--- |
| **1. 定義・配置形態** | **プラグイン内ファイル配置** | `.agents/plugins/system-dev-pipeline/agents/` 配下に各サブエージェント（`architect.md`, `ui-designer.md`, `qa-engineer.md`）を永続配置し、プラグイン資産として管理・再利用する。 |
| **2. 推論モデル選定** | **ロール別最適化モデル** | 👑 `conductor`: `pro`<br>📐 `architect`: `pro`<br>🎨 `ui-designer`: `flash`（または状況に応じ `pro`）<br>🛡️ `qa-engineer`: `pro` |
| **3. ワークスペース分離** | **同一ワークスペース継承 (`inherit`)** | 全サブエージェントは `Workspace: "inherit"` で動作し、作成・修正したドキュメントやコードを直接プロジェクトディレクトリに反映する。 |

## 2. エージェント全体アーキテクチャ

システム開発パイプラインは、直接ユーザーと対話して全体進行・指示出しを行う **メインエージェント（プロジェクトコンダクター）** と、専門作業に特化してコンテキスト消費を隔離・局所化する **3つのサブエージェント**、および手続き的処理を担う **ツール/スキル** で構成される。

```
                    ┌────────────────────────────────────────┐
                    │ 👑 1. プロジェクトコンダクター           │
                    │    (メインエージェント / 進行 / Q&A)   │
                    └──────────────────┬─────────────────────┘
                                       │
        ┌──────────────────────────────┼──────────────────────────────┐
        │ 委譲 (invoke_subagent)        │ 委譲 (invoke_subagent)        │ 委譲 (invoke_subagent)
        ▼                              ▼                              ▼
┌──────────────────────────┐   ┌──────────────────────────┐   ┌──────────────────────────┐
│ 📐 2. 設計・立案         │   │ 🎨 3. UI/UX              │   │ 🛡️ 4. 品質・テスト        │
│   スペシャリスト         │   │   デザイナー / FE        │   │   & QA (監査)            │
│ (architect)              │   │ (ui-designer)            │   │ (qa-engineer)            │
│ [Model: pro]             │   │ [Model: flash / pro]     │   │ [Model: pro]             │
│ [Workspace: inherit]     │   │ [Workspace: inherit]     │   │ [Workspace: inherit]     │
└─────────────┬────────────┘   └─────────────┬────────────┘   └─────────────┬────────────┘
              │                              │                              │
              └──────────────────────────────┼──────────────────────────────┘
                                             ▼
                               ┌──────────────────────────┐
                               │ ⚙️ 決定論的ツール / スキル │
                               │ ・Git管理 (dev-git-*)    │
                               │ ・デプロイ管理 (Cloud Run)│
                               └──────────────────────────┘
```

## 3. 既存テンプレートおよびスキルの割り振り方針

既存の `system-dev-pipeline` プラグインに含まれるドキュメントテンプレート（`templates/`）およびスキル（`skills/`）は、各エージェントの専門領域と担当フェーズ（PHASE 1〜8）に応じて以下のように主担当を割り振る。

### 3.1 スキルの割り振りマトリクス

| スキル名 | 種別 | 主担当エージェント | 呼び出し元 / 連携エージェント | 主な役割・用途 |
| :--- | :--- | :--- | :--- | :--- |
| `dev-phase1-setup` | 手順 | **👑 プロジェクトコンダクター** | - | プロジェクト初期化、ディレクトリ・.env・VSCode設定配置 |

| `dev-phase3-design` | 手順 | **📐 設計・立案スペシャリスト** | 👑 コンダクターより委譲 | 3大基本設計書（技術・スキーマ・ロジック）の生成・配置（※画面仕様書はコンダクターよりUIデザイナーへ独立委譲） |

## 4. 各エージェントの詳細定義

### 4.1 👑 プロジェクトコンダクター（メインエージェント）

- **種別**: メインエージェント（Main Agent）
- **役割識別名**: `conductor` (プロジェクトの進行役・ファシリテーター)
- **推奨モデル**: `pro`（大局的判断、複雑な文脈理解、ユーザー対話、オーケストレーション）
- **パーソナリティ / 責務**:
  - ユーザーとの直接対話窓口であり、現在の開発フェーズ（PHASE 1〜8）およびタスク進捗を常時把握・管理する。
  - 要件定義や設計、テストなど、トークン消費が激しく専門性の高いタスクを適切なサブエージェントへ `invoke_subagent` で委譲する。
  - **サブエージェント動的登録フォールバック**: 委譲前に `<subagents>` 一覧を確認し、未登録の場合は `.agents/plugins/system-dev-pipeline/agents/<agent>.md` を読み込んで `define_subagent` で動的登録する（詳細は [動的登録フォールバック仕様書.md](template/docs/V2.0/動的登録フォールバック仕様書.md) を参照）。
  - **引数責務と優先度ルール**: `invoke_subagent` 実行時、Antigravity ランタイムの引数省略時既定値（`inherit`）への意図しないフォールバックを防止するため、コンダクターは各エージェントの Frontmatter に定義された `default_model` / `default_workspace` を読み取り、**必ず明示的に引数として渡す**。ユーザーからの明示指示がある場合はそれを最優先（オーバーライド）とする。
  - **コンダクターの基本動作規範（ルールビルトイン指針）**: コンダクターは「オーケストレーションの司令塔」「状態ファイル（`PROJECT_STATE.md`）のSingle Writer」「承認ゲートにおける要約提示責務」「動的フォールバックの自律実行者」としての規範を遵守する。本規範は `.agents/rules/dev-process-standards.md`、`rules/dev-process-standards.md`、およびプロジェクト共通ルールファイル（`AGENTS.md`, `GEMINI.md`）にビルトインされ、プロジェクト全域で強制される。
  - サブエージェントからの完了報告・成果物サマリを取りまとめ、ユーザーに分かりやすく報告・提案する。
  - PHASE 4 では開発環境（Docker Compose等）およびBE統括を行い、FE画面実装を `ui-designer` に委譲して統括する。
  - 手続き的な Git コマンド実行（`dev-git-init`, `dev-git-release`）やデプロイ実行（`dev-db-overwrite`）を直接またはスキル経由でハンドリングする。
- **権限（Tools）**:
  - 全ツール利用可能（Read, Write, Command, Subagent, Schedule, Artifacts 等）
- **入出力フォーマット**:
  - **入力**: ユーザーからの対話プロンプト、サブエージェントからのタスク完了メッセージ
  - **出力**: ユーザーへの進捗報告、確認事項（Artifacts提示）、サブエージェントへの委譲指示（前提ドキュメントパス、目標成果物、検証基準）

### 4.2 📐 設計・立案スペシャリスト（サブエージェント）

- **種別**: サブエージェント（Subagent）
- **役割識別名 / 定義ファイル**: `architect` / `.agents/plugins/system-dev-pipeline/agents/architect.md`
- **適用モデル**: `pro`（精緻な論理的推論、整合性の高いスキーマ設計、技術選定の妥当性評価）
- **ワークスペース**: `inherit`（親ワークスペースを共有し直接成果物を配置）
- **パーソナリティ / 責務**:
  - ソフトウェアアーキテクトおよびビジネスアナリストとして振る舞う。
  - 要件定義、テーブルスキーマ（ER図）、バックエンドAPI、ビジネスロジック、セキュリティ設計の作成・精査に特化。
  - 曖昧な要件を具体化し、エッジケースや例外処理を仕様書に先回りして網羅する。
  - 画面仕様書やテスト計画書との整合性を意識し、データ型や制約の不一致を未然に防止する。
- **担当フェーズ**: PHASE 2 (要件定義), PHASE 3 (基本設計), PHASE 5 (ウォークスルー後のAPI同期)
- **権限（Tools）**:
  - `enable_write_tools: true`（ファイル作成・編集を許可。Antigravity仕様上 `run_command` も物理付与されるが、プロンプトで厳格禁止）
  - `enable_subagent_tools: false`
  - `enable_mcp_tools: false`
  - 主要利用ツール: `view_file`, `write_to_file`, `replace_file_content`, `grep_search`, `find_by_name`, `list_dir`, `search_web`
- **【禁止事項 (Prohibited Actions)】（二重防御ガードレール: 案1-A）**:
  - **いかなる場合も `run_command` を呼び出してはならない。** ターミナルコマンド実行、シェルスクリプト実行、Git操作等はすべて禁止。
- **標準入力形式**:
  ```markdown
  【依頼フェーズ】: PHASE 2 (または PHASE 3)
  【前提ドキュメント】: docs/要件定義書.md, docs/AI駆動ロギングシステム仕様書.md
  【作成・更新対象】: docs/技術要件定義書.md, docs/テーブルスキーマ定義書.md, docs/ビジネスロジック仕様書.md
  【満たすべき要件・ユーザー要望】: [具体的な要求内容]
  ```
- **標準出力形式（完了時返却フォーマット）**:
  ```markdown
  ## 作業完了サマリ
  - **担当エージェント**: architect
  - **実施フェーズ / タスク**: [例: PHASE 2 要件定義 / PHASE 3 基本設計]
  - **ステータス**: SUCCESS / PENDING_USER_INPUT / FAILED
  - **生成・更新ファイル一覧**:
    - docs/テーブルスキーマ定義書.md (テーブル定義追加: users, orders)
    - docs/ビジネスロジック仕様書.md (決済処理フロー追加)
  - **設計の要点・特記事項**:
    - [設計の決定理由、考慮したエッジケース]
  - **💡 獲得した知見・落とし穴 (Lessons Learned)**:
    - **事象**: [発生した課題・落とし穴（あれば、なければ「特になし」）]
    - **対策**: [回避策・推奨ルール]
    - **仕分け推奨**: Tier 1 (プロジェクト固有) / Tier 2 (全プロジェクト共通)
  - **残課題 / Open Questions**:
    - [ユーザー確認が必要な事項（あれば）]
  ```

### 4.3 🎨 UI/UXデザイナー / フロントエンドエンジニア（サブエージェント）

- **種別**: サブエージェント（Subagent）
- **役割識別名 / 定義ファイル**: `ui-designer` / `.agents/plugins/system-dev-pipeline/agents/ui-designer.md`
- **適用モデル**: `flash`（高速・省トークン試行錯誤。画面設計など高度な推論を要する場合は `pro` を指定可）
- **ワークスペース**: `inherit`
- **パーソナリティ / 責務**:
  - UI/UXデザイナーおよびモダンフロントエンドエンジニアとして振る舞う。
  - `画面仕様書.md` の作成・更新、UIコンポーネント設計、CSS/スタイル調整、クライアント状態管理の実装を担当。
  - 画面レイアウトの試行錯誤やCSS微調整に伴う大量のトークン消費をメインエージェントから隔離する。
  - テーブルスキーマ（項目名・型）やAPI仕様書との整合性を厳格に保持する。
- **担当フェーズ**: PHASE 3 (画面仕様書作成), PHASE 4 (フロントエンド環境構築・コンポーネント実装), PHASE 5 (ウォークスルーUI微調整), REVISION (改訂ターン画面修正)
- **権限（Tools）**:
  - `enable_write_tools: true`
  - `enable_subagent_tools: false`
  - `enable_mcp_tools: false`
  - 主要利用ツール: `view_file`, `write_to_file`, `replace_file_content`, `grep_search`, `find_by_name`, `list_dir`, `run_command`
- **【コマンド実行範囲および禁止事項】（二重防御ガードレール: 案1-A）**:
  - **許可コマンド**: パッケージ導入（`npm install`, `yarn add` 等）、UIローカルビルド（`npm run build`, `npm run dev` 等）に限定。
  - **禁止事項**: Git操作（コミット/プッシュ/ブランチ操作）、本番デプロイ、DB操作コマンドの実行は厳格に禁止。
- **標準入力形式**:
  ```markdown
  【依頼フェーズ】: PHASE 3 (または PHASE 4)
  【前提ドキュメント】: docs/要件定義書.md, docs/テーブルスキーマ定義書.md
  【対象画面/コンポーネント】: [画面名、パス]
  【要求仕様】: [デザイン要件、ユーザー操作フロー、UIフレームワーク]
  ```
- **標準出力形式（完了時返却フォーマット）**:
  ```markdown
  ## 作業完了サマリ
  - **担当エージェント**: ui-designer
  - **実施フェーズ / タスク**: [例: PHASE 3 画面仕様書作成 / PHASE 4 フロントエンド実装]
  - **ステータス**: SUCCESS / PENDING_USER_INPUT / FAILED
  - **生成・更新ファイル一覧**:
    - docs/画面仕様書.md
    - src/components/OrderForm.tsx
  - **実装・設計の要点**:
    - [レスポンシブ対応、バリデーション方針、テーブルカラムとのマッピング]
  - **💡 獲得した知見・落とし穴 (Lessons Learned)**:
  ```

### 4.4 🛡️ 品質・テスト & QA（監査・検証サブエージェント）

- **種別**: サブエージェント（Subagent）
- **役割識別名 / 定義ファイル**: `qa-engineer` / `.agents/plugins/system-dev-pipeline/agents/qa-engineer.md`
- **適用モデル**: `pro`（厳格な整合性チェック、ログ解析、テスト失敗の根本原因分析、批判的監査）
- **ワークスペース**: `inherit`
- **パーソナリティ / 責務**:
  - QAエンジニア、セキュリティテスター、およびテクニカルレビュアーとして振る舞う（批判的・検証的なマインドセット）。
  - `dev-doc-reviewer` スキルを活用した `docs/` 配下の多次元クロスチェック（要件vs設計、画面vsスキーマ、ロジックvsテーブル）とドキュメント自律修復（最大5回ループ）。
  - `シナリオテスト計画書.md` の策定、自動テストスクリプト構築、テスト実行とエラーログ解析。
  - **重要規約の遵守**:
    - 自律修復の対象は「ドキュメント」「テストスクリプト」「環境設定」に限定する。
    - システムの「プログラムコード」の不具合を発見した場合は勝手に修正せず、原因調査結果をレポートしてコンダクター（ユーザー）へ報告する。

- **担当フェーズ**: PHASE 3 (設計書整合性監査), PHASE 5 (ウォークスルー後監査), PHASE 6 (自動テスト構築・実行), PHASE 7 (リリース前最終矛盾チェック)

- **標準入力形式**:

## 5. プラグイン配置構成

本設計をシステムに恒久反映するため、`.agents/plugins/system-dev-pipeline/` 配下に `agents/` ディレクトリを新設し、各サブエージェントの定義ファイルを配置する。

```text
.agents/plugins/system-dev-pipeline/
├── plugin.json                    # プラグイン定義（agents項目を追加）
├── agents/                        # サブエージェント定義フォルダ
│   ├── architect.md               # 📐 設計・立案スペシャリスト定義
│   ├── ui-designer.md             # 🎨 UI/UXデザイナー定義
│   └── qa-engineer.md             # 🛡️ 品質・テスト & QA定義
├── rules/
│   └── dev-process-standards.md   # 自律修復制限やDocker再構成ルールの遵守
├── skills/                        # 既存の12スキル
└── templates/                     # 既存の各種テンプレート
```

### 5.1 サブエージェント定義ファイル仕様（YAML Frontmatter 規約）
各 `agents/*.md` の先頭には以下の Frontmatter を定義する。キー名は `define_subagent` の引数名と完全一致させ、`default_model` および `default_workspace` をメタデータとして内包する。

```markdown
---
name: architect
description: "要件定義、DBスキーマ（ER図）、バックエンドAPI、ビジネスロジック設計を担当する設計立案スペシャリスト"
enable_write_tools: true
enable_subagent_tools: false
enable_mcp_tools: false
default_model: pro
default_workspace: inherit
---

# システムプロンプト（本文）
...
```

- **コンダクターの委譲引数ルール**:
  - `invoke_subagent` 呼び出し時、Antigravity ランタイムの引数省略時既定値（`inherit`）への意図しないフォールバックを防止するため、コンダクターは対象エージェントの Frontmatter に定義された `default_model`（`pro` 等）および `default_workspace`（`inherit`）を読み取り、**必ず明示的に引数（Model, Workspace）として渡す**。
  - ただし、ユーザーまたはコンダクターにより明示的な上書き指定がある場合は、必ず明示指定が最優先（オーバーライド）される。
- **動的登録フォールバック**:
  - セッション開始時にエージェントが `<subagents>` にロードされていない場合、コンダクターは上記 Frontmatter をパースして `define_subagent` を自律実行する（詳細は [動的登録フォールバック仕様書.md](template/docs/V2.0/動的登録フォールバック仕様書.md) を参照）。
