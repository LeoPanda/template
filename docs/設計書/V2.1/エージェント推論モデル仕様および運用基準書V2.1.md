## 1. 背景と目的

Antigravityマルチエージェント開発環境において、各エージェント（メインエージェントおよびサブエージェント）に割り当てる推論モデル（`Model`）の仕様、論理ティア（抽象階層）の仕組み、および今後のGeminiバージョンアップ時における保守・運用方針について定義するものである。

本ドキュメントは以下の疑問および設計上の前提を体系化し、開発者・運用者が一貫した基準でモデル選定を行えるようにすることを目的とする。

1. **「Proモデル」とは具体的に何を指しているのか？**（Flashモデル等との位置づけの違い）
2. **今後Geminiがバージョンアップ（3.8 → 3.9 → 4.0等）するたびに、エージェント定義や呼び出しコードの書き換えが必要になるのか？**
3. **V2.1で新設・拡張されたロール（`backend-engineer`, 3大レビュー担当, WikiSkill）にはどのモデルティアを割り当てるべきか？**

---

## 2. モデル指定子のアーキテクチャ（論理ティア設計）

Antigravity のエージェントランタイム（`invoke_subagent` 等）における `Model` パラメータは、特定の具体的なモデルバージョン文字列（例: `gemini-3.8-flash` 等）を直接指定する方式ではなく、**役割や計算リソースに応じた「抽象化されたモデル階層（論理ティア）」** として設計されている。

### サポートされているモデル指定子一覧 (`invoke_subagent` 引数)

| 指定値 (`Model`) | 役割と対象タスク | 想定されるモデル特性 | 推奨用途 |
| :--- | :--- | :--- | :--- |
| **`inherit`**<br>(デフォルト) | 呼び出し元（親エージェント）のモデル設定をそのまま継承 | 親エージェントと完全に同一のモデルで実行 | 基本的なデフォルト指定 |
| **`flash_lite`** | 非常に軽量な単純タスク | 最小コスト・超高速 | 単純なテキスト変換・フラグ判定など |
| **`flash`** | 軽量・高速な探索・閲覧タスク | 高速・低レイテンシ | ファイル閲覧、キーワード検索、一次リサーチ、UI試行錯誤 |
| **`pro`** | **深い推論（Deep Reasoning）、高度な設計、大規模リファクタリング、多段階計画、厳格な監査** | **最上位推論・高キャパシティ** | アーキテクチャ設計、BE実装、3大レビュー、テスト原因分析、複合検証ゲート |

## 3. 「Proモデル」の具体的位置づけと実体

### 3.1 プラットフォーム側での動的ルーティング
ユーザーがUI（IDE等の設定）上でベースモデルとして例えば「Gemini 3.8 Flash」を選択している場合であっても、サブエージェント呼び出し時に `Model: "pro"` を明示すると、以下のように動作する：

```
[親エージェント: Conductor] ──── (invoke_subagent: Model="pro") ────> [サブエージェント: Architect / QA / BE]
      │                                                                           │
      ▼                                                                           ▼
  Flash系推論エンジン                                                         Pro系推論エンジン
 (通常対話・オーケストレーション)                                             (深い推論・設計・レビュー・BE実装)
```

* **実体**: Google / Antigravity のバックエンドインフラ側において、**「その時点で利用可能な最高性能の推論モデル（Proクラス / Reasoning強化モデル）」** に自動的にバインド（ルーティング）される論理エイリアスである。
* **狙い**: 普段のチャットや全体統括はレスポンスが高速なFlash系を使いつつ、高い論理的思考力が要求される専門エージェントにのみPro系の推論リソースを局所的に割り振ることで、全体の処理速度と推論精度の最適化を両立する。

## 4. Geminiバージョンアップ時の保守方針（変更不要性）

### 結論：原則として、エージェント定義やコードの修正は不要

Geminiの世代が新しくなった場合でも、**設計書やエージェント呼び出しコードを都度書き換える必要はない**。

### 変更が不要な理由

1. **バージョン非依存の抽象化（ハードコードの排除）**
   * エージェント定義や呼び出し引数には `pro`, `flash`, `inherit` などの論理ティア名のみを使用し、具体的なバージョン番号（例: `3.8`, `4.0`）をコード内に埋め込まない規約となっている。
2. **プラットフォーム側での自動追従**
   * プラットフォーム（Google / Antigravity）側で新しい世代のモデルがロールアウトされると、論理名 `pro` や `flash` が指すバックエンドのターゲットモデルが最新の推奨安定版へと自動的に更新される。
   * これにより、ユーザーや開発者が個別設定を追従・メンテナンスする人的コストをゼロに抑えることができる。

## 5. 各エージェントにおけるモデル割り当て基準 (V2.1)

システム開発パイプライン V2.1 における各エージェントの推奨モデル割り当て方針は以下の通りとする。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       エージェント別 モデル割り当て指針 (V2.1)              │
├────────────────────────────────┬───────────────┬────────────────────────────┤
│ エージェント名 / 役割          │ 指定モデル    │ 選定理由                   │
├────────────────────────────────┼───────────────┼────────────────────────────┤
│ 👑 conductor (コンダクター)    │ inherit / pro │ プロジェクト進行・状態統括 │
│ 📐 architect (設計スペシャリスト)│ pro           │ 多次元整合性・深層推論必須 │
│ 💻 backend-engineer (BE実装)   │ pro           │ API整合・DB/ロジック堅牢性 │
│ 🎨 ui-designer (UI/UXデザイナー)│ flash または pro│ 画面モック/UIロジック      │
│ 🛡️ qa-engineer (QA・監査・検証)│ pro           │ 3大レビュー・網羅的テスト  │
│ 🔍 research (リサーチ)          │ flash         │ 高速探索・情報収集         │
└────────────────────────────────┴───────────────┴────────────────────────────┘
```

1. **📐 architect (`pro`)**
   * `docs/` 配下の要件定義・設計書間の不整合検出、ディレクトリ構造設計、システム展開プロファイル（Profile A〜D）の選定など、文脈把握と論理矛盾の検証に極めて高度な推論を要するため。
2. **💻 backend-engineer (`pro`)**
   * テーブルスキーマやビジネスロジック仕様書に完全準拠したコード生成、トランザクション境界設計、型安全なAPI実装、例外処理の網羅など、堅牢なシステム基盤構築にProティアの深い論理推論が不可欠であるため。
3. **🛡️ qa-engineer (`pro`)**
   * **3大レビュー（基本設計レビュー、コード品質レビュー、システム総合レビュー）** の批判的検証（Red Team的アプローチ）、複雑なUnified Diffの立案、E2Eシナリオテストの自動生成、エラーログ解析、複合検証ゲート（Gating）の多角判定を担うため、最上位の推論力が必要。
4. **🎨 ui-designer (`flash` または `pro`)**
   * 初期のUIモックアップやCSS/コンポーネントの試行錯誤は高速な `flash` を推奨。
   * 複雑なクライアント状態管理やインタラクション設計を伴う場合は `pro` へ昇格。
5. **👑 conductor (`inherit` または `pro`)**
   * 通常の対話進行や状態管理（Single Writer）は高速なベースモデル（`inherit`）で対応可能。大規模なプロジェクト全体の文脈要約や、WikiSkill進化パッチの集約時には `pro` を指定可能。
6. **🔍 research (`flash`)**
   * ソースコードの文字列検索やWeb上の公式ドキュメント調査など、レイテンシと探索スピードが重視されるタスクに最適。

## 6. まとめ・運用ルール

* **新エージェント作成時**:
  * 具体的バージョン番号（`gemini-X.Y-...`）は一切記載せず、必ず `inherit`, `pro`, `flash`, `flash_lite` のいずれかを使用すること。
* **モデル指定の引数解決ルール**:
  * モデルの割り当てはエージェント静的定義（YAML Frontmatterの `default_model`）に閉じ込めるのではなく、親エージェント（コンダクター）が `invoke_subagent` を呼び出す際の引数（`Model`）で明示的に制御する。
  * コンダクターが明示的に指定しない場合、Frontmatterの `default_model` を読み取って引数へセットし、Antigravity既定値への意図しないフォールバックを防止する。
