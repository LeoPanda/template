文書バージョン: 1.0  
作成日: 2026-10-10  
対象バージョン: AI駆動システム開発ライフサイクルテンプレート V2.1  
ステータス: 策定完了 (Step 3 決定版)

## 1. はじめに

### 1.1 背景と課題認識
AI駆動システム開発ライフサイクル V2.0 および V2.1（Step 1: レビューシステム、Step 2: WikiSkill永続ナレッジループ）を通じて、成果物の品質担保と試行錯誤知見の自己進化機構が整備された。

しかしながら、**「AIエージェント協調体制、状態管理機構（Single Writer）、レビューゲート、自律修復ループなどの開発支援システム（テンプレート）そのものが、実際にどれほど有効に機能しているか」** という点については、これまで主に開発者やエージェントの主観的・感覚的なフィードバックに依存していた。

この主観的運用には以下の重大な構造的課題が存在する：
1. **ボトルネックとオーバーヘッドの不可視性**:
   - メインコンテキストが急速に枯渇する原因が「不必要な会話の肥大化」なのか「サブエージェント委譲の不足」なのか「特定ツールの過剰呼び出し」なのか客観判断できない。
2. **手戻りとリグレッションの定量的把握の欠如**:
   - フェーズ間（設計〜実装〜テスト）での手戻り回数や、自律修復ループ（Auto-Healing）の収束速度が測定されていないため、プロンプトやスキルのどの部分が品質劣化を引き起こしているかを特定できない。
3. **テンプレート自身の改善サイクルの断絶**:
   - 個別案件で生じた「開発プロセスの摩擦や非効率」が、テンプレート開発元（プロンプト、規約、スキル群）に定量的データとしてフィードバックされず、テンプレート自体の客観的進化が進まない。

### 1.2 本設計書の目的と位置づけ
本文書は、開発対象システム（アプリケーション）のテストやレビューとは明確にレイヤーを区別し、**本テンプレートシステム（開発支援基盤・メタプラットフォーム）自身の稼働健全性・開発効率・アーキテクチャ適合性を客観的・定量的に測定し、テンプレートリポジトリへ還元するフィードバック機構** を定義する。

#### WikiSkill（Step 2: 知見蓄積システム）とのレイヤー分離
```
┌────────────────────────────────────────────────────────────────────────┐
│  【Step 3: 開発支援システム定量測定・フィードバック】 (Meta Platform)   │
│   ・対象: AIエージェント体制、Single Writer、Token効率、プロセス健全性 │
│   ・方式: 事前定義されたKPIに基づく定量的・演繹的メトリクス集計        │
│   ・出力: 健全性スコア、ボトルネック検知、テンプレート改善トリガー     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ (客観的メトリクス異常の検知・投入)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│  【Step 2: WikiSkill 永続ナレッジ自己進化ループ】 (Implementation Asset)│
│   ・対象: 開発作業中のエラー・障害・ベストプラクティス (Tier 1 / Tier 2)│
│   ・方式: 事後・帰納的な試行錯誤の根本原因分析 (RCA) とスキル蒸留      │
│   ・出力: 再発防止パターン (Wiki層)、昇格スキルパッチ (.agents/plugins)│
└────────────────────────────────────────────────────────────────────────┘
```

### 1.3 測定の4大基本原則
1. **非侵襲性（Non-Invasive）**:
   - メトリクス収集のためにエージェントの推論コンテキストを過度に消費したり、開発進行を阻害してはならない。ログ解析やターン境界でのメタデータ抽出によりバックグラウンドで収集する。
2. **客観的・機械的集計（Objective & Automated）**:
   - エージェントの主観的な自己評価（「スムーズに進んだ」等）を排除し、トークン数、ターン数、違反検出数、初回合格率など機械的数値に基づく。
3. **Single Writer ガードレールの厳格保護**:
   - メトリクス記録によって状態ファイル（`PROJECT_STATE.md`）の整合性が脅かされないよう、メトリクス専用領域（`metrics/`）への分離記録を行う。
4. **実行可能な改善への直結（Actionable Feedback）**:
   - 単なる集計・可視化にとどまらず、閾値超過時に「どのプロンプト/スキル/規約をどう見直すべきか」の改善アクションを自動導出する。

## 2. 定量測定メトリクス体系（3大軸・12指標）

本テンプレートシステムの稼働状態を多角的に捉えるため、**「リソース＆コンテキスト効率」「開発品質＆手戻り」「プロセス健全性＆ガバナンス」** の3軸・12指標を策定する。

```
┌────────────────────────────────────────────────────────────────────────┐
│                  開発支援システム 定量測定メトリクス体系 (3大軸)       │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  【1. リソース＆コンテキスト効率】 (Resource & Context Efficiency)     │
│    ・M-RES-01: メインコンテキスト消費率 / セッション寿命               │
│    ・M-RES-02: サブエージェント委譲率 (Delegation Ratio)               │
│    ・M-RES-03: トークン対成果物効率 (Tokens per Artifact)              │
│    ・M-RES-04: ツール呼び出し密度・冗長性 (Tool Call Efficiency)       │
│                                                                        │
│  【2. 開発品質＆手戻り】 (Quality & Rework Metrics)                    │
│    ・M-QLT-01: レビュー初回合格率 (First-Pass Review Rate)             │
│    ・M-QLT-02: レビュー指摘密度 (Defect Density per Phase)             │
│    ・M-QLT-03: スルーテスト初回合格率 & リグレッション率              │
│    ・M-QLT-04: 自律修復ループ収束ターン数 (Auto-Healing Convergence)    │
│                                                                        │
│  【3. プロセス健全性＆ガバナンス】 (Process Health & Governance)       │
│    ・M-GOV-01: Single Writer原則遵守度 (State Mutation Violations)     │
│    ・M-GOV-02: コンテキスト汚染・ルール違反率 (Guardrail Violations)   │
│    ・M-GOV-03: フェーズ所要ターン数 (Phase Turn Duration)              │
│    ・M-GOV-04: ドキュメント相互整合性スコア (Doc Consistency Score)    │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

---

### 2.1 軸1: リソース＆コンテキスト効率指標 (Resource & Context Efficiency)

エージェントの有限なコンテキストウィンドウとトークンリソースが、過不足なく健全に配分されているかを測定する。

| 指標ID | 指標名称 | 定義・算出式 | 目標基準値 | 判定基準 (Warning / Critical) |
| :--- | :--- | :--- | :--- | :--- |
| **M-RES-01** | **メインコンテキスト消費率** | `(現在ターンのメインコンテキストToken数) / (モデル最大コンテキスト長) * 100` | **< 60%** (通常時) | Warning: ≥ 70%<br>Critical: ≥ 85% |
| **M-RES-02** | **サブエージェント委譲率** | `(サブエージェント実行ターン数) / (総実行ターン数) * 100` | **≥ 50%** (PHASE 3, 4, 6) | Warning: < 40%<br>Critical: < 25% (Main抱え込み) |
| **M-RES-03** | **成果物トークン効率** | `(生成・改訂された正味コード/ドキュメント行数 LOC) / (総消費Token数 / 1,000)` | **≥ 1.5 LOC / kTokens** | Warning: < 1.0<br>Critical: < 0.5 (過剰空転) |
| **M-RES-04** | **ツール呼出重複率** | `(同一ファイルへの重複読込・無駄なコマンド再実行回数) / (総ツール呼出数) * 100` | **< 5%** | Warning: ≥ 10%<br>Critical: ≥ 20% (探索迷走) |

---

### 2.2 軸2: 開発品質＆手戻り指標 (Quality & Rework Metrics)

成果物の完成度と、フェーズ進行に伴う手戻り・自律修復の効率性を測定する。

| 指標ID | 指標名称 | 定義・算出式 | 目標基準値 | 判定基準 (Warning / Critical) |
| :--- | :--- | :--- | :--- | :--- |
| **M-QLT-01** | **レビュー初回合格率** | `(初回レビュー合格となったレビュー数) / (実施総レビュー数[設計・コード・総合]) * 100` | **≥ 70%** | Warning: < 60%<br>Critical: < 40% (設計・実装の低精度) |
| **M-QLT-02** | **レビュー指摘密度** | `(総指摘件数[ARCH/CODE/SYS]) / (対象コード・設計書 100行あたり)` | **< 2.0 件 / 100行** | Warning: ≥ 3.0<br>Critical: ≥ 5.0 (低品質パッチの頻発) |
| **M-QLT-03** | **スルーテスト初回合格率 & リグレッション率** | ・初回合格率: `(PHASE 6 初回実行でパスしたテスト数) / (全シナリオテスト数) * 100`<br>・リグレッション率: `(改訂ターンで既存機能破壊が発生した件数) / (改訂ターン数) * 100` | 初回: **≥ 80%**<br>リグレッション: **0%** | Warning: 初回 < 70% / リグレッション > 0%<br>Critical: 初回 < 50% / リグレッション ≥ 20% |
| **M-QLT-04** | **自律修復ループ収束ターン数** | `(エラー検知から修復完了までに要したターン数の平均)` (PHASE 5.5, 6, 改訂) | **≤ 2.0 ターン** | Warning: ≥ 3.0 ターン<br>Critical: ≥ 4.0 ターン (上限到達寸前) |

---

### 2.3 軸3: プロセス健全性＆ガバナンス指標 (Process Health & Governance)

テンプレートが定めたルール、二重防御ガードレール、Single Writer原則が厳格に機能しているかを測定する。

| 指標ID | 指標名称 | 定義・算出式 | 目標基準値 | 判定基準 (Warning / Critical) |
| :--- | :--- | :--- | :--- | :--- |
| **M-GOV-01** | **Single Writer原則違反件数** | コンダクター以外のエージェントによる `PROJECT_STATE.md` や状態更新の試行件数 | **0 件 (絶対厳守)** | Warning: N/A<br>Critical: ≥ 1 件 (致命的規約違反) |
| **M-GOV-02** | **ガードレール違反検知数** | 絶対パス混入、未承認ブランチ直接編集、シークレット平文コミットなどの検知件数 | **0 件** | Warning: 1件 (自動検知ブロック)<br>Critical: ≥ 2件 |
| **M-GOV-03** | **フェーズ所要ターン超過率** | `(当該フェーズ実ターン数) / (フェーズ標準基準ターン数)`<br>※ PHASE 3: 4ターン、PHASE 4: 6ターン、PHASE 6: 4ターン等 | **≤ 1.2 倍** | Warning: ≥ 1.5 倍<br>Critical: ≥ 2.0 倍 (スタック発生) |
| **M-GOV-04** | **ドキュメント相互整合性スコア** | `dev-doc-reviewer` によるクロスチェック合格率（整合性欠陥0件で 100%） | **100%** | Warning: < 95%<br>Critical: < 90% (仕様ドリフト) |

## 3. データ収集＆測定アーキテクチャ

エージェントの思考や推論を妨げず、非侵襲的に正確なメトリクスを収集・集計するアーキテクチャを定義する。

### 3.1 測定データ収集アーキテクチャ概要

```
┌────────────────────────────────────────────────────────────────────────┐
│                        開発実行基盤 (Agent Runtime)                    │
│   ・👑 コンダクター (Main)                                             │
│   ・📐 architect / 💻 backend-engineer / 🎨 ui-designer / 🛡️ qa-engineer│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 各ターン完了・ツール実行
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│             【非侵襲メトリクス・インターセプター (Collector)】         │
│   ・トークン消費ログ、ツール呼出履歴、エラー・修復ログを自動フック     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ JSON出力
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│               【メトリクス永続化領域 (metrics/)】                       │
│   ・metrics/turns/turn_{NNN}.json  (ターン詳細生データ)                 │
│   ・metrics/phases/phase_{N}.json   (フェーズ集計データ)                │

```

### 3.2 ディレクトリ構成とデータスキーマ

プロジェクトルート直下に `metrics/` ディレクトリを新設し、メトリクス情報を集約する（正式サマリは `docs/plans/metrics/` にも同期出力される）。

```
metrics/
├── turns/                          # 各ターンの実行スナップショット (自動蓄積)
│   ├── turn_001.json
│   └── ...
├── phases/                         # フェーズ完了ごとの集計サマリ
│   ├── phase_1_summary.json
│   ├── phase_2_summary.json
│   ├── phase_3_summary.json
│   ├── phase_5.5_summary.json
│   ├── phase_6_summary.json
│   └── phase_7_summary.json
├── system_summary.json             # プロジェクト全体の総合メトリクス (docs/plans/metrics/development-metrics-summary.json と同期)
└── system_health_report.md         # 人間可読な総合健全性診断レポート (PHASE 8生成)
```

## 4. 客観的評価基準（スコアリング＆健全性グレード判定）

集計されたメトリクスに基づき、プロジェクト全体の開発健全性を5段階（S / A / B / C / Critical）で判定する。

### 4.1 総合健全性グレード判定マトリクス

| グレード | 判定基準（すべてを満たすこと） | 評価と開発プロセスの状態 |
| :---: | :--- | :--- |
| **Grade S**<br>(最適・模範) | ・Single Writer / ガードレール違反: **0件**<br>・レビュー初回合格率: **≥ 80%**<br>・委譲率: **≥ 60%**<br>・自律修復収束: **平均 ≤ 1.5ターン**<br>・フェーズ超過率: **≤ 1.1倍** | エージェント間の役割分担が極めて優れており、コンテキスト消費も最小限。手戻りがほぼ発生せず、理想的なAI開発が達成された状態。 |
| **Grade A**<br>(健全・良好) | ・Single Writer / ガードレール違反: **0件**<br>・レビュー初回合格率: **≥ 70%**<br>・委譲率: **≥ 50%**<br>・自律修復収束: **平均 ≤ 2.0ターン**<br>・フェーズ超過率: **≤ 1.3倍** | 標準的な高品質開発。軽微な手戻りは自律修復の範囲内で迅速に収束しており、テンプレートの挙動は極めて安定。 |
| **Grade B**<br>(許容・注意) | ・Single Writer違反: **0件**<br>・レビュー初回合格率: **≥ 50%**<br>・自律修復収束: **平均 ≤ 3.0ターン**<br>・フェーズ超過率: **≤ 1.6倍** | 一部フェーズ（コードレビューやテスト）で複数回の手戻りが発生。プロンプト指示の曖昧さやコンテキスト圧迫が軽微に発生。 |
| **Grade C**<br>(要改善) | ・自律修復収束: **平均 > 3.0ターン** または<br>・フェーズ超過率: **> 1.6倍** または<br>・委譲率: **< 35%** (Main過負荷) | 特定フェーズでAIが迷走傾向。自律修復ループの上限到達リスクがあり、プロンプト・スキルの調整が必要。 |
| **Critical**<br>(危険・破綻) | ・**Single Writer原則違反 ≥ 1件** または<br>・各自律修復ループ上限回数（ドキュメント整合性5回、レビュー修正3回、テスト修復5回）到達・タイムアウト多発 または<br>・メインコンテキスト枯渇による強制中断 | テンプレートの基本ガードレールが機能不全に陥った状態。即時の原因究明とテンプレート構造の改修が必須。 |

## 5. テンプレート還元・フィードバック機構（Template Feedback Loop）

測定された客観メトリクスを、個別案件で終わらせず、**「テンプレートシステム自体の自己進化」** へ還元するサイクルを規定する。

```
┌────────────────────────────────────────────────────────────────────────┐
│                   【開発案件ライフサイクル (個別プロジェクト)】          │
│   PHASE 1 〜 7 開発実行 ──► 各フェーズ集計 (`metrics/phases/`)        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ PHASE 8 完了時
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│             【総合健全性診断スキルの実行 (`dev-metrics-report`)】       │
│   ・`metrics/system_summary.json` 自動算出                             │
│   ・目標基準値（閾値）との乖離分析 (Gap Analysis)                     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ ボトルネック・課題の抽出
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│             【テンプレート還元プロポーザル (`TEMPLATE_PROMOTIONS.md`)】│
│   ・プロンプト改善案: 迷走したサブエージェントの制約明確化             │
│   ・スキル改善案: 修復ターンの長引いたテスト・レビュー手順の自動化     │
│   ・規約改善案: フェーズゲート判定の厳格化 / 緩和基準の調整           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 👤 ユーザー承認
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│             【テンプレートリポジトリへの反映 (Template Release)】       │
│   ・`.agents/plugins/system-dev-pipeline/` 配下の改訂反映              │
│   ・次期プロジェクトへの恒久展開                                       │
└────────────────────────────────────────────────────────────────────────┘
```

### 5.1 メトリクス異常からテンプレート改善への変換ルール

集計されたメトリクスの弱点傾向に応じて、テンプレートの改修対象を自動マッピングする。

| 観測されたメトリクス異常 | 想定されるテンプレート弱点 | テンプレートへの還元アクション (Feedback Action) |
| :--- | :--- | :--- |
| **委譲率 M-RES-02 低下** (< 40%)<br>メインToken M-RES-01 逼迫 | コンダクターがサブエージェントに委譲せず自身で実装・調査を抱え込んでいる | `conductor.md`（独立プロンプト）の委譲トリガーを強化し、抱え込み禁止ガードレールを追加する。 |
| **設計レビュー合格率 M-QLT-01 低下** (< 60%)<br>ARCH_YAGNI 指摘が多発 | `architect` が案件規模（プロファイル）を無視して過剰な分散設計を生成している | `architect.md` にプロファイル別（Profile A〜D）の複雑度上限規約を追記・強化する。 |
| **コードレビュー指摘密度 M-QLT-02 悪化**<br>重複コード・型不整合が多発 | `ui-designer` または BE実装スキルがDRY原則や型共通化を怠っている | `dev-phase4-env-build` および `ui-designer.md` に、共通ユーティリティ先行定義の強制ルールを付与。 |
| **テスト自律修復ターン M-QLT-04 悪化** (≥ 3ターン) | テストエラーの原因分析が不十分で、当てずっぽうなパッチを反復している | `dev-phase6-testing` の修復ループに、エラーログのスタックトレース詳細分析フェーズを義務付ける。 |
| **Single Writer 違反 M-GOV-01 発生** (≥ 1件) | サブエージェントが自律的に `PROJECT_STATE.md` を書き換えようとした | 全サブエージェントプロンプトの禁止事項（Tool Blacklist / ガードレール）を最上位ブロックへ昇格・再強化。 |

### 5.2 WikiSkill（Step 2）との連携インターフェース

Step 3 のメトリクス分析によって検知された「テンプレート改善課題」は、Step 2（WikiSkill）の資産昇格機構と以下のようにシームレスに連携する：

1. **メトリクス異常の検知**: `dev-metrics-collector`（集計・診断）が閾値逸脱（Warning / Critical）を検知。
2. **課題チケット化**: 検知された事象が `metrics/system_health_report.md` に課題として記録され、同時に `./TEMPLATE_PROMOTIONS.md` の「テンプレート基盤改善セクション」へ自動追記される。
3. **Skill Proposer による改訂パッチ作成**: `wiki-proposer` が該当スキルまたはプロンプトの改訂パッチを自動起草。
4. **複合検証ゲート判定**: 🛡️ `qa-engineer`（複合検証ゲート）により、改訂後のテンプレートが既存の整合性・テストを満たすか検証。
5. **正式昇格**: ユーザーの明示的承認を経て、`EXECUTION_MODE` に応じたルーティングを実行（`GLOBAL_PLUGIN` 時は `./promotions/*.patch` 出力案内、`LOCAL_STANDALONE` 時はローカルの `.agents/plugins/system-dev-pipeline/` へ直接コミット）。

## 6. パイプライン各フェーズへの統合運用手順

本定量測定システムは、既存の `AI駆動システム開発フェーズ定義書V2.1.md` の各フェーズに以下の通り統合される。

```
PHASE 1: 準備 ──► metrics/ ディレクトリの初期化 (`dev-phase1-setup`)
   │
PHASE 2〜7: 開発実行 ──► 各フェーズ完了ゲートで `metrics/phases/phase_{N}_summary.json` 自動生成
   │
PHASE 8: リリース・改訂移行
   ├─► 1. `dev-metrics-collector` 実行（プロジェクト総合健全性診断 & Grade判定）
   ├─► 2. `system_health_report.md` 生成 & ユーザー提示
   ├─► 3. テンプレート改善案を `TEMPLATE_PROMOTIONS.md` へ反映
   └─► 4. ユーザー承認を経て次期テンプレートへ還元
```

### 6.1 新設・改訂スキル一覧
- **`dev-metrics-collector` (新規 / メトリクス一元担当)**:
  - ターン終了時・ツール呼び出し時の非侵襲記録、`metrics/phases/` のフェーズ集計サマリ出力、総合健全性スコア（Grade S〜Critical）の判定、ボトルネック分析、および `system_health_report.md` / `docs/plans/metrics/development-metrics-summary.json` の生成までを一元的に担う。
- **`dev-phase1-setup` (改訂)**:
  - プロジェクト初期化時に `metrics/`（`turns/`, `phases/`）ディレクトリ構造を自動作成。
- **`dev-phase8-rules` (改訂)**:
  - PHASE 8 完了処理において、`dev-metrics-collector` による総合診断レポート出力とテンプレート還元提案の出力を標準手順として組み込み。
