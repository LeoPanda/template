## 1. はじめに

### 1.1 背景と問題意識
AI駆動開発ライフサイクル V2.0 においては、[エージェント間知見蓄積運用基準書.md](../V2.0/エージェント間知見蓄積運用基準書.md) を通じて「プロジェクト固有知見（Tier 1）」と「全体共通知見（Tier 2）」の二層分離、および Actionable Knowledge（状況・現象・根本原因・処方箋）の蓄積フローが確立された。

一方、V2.1 において導入された [WikiSkill統合設計書.md](./WikiSkill統合設計書.md) では、試行錯誤や失敗知見を破棄しない「永続 Wiki 層（`wiki/patterns/`, `wiki/logs.md`）」および「推論とWikiの分離原則（Context Isolation）」が新たに組み込まれた。

しかし、この二つの仕組みを単純に並立させた場合、以下の **構造的な重複と運用の混乱** が生じる：
1. **知見の二重管理と行き場（正本）の曖昧さ**:
   - プロジェクト固有のエラーや設計判断（Tier 1）が `wiki/patterns/` にも `docs/` や `PROJECT_STATE.md` にも記録され、どれが最新の正本かが不明瞭になる。
2. **Context Isolation と Tier 1 知見利用の矛盾**:
   - 「推論エージェントに Wiki を見せない（Context Isolation）」原則を機械的に適用すると、推論エージェント（`conductor`, `architect`, `backend-engineer`, `ui-designer`）が当該プロジェクト固有の業務ルールや例外制約（Tier 1）を参照できず、実装・改訂で同一の業務的ミスを犯す。
3. **評価・フィードバックタイミングの混同**:
   - 「どの知見を、どのフェーズで、誰が評価し、どこへいつ還元すべきか」のライフサイクルが整理されていないと、不要な共通スキル化やドキュメントへの反映漏れが発生する。

### 1.2 目的
本文書は、**Tier 1（プロジェクト固有知見）** と **Tier 2（全体共通知見）** の責務境界を WikiSkill 永続層と統合・再定義し、**「どの知見を、どのタイミングで評価し、どこへフィードバック（正本化）していくか」** の全ライフサイクルを明確化することを目的とする。

## 2. 知見の二層分離（Tier 1 / Tier 2）と WikiSkill 永続層の棲み分け

### 2.1 全体構造マッピング

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│               エージェント試行錯誤・手戻り・障害 (Raw Traces / Logs)                     │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ 根本原因分析 (RCA / Wiki Maintainer)
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        【永続 Wiki 層 (wiki/patterns/)】                               │
│      ※ 決してロールバックされない一次診断ナレッジベース (Catastrophic Forgetting防止) │
├───────────────────────────────────────────┬────────────────────────────────────────────┤
│   【Tier 1: プロジェクト固有知見 (Local)】 │   【Tier 2: 全体共通知見 (Universal)】       │
│   ・格納: wiki/patterns/local/            │   ・格納: wiki/patterns/universal/         │
│   ・内容: 業務ルール、独自画面、個別API   │   ・内容: FW挙動、Docker、型安全、共通手順 │
└─────────────────────┬─────────────────────┴─────────────────────┬──────────────────────┘
                      │                                           │
         [即時〜フェーズ完了時フィードバック]                 [マイルストーン完了時自己進化]
                      │ (ドキュメント逆同期)                       │ (複合検証ゲート・昇格)
                      ▼                                           ▼
┌───────────────────────────────────────────┐ ┌──────────────────────────────────────────┐
│   【Tier 1 永続正本 (Specification)】     │ │   【Tier 2 永続正本 (Reusable Assets)】    │
│   ・docs/ (要件定義書・基本設計書・画面)  │ │   ・.agents/plugins/system-dev-pipeline/   │
│   ・PROJECT_STATE.md (決定・未決事項)     │ │     ├ skills/SKILL.md (PURPOSE.md 連携)    │
│                                           │ │     ├ rules/dev-process-standards.md       │
│   ★ 推論エージェントの直接参照対象        │ │     └ agents/<role>.md, templates/         │
│   (Context Isolationを維持して仕様消費)   │ │   ★ 蒸留・検証済み実行手順として消費       │
└───────────────────────────────────────────┘ └──────────────────────────────────────────┘
```

### 2.2 二層の棲み分け詳細

| 項目 | Tier 1: プロジェクト固有知見 (Local) | Tier 2: 全体共通知見 (Universal) |
| :--- | :--- | :--- |
| **定義と対象** | 当該プロジェクトの業務ドメイン、特定顧客要件、個別画面仕様、個別DB制約、特定外部API連携に起因する知見。 | 開発言語、ライブラリ、FW、Docker、GCP、Git運用、リンター、エージェント共通行動規範に起因する知見。 |
| **Wiki層での扱い** | `wiki/patterns/local/PAT-LOC-xxx.md`<br>（障害診断・手戻り履歴としての永続一次記録） | `wiki/patterns/universal/PAT-{CAT}-xxx.md`<br>（自己進化ループの入力資産） |
| **最終到達先 (正本)** | **`docs/` (各種設計書・仕様書)**<br>および **`./PROJECT_STATE.md`**<br>※ グローバル配置は厳禁（越境汚染防止） | **プラグイン資産 (`skills/`, `rules/`, `templates/`)**<br>・モード A (`GLOBAL_PLUGIN`): `./promotions/*.patch` 経由で昇格<br>・モード B (`LOCAL_STANDALONE`): ローカル `.agents/...` へ直接反映 |
| **推論エージェントへの提供方法** | **「仕様・設計ドキュメントの最新化」** により提供。<br>※ 推論エージェントは `docs/` を読むため、Wikiを直接見せる必要がなく Context Isolation が完全に成立する。 | **「蒸留・検証された `SKILL.md` / `rules/`」** により提供。<br>※ 雑多な事例ではなく、洗練された標準手順・ガードレールとして適用。 |
| **共通スキルへの昇格** | **原則禁止 (Strict Prohibition)**<br>個別業務仕様がテンプレートに混入することを防ぐ。 | **複合検証ゲート合格後に昇格**<br>複合検証ゲート（Gating）とユーザー承認を経て反映（モード別ルーティング）。 |

## 3. 知見の評価・フィードバック タイミング マトリクス

知見を「いつ評価し」「どこへフィードバック（反映）するか」の完全なタイムラインを規定する。

```
【開発中 (PHASE 3, 5, 5.5, 6 / 改訂ターン)】
  障害・エラー発生 ──► Wiki Maintainer が wiki/patterns/ へ即時記録 (RCA)
                               │
                               ├─► [Tier 1] ──► 各フェーズ完了ゲートで評価 (Doc Review / ユーザー確認)
                               │                ──► docs/ 設計書・仕様書へ即時逆同期 (正本化)
                               │
【マイルストーン完了時 (PHASE 8 / 改訂完了)】
                               └─► [Tier 2] ──► 昇格レビュー & 複合検証ゲート (Gating) で評価
                                                ──► skills/SKILL.md, rules/ へ確定昇格 (自己進化)
```

### 3.1 評価・フィードバック詳細マトリクス

| 評価フェーズ / タイミング | 対象知見 (Tier) | 一次記録内容 | 評価者・評価手段 | フィードバック先 (正本への反映) | 完了ゲート条件 |
| :--- | :---: | :--- | :--- | :--- | :--- |
| **PHASE 3 完了時**<br>(設計完了ゲート) | **Tier 1**<br>(設計判断) | `wiki/patterns/local/`<br>設計レビュー是正内容 | ・`dev-doc-reviewer`<br>・🛡️ 基本設計レビュー<br>・👤 ユーザー承認 | `docs/要件定義書.md`<br>`docs/基本設計書.md`<br>`PROJECT_STATE.md` | ドキュメント間の不整合0件、未解決設計課題0件。 |
| **PHASE 5 完了時**<br>(ウォークスルー後) | **Tier 1**<br>(UI/仕様齟齬) | ウォークスルー不具合修正ログ | ・👤 ユーザー操作検証<br>・📐 architect 同期 | `docs/画面仕様書.md`<br>`docs/バックエンドAPI仕様書.md` | 最新コードの挙動と仕様書が100%一致（逆同期完了）。 |
| **PHASE 5.5 完了時**<br>(コード品質レビュー) | **Tier 1 & 2**<br>(コード品質) | 重複コード、型アンチパターン | ・🛡️ `dev-review-code`<br>・コンテナ再ビルド疎通 | (Tier 1) 実装コード・共通関数<br>(Tier 2) `wiki/patterns/universal/` | 判定 CLEAN、環境ビルド成功。 |
| **PHASE 6 完了時**<br>(スルーテスト完了) | **Tier 1 & 2**<br>(テスト修復) | 自動修復（Auto-Healing）ログ、テストタイムアウト原因 | ・🛡️ `dev-phase6-testing`<br>・全シナリオ100%パス | (Tier 1) `docs/plans/シナリオテスト計画書.md`<br>(Tier 2) `wiki/patterns/universal/` | 全テストパス、未解決エラー0件。 |

## 4. フォーマット仕様の統合（Tier 1 / Tier 2 共通スキーマ）

知見を記録する際は、V2.0 の Actionable Knowledge と V2.1 WikiSkill を統合した以下の統一スキーマ（Markdown）を使用する。

```markdown
# [PAT-{TIER}-{通番}]: [簡潔なタイトル] (例: PAT-LOC-001: 会員ランク別割引率計算の端数処理)

- **Pattern ID**: PAT-LOC-001 (Tier 1 の場合は PAT-LOC-xxx, Tier 2 の場合は PAT-{CAT}-xxx)
- **作成日**: YYYY-MM-DD
- **更新日**: YYYY-MM-DD
- **知見スコープ**: [Tier 1: プロジェクト固有 (Local) / Tier 2: テンプレート共通 (Universal)]
- **カテゴリ**: [ARCH / CODE / TEST / ENV / SEC / BIZ]
- **ステータス**: [Active / Synced-to-Docs / Promoted-to-Skill / Archived]
- **関連ロール**: [👑 conductor / 📐 architect / 💻 backend-engineer / 🎨 ui-designer / 🛡️ qa-engineer / 共通]

## 1. 発生状況 (Context & Condition)
- どのような業務ユースケース、画面、フェーズ、または技術環境で発生したか。

## 2. 現象・落とし穴 (Problem / Trap)
- どのような不具合、テスト失敗、認識齟齬、またはエラーが発生したか。

## 3. 根本原因 (Root Cause)
- なぜその問題が生じたか（業務仕様の曖昧さ、ライブラリの癖、前提条件の欠如）。

## 4. 処方箋・推奨ルール (Prescription / Rule)
- どのように修正・解決したか。次回からエージェントはどう行動・記述すべきか。

## 5. 正本還元先とフィードバック履歴 (Lineage & Destination)
- **一次記録元**: PHASE 5 ウォークスルーデバッグログ
- **正本反映先**:
  - (Tier 1 の場合) `docs/ビジネスロジック仕様書.md` §3.2, `./PROJECT_STATE.md`
  - (Tier 2 の場合) `.agents/plugins/system-dev-pipeline/skills/dev-phase4-env-build/SKILL.md`
- **昇格 / 同期確認日**: YYYY-MM-DD (承認者: 👤 ユーザー / 検証結果: Gate PASS)
```

## 5. エージェントの役割と知見フィードバック手順

### 5.1 サブエージェント返却サマリ（知見の吸い上げ）
各サブエージェント（`architect`, `backend-engineer`, `ui-designer`, `qa-engineer`）は、作業完了時に以下の形式で知見をコンダクターへ報告する。

```markdown
## 作業完了サマリ
- **担当エージェント**: [architect / backend-engineer / ui-designer / qa-engineer]
- **実施フェーズ / タスク**: [例: PHASE 5.5 コード品質レビュー]
- **ステータス**: [SUCCESS / PENDING_USER_INPUT / FAILED]
- **生成・更新ファイル一覧**:
  - `path/to/file`
- **💡 獲得した知見・落とし穴 (Lessons Learned)**:
  - **事象**: Next.js App Router 内でクライアントコンポーネントの import パスに循環参照が発生。
  - **根本原因**: 共通型定義をコンポーネントファイル側から逆 import していたため。
  - **処方箋**: 型定義は必ず `src/types/` 配下に分離し、コンポーネントからは型定義のみを参照する。
  - **推奨スコープ**: [Tier 1: プロジェクト固有 / Tier 2: テンプレート共通]
```

### 5.2 👑 コンダクターによる仕分けと反映ワークフロー
1. **仕分け判定**:
   - サマリの知見が「業務要件・個別画面」なら **Tier 1**、「汎用FW・インフラ・手順」なら **Tier 2** に分類。
2. **一次記録 (Wiki Maintainer 連携)**:
   - `qa-engineer` と連携し、`wiki/patterns/` へパターンファイルを生成（スキル: `wiki-maintainer`）。
3. **Tier 1 の即時フィードバック（ドキュメント正本化）**:
   - 当該フェーズの成果物（設計書や画面仕様書）へ反映させ、`PROJECT_STATE.md` を更新。
   - 次フェーズへ進む前に、推論エージェントが参照できる「正本文書」として定着させる。
4. **Tier 2 の集約と昇格（マイルストーン時）**:
   - 知見実体は `wiki/patterns/universal/` に永続登録され、同時にユーザーが確認・承認できるよう `./TEMPLATE_PROMOTIONS.md`（知見昇格レビュー用提示サマリ）へ集約・提示する。
   - PHASE 8 または改訂完了時にユーザー承認を経て、`wiki-proposer` によるスキル改修案立案 ＋ 複合検証ゲート（Gating）を実行して正式昇格する。

## 6. 知見の肥大化・陳腐化防止（メンテナンスと枝刈り）

### 6.1 Tier 1 のメンテナンス
- **ドキュメント正本化完了後の扱い**:
  - `docs/` 設計書に正式反映された Tier 1 パターンは、ステータスを `Synced-to-Docs` に変更。
  - プロジェクト固有のナレッジは `docs/` 側を正として保守し、Wikiパターン側は「解決済みトラブルアーカイブ」として参照用に維持する。

### 6.2 Tier 2 のメンテナンス (Wiki Compactor)
- **統合 (Consolidation)**:
  - 類似のエラーパターンが複数発生した場合、`wiki-compactor` により上位の共通パターンへ統合。
- **アーカイブ (Archiving)**:
  - テンプレートの `SKILL.md` に昇格され、5サイクル以上リグレッションのないパターンは `wiki/archive/patterns/` へ退避。
  - これにより、Skill Proposer のコンテキストトークン消費を常に最小限に抑える。
