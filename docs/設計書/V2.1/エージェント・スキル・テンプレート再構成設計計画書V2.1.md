## 1. はじめに

### 1.1 目的と背景
AI駆動システム開発ライフサイクル V2.0 においては、コンダクター（Main）、設計（architect）、UI（ui-designer）、QA（qa-engineer）の協調体制、Single Writer原則、二重防御ガードレールによる自動開発・改訂プロセスを確立した。

一方、先行検討資料 [V2.1へ向けた検討課題.md](../検討課題/V2.1/V2.1へ向けた検討課題.md) および [V2.1検討方針書.md](./V2.1検討方針書.md) において策定された **3大重点実装テーマ**（レビューシステム、WikiSkill型永続ナレッジ自己進化ループ、定量測定・フィードバック機構）を具現化するため、現行のサブエージェント体系、スキル群、およびテンプレート群を再構成する必要がある。

### 1.2 本計画書のスコープ
本文書は、以下を規定する：
1. **エージェント体制の再構成設計**: 各エージェントの役割、配置、権限、および新設エージェント（`conductor.md` 独立化、`backend-engineer` の新設・委譲方針）。
2. **スキルの再構成設計**: 3大レビュースキル、WikiSkill関連スキル、定量メトリクス集計スキルの新設と、既存フェーズスキルの改修仕様。
3. **テンプレートおよびルールの再構成設計**: `PROJECT_STATE.md`、`TEMPLATE_PROMOTIONS.md`、共通規約（`dev-process-standards.md`）の更新。
4. **段階的移行・改変作業計画（ロードマップ）**: ユーザーによる計画承認後に実施する具体的な変更ファイル一覧と実行手順。

> [!IMPORTANT]
> **改変保留ガードレール**:  
> 本計画書に記載された `.agents/` 配下のファイル作成・変更は、ユーザーによる本計画書の確認・明示的承認が得られるまで **一切実行しない**。

### 2.3 バックエンド専門エージェント (`backend-engineer`) の新設設計

#### 新設の理由
V2.0 においては PHASE 4 のバックエンド実装をコンダクター自身が担当していた。しかし、APIエンドポイントの増加や複雑なドメインロジックの実装に伴い、コンダクターのコンテキストが急速に枯渇し、その後のウォークスルーやフェーズ進行で文脈喪失やレスポンス劣化を招くリスクが実案件で指摘された。
したがって、`backend-engineer` を独立サブエージェントとして新設し、コード実装作業をコンテキスト隔離環境へ委譲する。

#### 定義仕様概要 (`agents/backend-engineer.md`)
```yaml
---
name: backend-engineer
description: "バックエンドAPI、データベース接続・マイグレーション、ビジネスロジック実装を担当するバックエンド実装スペシャリスト"
enable_write_tools: true
enable_subagent_tools: false
enable_mcp_tools: false
default_model: pro
default_workspace: inherit
---
```
- **許可コマンド**: 言語ランタイムの実行・テスト・フォーマット（`uv run`, `python`, `npm test`, `pytest`, `ruff check` 等）
- **禁止事項**: Git操作（コミット/プッシュ/ブランチ操作）、本番デプロイ、DB強制上書きコマンド（`dev-db-overwrite`）

### 2.4 👑 コンダクター専用プロンプト (`conductor.md`) の独立化設計

#### 独立化の理由
これまでコンダクターの動作規範は `rules/dev-process-standards.md` や `GEMINI.md` に分散して記述されていた。
コンダクターが果たすべき中核責務（①進行管理とオーケストレーション、②状態管理の Single Writer、③承認ゲート提示、④動的フォールバック自律実行、⑤WikiSkill自己進化統括）を1つの明示的な定義ファイル `.agents/plugins/system-dev-pipeline/agents/conductor.md` に集約し、プロジェクト初期化時およびセッション開始時に参照可能な標準規範として確立する。

### 3.2 新設スキルの詳細仕様

#### 1. `dev-review-arch` (基本設計レビュー)
- **目的**: PHASE 3 完了直前において、定常的観点（データ保全、クラッシュ防止、過剰設計抑止/YAGNI）と展開プロファイル別観点（SPOF、OS依存、ローカル完結等）を監査する。
- **入力**: `docs/要件定義書.md`, `docs/技術要件定義書.md`, `docs/テーブルスキーマ定義書.md`, `docs/ビジネスロジック仕様書.md`, `docs/画面仕様書.md`
- **出力**: `docs/plans/基本設計レビュー結果報告書.md`（判定: PASS / CONDITIONAL PASS / REJECT、指摘事項一覧）

#### 2. `dev-review-code` (コード品質・整合性レビュー)
- **目的**: PHASE 5.5 において、DRY原則、単一責任、デッドコード排除、型安全性、ファイル行数制限（400行以下）を監査し、リファクタリングDiffを提示する。
- **入力**: `src/` 配下のフロントエンド・バックエンド全ソースコード
- **出力**: `docs/plans/コード品質レビュー及びリファクタリング提案書.md`（判定: CLEAN / REFACTOR RECOMMENDED / BLOCKED、Unified Diff）

#### 3. `dev-review-system` (システム総合レビュー)
- **目的**: PHASE 7 本番リリース直前において、稼働環境耐性、平文シークレットの排除、IAM/IAP認可ポリシー、ロールバック計画の完全性を監査する。
- **入力**: 本番適用作業手順書、Dockerfile、環境変数設定、デプロイ構成
- **出力**: `docs/plans/システム総合レビュー結果報告書.md`（判定: RELEASE APPROVED / RELEASE BLOCKED）

#### 4. `wiki-maintainer` (Wiki知見永続化)
- **目的**: レビュー不合格、テスト失敗、自律修復発生時に、コンテキストが新鮮な状態で根本原因（RCA）を抽出し、カレントプロジェクト配下の `wiki/patterns/` に永続登録する。
- **入力**: テストログ、レビュー指摘、エラーメッセージ
- **出力**: `./wiki/patterns/{local,universal}/PAT-*.md`（ローカル・ファースト蓄積、越境汚染防止）

#### 5. `dev-metrics-collector` (定量測定・メトリクス集計・レポート生成)
- **目的**: 各ターン・フェーズおよび改訂ターン完了時に、トークン効率、品質・手戻り件数、コード健全性、リードタイムを集計し、総合健全性診断レポートとテンプレート還元データを出力する。
- **出力**: `metrics/`（一次集計領域。`turns/` は `.gitignore` 除外）、`docs/plans/metrics/development-metrics-summary.json`（全体統合サマリ）、`metrics/system_health_report.md`（PHASE 8 総合診断レポート）

## 4. テンプレートおよびルールの再構成設計

### 4.1 `PROJECT_STATE.md` テンプレートの改訂 (V2.1)
- **動作モード・テンプレートソース記録欄**の追加 (`EXECUTION_MODE: [GLOBAL_PLUGIN | LOCAL_STANDALONE]`, `TEMPLATE_SOURCE`)。
- **展開プロファイル記録欄**の追加（Profile A〜D）。
- **3大レビューゲート欄**の追加:
  - `[ ] PHASE 3 内完了ゲート: 基本設計レビュー (dev-review-arch)`
  - `[ ] PHASE 5.5 独立フェーズ: コード品質レビューとリファクタリング (dev-review-code)`
  - `[ ] PHASE 7 内完了ゲート: システム総合レビュー (dev-review-system)`
- **WikiSkill & ナレッジ昇格ステータス**の追加（Tier 1/2 パターン件数、自己進化サイクル成否）。
- **定量メトリクス集計欄**の追加（一次集計領域 `metrics/`、全体統合サマリ `docs/plans/metrics/`）。

### 4.2 `TEMPLATE_PROMOTIONS.md` の役割明確化
- **位置づけ**: 永続知見の実体ファイルは `./wiki/patterns/universal/` に格納されるが、`./TEMPLATE_PROMOTIONS.md` は PHASE 8 完了時にユーザーが昇格可否を判断・承認するための **「知見昇格レビュー用提示サマリ」** として位置付けを明確化する。
- **昇格先ルーティング**: `EXECUTION_MODE` に応じ、`GLOBAL_PLUGIN` 時は `./promotions/*.patch` エクスポート案内、`LOCAL_STANDALONE` 時はローカルプラグイン資産直接更新を行う仕様を明記。

### 4.3 `rules/dev-process-standards.md` の改訂
- コンダクター基本動作規範の刷新（Single Writer、委譲プロトコル）。
- 3大レビュー必須通過規約（合否判定を満たさないフェーズ進行の禁止）。
- WikiSkill Context Isolation 原則（通常推論エージェントへの生Wiki注入禁止）。
- 二重防御ガードレール（サブエージェントの `run_command` ブロック）。
