## 1. 目的と位置付け

本文書は、Antigravity環境におけるAI駆動システム開発ライフサイクル（新規開発 PHASE 1〜8、および本番リリース後の継続的システム改訂プロセス）において、**メインエージェント（コンダクター）、4つの専門サブエージェント（architect, backend-engineer, ui-designer, qa-engineer）、決定論的スキル群、およびユーザー（開発者/PO）** が協調して開発・改訂を完遂するためのフェーズ定義と役割分担を規定するものである。

V2.2 において導入された **「Shift-Left（要件定義・基本設計・初期スケルトン展開段階からの堅牢な標準パターンの前倒し組み込み）」** および **「2層構造システムプロファイル体系」** に加え、V2.3 では複数プロジェクト・複数環境での継続的な自己進化を可能にする **「Central Knowledge Hub・3段階意味的整合性監査・Immutable Core / Local Overlay 二層プラグイン機構」** を統合する：

1. **2層構造システムプロファイル体系と Shift-Left 基盤**:
   - **第1層: 定常的コア設計規範（Universal Core Specifications）**: 全システム共通の8大普遍的規約（フロント責務分離・250行制限、型定義自動同期、環境変数厳格検証、統一UTC/JST、自動CI、モック制御ハイブリッド、画面グランドデザイン、外部API二重キャッシュ＆可観測性）。
   - **第2層: 可変的システム展開プロファイル（Deployment Profiles）**: PHASE 2で選定され、PHASE 1〜7の設計・実装・監査を一気通貫で決定する適合プロファイル（Profile A〜D）。
   - **ハイブリッド方式（静的スケルトン vs 可変ドメイン生成）**: 基盤コード（Alembic環境、`entrypoint.sh`、CI、認証ミドルウェア、MSWモック基盤等）を `skeletons/` として初期展開し、エージェントは業務ドメイン生成に専念。
2. **V2.3 新知見フィードバック機構（Central Knowledge Hub & 2層プラグインモデル）**:
   - **Knowledge Inbox ＆ 標準化知見原票（1-A / 1-B / 1-C）**: 行番号依存の `.patch` 出力を廃止し、セマンティック・アンカー付きの自己完結 Markdown 原票（`CLAIM-*.md`）を環境共通の `~/.gemini/knowledge-hub/inbox/` へ集約。ルール本文（State）から履歴ID（Lineage）を完全分離。
   - **3段階の意味的整合性監査と絶対行数バジェット（2-A / 2-B）**: PHASE 8 の複合検証ゲートを「プロンプト・知見専用の4大関門（Core Invariants 監査 / 4分類矛盾監査 / 過剰適合排除 / 履歴IDゼロ＆絶対行数バジェット監査）」へ刷新。
   - **Immutable Core ＋ Local Overlay ＆ Upgrade Reconciler（3-A / 3-B / 3-C）**: 個別案件の PHASE 8 では公式プラグイン（Immutable Core）を一切書き換えず、`~/.gemini/knowledge-hub/overlay/LOCAL_FEEDBACK_RULES.md` をクリーン再生成して次案件から即時有効化。新バージョン配布時は `Upgrade Reconciler` が `PIPELINE_MANIFEST.json` / `FEEDBACK_LEDGER.md` と照合して安全にマイグレーションを実行。

## 2. 採用された基本方針（V2.3 決定事項）

| 検討項目 | 採択方針 | 詳細内容 |
| :--- | :--- | :--- |
| **1. 開発思想** | **Shift-Left（品質・標準の前倒し組み込み）** | 事後レビューによる手戻りを防ぐため、PHASE 1（スケルトン展開）、PHASE 2（プロファイル選定）、PHASE 3（基本設計）から標準パターンを組み込む。 |
| **2. システムプロファイル** | **2層構造プロファイル体系** | 「第1層: 定常的コア設計規範（普遍的8大規約）」と「第2層: 展開プロファイル（Profile A〜D）」に構造化し、初期スケルトンからレビューゲートまで一気通貫でバインドする。 |
| **3. 基盤実装方式** | **ハイブリッド方式（静的スケルトン ＋ 可変ドメイン生成）** | `skeletons/` から検証済み基盤（Alembic, entrypoint.sh, CI, 共通フック等）を展開し、エージェントはドメイン設計・ロジック実装に専念する。 |
| **4. 画面デザイン** | **グランドデザイン全面標準採用** | `doc_samples/グランドデザイン/` の規格を標準化。セマンティックカラー（HEX/px併記）、4px/8pxグリッド、ウィンドウ形態選定基準、画面仕様書新規格を強制適用。 |
| **5. フロントエンド設計** | **責務分離 & 1ファイル最大250行制限** | God Component化を根絶するため、`components/ui/`, `components/[domain]/`, `hooks/`, `services/`, `types/` に物理分割し、250行超過をレビューでREJECTする。 |
| **6. モックアップ制御** | **環境変数切替 (案C) ＋ 直書きモック禁止 (案A)** | `.env` の `VITE_ENABLE_MOCK` で実APIとモックを透過切替。コンポーネント内のダミーデータハードコードは原則禁止とし、MSW等で制御する。 |
| **7. データベース運用** | **Alembic標準統合 & SQLite WAL運用** | 生SQL手動DDLを完全排除。起動シーケンス（`entrypoint.sh`）で Litestreamリストア ➔ Alembicマイグレーション ➔ アプリ起動を確定実行する。 |
| **8. セキュリティ・認可** | **IAP JWT署名二重検証** | 前段プロキシ依存による認証バイパスを防止するため、FastAPIバックエンド側でJWT署名を検証し、モックの安全なローカル切替を実現する。 |
| **9. 型同期 & 自動化** | **OpenAPI ➔ TypeScript Codegen** | バックエンドスキーマからTypeScript型定義をワンコマンド自動生成し、CIで型安全性を機械的検証する。 |
| **10. 状態管理・レビュー** | **Single Writer ＋ 3大レビュー品質ゲート** | コンダクターが `PROJECT_STATE.md` を一元更新。PHASE 3（基本設計）、PHASE 5.5（コード品質）、PHASE 7（システム総合）の合格とユーザー明示承認を必須とする。 |
| **11. 知見還流・自己進化** | **Central Knowledge Hub ＋ Immutable Core / Local Overlay** | `.patch` と個別 `PURPOSE.md` を廃止。Tier 2 知見は標準原票（`CLAIM-*.md`）として `~/.gemini/knowledge-hub/inbox/` へ集約し、3段階意味的監査と `ask_question` 承認を経て `overlay/LOCAL_FEEDBACK_RULES.md` へ即時クリーン再生成する。 |

### 3.1 アクター詳細

1. **👤 ユーザー (`user` / 人間)**:
   - システム要求提示、展開プロファイル選定確認、レビュー結果確認、各ゲートの明示的承認、ウォークスルーでのUI操作検証、本番リリース最終判断、および Knowledge Hub 知見反映・矛盾裁定の承認（`ask_question` モーダル）。
2. **👑 プロジェクトコンダクター (`conductor` / メインエージェント / Model: `pro` または `inherit`)**:
   - 全体進行管理、`PROJECT_STATE.md` の一元更新（Single Writer）、PHASE 1 でのスケルトン展開＆Knowledge Hub 未処理原票検知、Docker/環境構築統括、サブエージェント委譲、標準コマンドシーケンス実行、外部CLI実行時の非対話フラグ（`--quiet` 等）とタイムアウト監視の徹底、PHASE 8 での標準化知見原票（`CLAIM-*.md`）起案・投函・Overlay 再生成統括、Git/デプロイスキル呼び出し。
3. **📐 設計・立案スペシャリスト (`architect` / サブエージェント / Model: `pro`)**:
   - 要件定義書（プロファイル選定・チェックリスト包含）作成、基本設計書3種（技術・スキーマ・ロジック）作成、外部APIキャッシュ・モック制御方針設計、Alembic前提スキーマ設計、レビュー指摘の設計反映、API仕様書同期。※ `run_command` は厳禁（INV-02）。
4. **💻 バックエンドエンジニア (`backend-engineer` / サブエージェント / Model: `pro`)**:
   - バックエンドAPI、SQLAlchemyモデル、Alembicマイグレーション生成・適用、ビジネスロジック、IAP JWT署名検証ミドルウェア、内部監視エンドポイントの実装。標準コマンドシーケンスの遵守。※ 生SQL禁止（INV-05）、Git/デプロイ/DB上書きは厳禁（INV-02）。
5. **🎨 UI/UXデザイナー (`ui-designer` / サブエージェント / Model: `flash` または `pro`)**:
   - `画面仕様書.md`（グランドデザイン新規格準拠）作成、フロントエンド画面・UI部品実装。**1ファイル最大250行制限の遵守（INV-03）**、`hooks/` や `services/` への責務分離、**コンポーネント内直書きモックの原則禁止（INV-04）**、MSWモックハンドラー構築。※ Git/デプロイは厳禁。
6. **🛡️ 品質・監査 & QA (`qa-engineer` / サブエージェント / Model: `pro`)**:
   - 基本設計レビュー（`dev-review-arch`）、コード品質レビュー（`dev-review-code`: 250行制限、直書きモック排除、型安全）、システム総合レビュー（`dev-review-system`: 本番モックOFF、IAP検証、Alembic起動検証）、自動テストループ（`dev-phase6-testing`）、Wiki Maintainer（RCA記録）、および **Semantic Auditor（PHASE 8 新・複合検証ゲート：3段階意味的整合性監査）**。※ コード直接改変・Git/デプロイは厳禁（INV-02）。

### 4.1 PHASE 1: プロジェクトの準備 & スケルトン展開 & Knowledge Hub 検知
- **目的**: ディレクトリ構成、`.env`、ドキュメント雛形、永続ナレッジ領域（`./wiki/`）、メトリクス領域（`./metrics/`）、静的スケルトン基盤（`skeletons/`）を初期配置するとともに、**PC環境共通の `~/.gemini/knowledge-hub/` を初期化・スキャンし、未処理の知見原票があれば開発開始前に決裁・Overlay反映できるようにする**。
- **主担当**: 👑 コンダクター（スキル: `dev-phase1-setup`）
- **主要作業**:
  1. `~/.gemini/knowledge-hub/`（`inbox/`, `pending_approval/`, `overlay/`, `active_claims/`, `archive/upstreamed/`, `suspended/`, `rejected/`）の存在確認と初期化。
  2. **Hub 未処理原票検知フック**: `inbox/` または `pending_approval/` に未反映・裁定待ち原票が存在する場合、ユーザーへアラートし、`ask_question` モーダルで即時決裁・`LOCAL_FEEDBACK_RULES.md` 更新を行うか確認する。
  3. プロジェクト内ディレクトリ構造の初期展開（`docs/`, `docs/plans/`, `rules/`, `wiki/`, `promotions/`, `metrics/turns/`）。
  4. プロファイル別静的スケルトン（`skeletons/`）の初期配置（CIワークフロー、Alembic環境、`entrypoint.sh`、セッション基盤、共通フック、UIベース部品、MSWモック基盤）。
  5. `.env` 初期化（`VITE_ENABLE_MOCK=true`, `DEBUG=True` 等のモック制御設定を含む）。
  6. `PROJECT_STATE.md` 初期化（`EXECUTION_MODE`, `TEMPLATE_SOURCE`, `BASE_CORE_VERSION`, 初期ステータス記録）。
- **完了判定条件（ゲート）**:
  - [x] ディレクトリ構造、静的スケルトン、および `~/.gemini/knowledge-hub/` が正常構成されていること。
  - [x] `.env` が生成され、モック制御環境変数が設定されていること。
  - [x] 永続ナレッジ領域（`./wiki/`）およびメトリクス集計領域（`./metrics/`）が初期化されていること。
  - [x] `PROJECT_STATE.md` が初期化され、Status: `PHASE_1_COMPLETED` が記録されていること。

- **完了判定条件（明示的承認ゲート）**:
