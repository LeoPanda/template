## 1. はじめに

### 1.1 背景と問題意識
AI駆動開発ライフサイクルにおいては、「プロジェクト固有知見（Tier 1）」と「全体共通知見（Tier 2）」の二層分離、および試行錯誤や失敗知見を破棄しない「永続 Wiki 層（`./wiki/patterns/`）」と「推論とWikiの分離原則（Context Isolation）」により、高い学習能力とコンテキスト効率を両立してきた。

V2.3 においては、複数プロジェクト・複数環境での長期運用で顕在化した「パッチ競合」「新バージョン更新時のローカル知見消失」「ルール間の意味的矛盾」「履歴ID追記によるプロンプト肥大化」を解決するため、[V2.3新知見フィードバック機構設計書.md](./V2.3新知見フィードバック機構設計書.md) に基づき以下の進化を導入する：
1. **標準化知見原票（Knowledge Claim MD: `CLAIM-*.md`）への統一（`.patch` 廃止）**
2. **PC環境共通の Central Knowledge Hub（`~/.gemini/knowledge-hub/`）への集約**
3. **3段階意味的整合性監査（Core Invariants / 4分類矛盾監査 / 過剰適合・絶対行数バジェット監査）**
4. **Immutable Core ＋ Local Overlay（`LOCAL_FEEDBACK_RULES.md`）による二段階進化と State/Lineage 分離**

### 1.2 目的
本文書は、**Tier 1（プロジェクト固有知見）** と **Tier 2（全体共通知見）** の責務境界を V2.3 Central Knowledge Hub アーキテクチャと統合し、**「どの知見を、どのタイミングで評価し、どこへフィードバック（正本化・昇格）していくか」** の全ライフサイクルを規定する。

## 2. 知見の二層分離（Tier 1 / Tier 2）と V2.3 3スコープの棲み分け

### 2.1 全体構造マッピング

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│               エージェント試行錯誤・手戻り・障害 (Raw Traces / Logs)                     │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ 根本原因分析 (RCA / wiki-maintainer)
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                 【Spoke 永続 Wiki 層 (<project-root>/wiki/patterns/)】                 │
│      ※ 決してロールバックされない一次診断ナレッジベース (Catastrophic Forgetting防止) │
├───────────────────────────────────────────┬────────────────────────────────────────────┤
│   【Tier 1: プロジェクト固有知見 (Local)】 │   【Tier 2: 全体共通知見 (Universal)】       │
│   ・格納: ./wiki/patterns/local/          │   ・格納: ./wiki/patterns/universal/       │
│   ・内容: 業務ルール、独自画面、個別API   │   ・内容: FW挙動、Docker、型安全、共通手順 │
└─────────────────────┬─────────────────────┴─────────────────────┬──────────────────────┘
                      │                                           │
         [即時〜フェーズ完了時フィードバック]            [PHASE 8: 標準原票化 & Hub投函]
                      │ (ドキュメント逆同期)                       │ (CLAIM-*.md 生成・3段階監査)
                      ▼                                           ▼
┌───────────────────────────────────────────┐ ┌──────────────────────────────────────────┐
│   【Tier 1 永続正本 (案件内完結)】        │ │   【Tier 2 二段階進化正本 (Hub & Core)】 │
│   ・./docs/ (要件定義・基本設計・画面)    │ │   ① 第1段階 (PC環境内即時有効化):       │
│   ・./PROJECT_STATE.md (決定・未決事項)   │ │      ~/.gemini/knowledge-hub/overlay/    │
│                                           │ │        LOCAL_FEEDBACK_RULES.md (80行内)  │
│   ★ 推論エージェントの直接参照対象        │ │   ② 第2段階 (パイプライン改訂時本流化): │
│   (Central Hubへは一切持ち出さない)       │ │      Immutable Core (AGENTS.md/SKILL.md) │
│                                           │ │      + PIPELINE_MANIFEST / FEEDBACK_LEDGER│
└───────────────────────────────────────────┘ └──────────────────────────────────────────┘
```

### 2.2 二層の棲み分け詳細（V2.3）

| 項目 | Tier 1: プロジェクト固有知見 (Local) | Tier 2: 全体共通知見 (Universal) |
| :--- | :--- | :--- |
| **定義と対象** | 当該プロジェクトの業務ドメイン、特定顧客要件、個別画面仕様、個別DB制約、特定外部API連携に起因する知見。 | 開発言語、ライブラリ、FW、Docker、GCP、Git運用、リンター、エージェント共通行動規範に起因する知見。 |
| **Spoke Wiki層での扱い** | `./wiki/patterns/local/PAT-LOC-xxx.md`<br>（障害診断・手戻り履歴としての永続一次記録） | `./wiki/patterns/universal/PAT-{CAT}-xxx.md`<br>（標準化知見原票 `CLAIM-*.md` の生成元） |
| **最終到達先 (正本)** | **案件内の `./docs/` (各種設計書・仕様書)**<br>および **`./PROJECT_STATE.md`**<br>※ Central Hub やグローバル配置は厳禁（INV-09） | **第1段階（案件完了時）**: `~/.gemini/knowledge-hub/overlay/LOCAL_FEEDBACK_RULES.md`（および `active_claims/`）<br>**第2段階（改訂リリース時）**: Immutable Core（`rules/AGENTS.md`, `skills/*/SKILL.md`）＋ 系譜台帳（`PIPELINE_MANIFEST.json`, `FEEDBACK_LEDGER.md`） |
| **推論エージェントへの提供方法** | **「仕様・設計ドキュメント（`./docs/`）の最新化」** により提供。<br>※ 推論エージェントは `./docs/` を読むため、Wikiを直接見せる必要がなく Context Isolation が成立する。 | **「履歴ノイズゼロの `SKILL.md` / `AGENTS.md` ＋ `LOCAL_FEEDBACK_RULES.md`」** により提供。<br>※ 本文中には `[PAT-xxx]` 等の履歴IDを一切含めず、純粋な規範文として提供する（1-C）。 |
| **共通スキルへの昇格** | **絶対禁止 (Strict Prohibition: INV-09)**<br>個別業務仕様が環境共通ハブやテンプレートに混入することを防ぐ。 | **新・複合検証ゲート（3段階意味的監査）合格後に昇格**<br>`ask_question` モーダルでのユーザー承認を経て Local Overlay（または改訂時 Core）へクリーン統合。 |

## 3. 知見の評価・フィードバック タイミング マトリクス（V2.3）

```
【PHASE 1 開始時】
  Hub 未処理検知 ──► ~/.gemini/knowledge-hub/{inbox,pending_approval}/ に未処理原票があれば即時決裁・Overlay反映
                                │
【開発中 (PHASE 3, 5, 5.5, 6 / 改訂ターン)】
  障害・エラー発生 ──► wiki-maintainer が ./wiki/patterns/ へ即時記録 (RCA)
                                │
                                ├─► [Tier 1] ──► 各フェーズ完了ゲートで評価 ➔ ./docs/ & PROJECT_STATE.md へ逆同期完結
                                │
【マイルストーン完了時 (PHASE 8 / 改訂リリース時)】
                                └─► [Tier 2] ──► wiki-proposer が標準原票 CLAIM-*.md を ~/.gemini/knowledge-hub/inbox/ へ投函
                                                 ──► qa-engineer が 3段階意味的整合性監査 (New Gate 1〜4) を実行
                                                 ──► ask_question 承認後、LOCAL_FEEDBACK_RULES.md を即時クリーン再生成
```

### 3.1 評価・フィードバック詳細マトリクス

| 評価フェーズ / タイミング | 対象知見 (Tier) | 一次記録・入力 | 評価者・評価手段 | フィードバック先 (正本への反映) | 完了ゲート条件 |
| :--- | :---: | :--- | :--- | :--- | :--- |
| **PHASE 1 開始時**<br>(環境セットアップ) | **Tier 2**<br>(他案件・定期監査分) | `~/.gemini/knowledge-hub/inbox/` または `pending_approval/` | ・🛡️ `qa-engineer` (3段階意味的監査)<br>・👤 `ask_question` 承認 | `~/.gemini/knowledge-hub/overlay/LOCAL_FEEDBACK_RULES.md` | 未処理原票の決裁または保留選択完了。 |
| **PHASE 3 完了時**<br>(設計完了ゲート) | **Tier 1**<br>(設計判断) | `./wiki/patterns/local/`<br>設計レビュー是正内容 | ・`dev-doc-reviewer`<br>・🛡️ `dev-review-arch`<br>・👤 ユーザー承認 | `./docs/要件定義書.md`<br>`./docs/` 4大基本設計書<br>`./PROJECT_STATE.md` | ドキュメント間の不整合0件、未解決設計課題0件。 |
| **PHASE 5 完了時**<br>(ウォークスルー後) | **Tier 1**<br>(UI/仕様齟齬) | ウォークスルー不具合修正ログ | ・👤 ユーザー操作検証<br>・📐 `architect` 同期 | `./docs/画面仕様書.md`<br>`./docs/ビジネスロジック仕様書.md` | 最新コードの挙動と仕様書が100%一致（逆同期完了）。 |
| **PHASE 5.5 完了時**<br>(コード品質レビュー) | **Tier 1 & 2**<br>(コード品質) | 250行超過分割、重複排除、直書きモック排除 | ・🛡️ `dev-review-code`<br>・コンテナ再ビルド疎通 | (Tier 1) 実装コード・共通関数<br>(Tier 2) `./wiki/patterns/universal/` | 判定 CLEAN、250行超過0件、直書きモック0件。 |
| **PHASE 6 完了時**<br>(スルーテスト完了) | **Tier 1 & 2**<br>(テスト修復) | 自動修復（Auto-Healing）ログ、RCA | ・🛡️ `dev-phase6-testing`<br>・全シナリオ100%パス | (Tier 1) `./docs/plans/シナリオテスト計画書.md`<br>(Tier 2) `./wiki/patterns/universal/` | 全テストパス、未解決エラー0件。 |
| **PHASE 8 完了時**<br>(リリース・自己進化) | **Tier 2**<br>(環境共通昇格) | `./TEMPLATE_PROMOTIONS.md`<br>`CLAIM-*.md` 原票 | ・🛡️ 新複合検証ゲート (New Gate 1〜4)<br>・👤 `ask_question` 承認 | `~/.gemini/knowledge-hub/active_claims/` & `overlay/LOCAL_FEEDBACK_RULES.md` | 新4大関門クリア、Overlayクリーン再生成完了。 |
| **パイプライン改訂時**<br>(`template` リリース) | **Tier 2**<br>(本流Core統合) | `active_claims/` & `inbox/CLAIM-*.md` | ・🔄 `template-pipeline-sync`<br>・🛡️ Core Gate 総合監査 | Immutable Core (`AGENTS.md`, `SKILL.md`) ＋ `PIPELINE_MANIFEST.json` & `FEEDBACK_LEDGER.md` | 行数バジェット内統合、履歴ID混入0件、Global Deploy同期完了。 |

## 4. フォーマット仕様の統合（V2.3 スキーマ体系）

### 4.1 プロジェクト内一次記録フォーマット (`./wiki/patterns/{local|universal}/PAT-*.md`)
開発中に `wiki-maintainer` が記録するフォーマット。

```markdown
# [PAT-{TIER/CAT}-{通番}]: [簡潔なタイトル]

- **Pattern ID**: PAT-LOC-001 (Tier 1) または PAT-SYS-001 (Tier 2)
- **作成日**: YYYY-MM-DD
- **知見スコープ**: [Tier 1: プロジェクト固有 (Local) / Tier 2: テンプレート共通 (Universal)]
- **発生プロファイル**: [Profile A / Profile B / Profile C / Profile D]
- **適用対象プロファイル**: [ALL / Profile A / Profile D 等]
- **カテゴリ**: [ARCH / CODE / TEST / ENV / SEC / SYS / BIZ]
- **重大度**: [CRITICAL / HIGH / MEDIUM / LOW]
- **ステータス**: [Active / Synced-to-Docs / Claim-Exported / Archived]
- **統合候補アンカー** (Tier 2 の場合):
  - `対象ファイルパス` (`## セクション見出し`)

## 1. 発生状況・前提条件 (Context & Preconditions)
- どのような業務ユースケース、画面、フェーズ、または技術環境・前提条件で発生したか。

## 2. 現象・根本原因 (Problem & Root Cause Analysis)
- どのような不具合・エラーが発生し、なぜその問題が生じたか（RCA）。

## 3. 処方箋・推奨ルール (Distilled Prescription)
- 次回からエージェントはどう行動・記述すべきか（Tier 2 の場合は固有名詞を含まない純粋な規範文）。

## 4. 正本還元先とフィードバック履歴 (Lineage & Destination)
- **正本反映先**:
  - (Tier 1) `./docs/ビジネスロジック仕様書.md` §3.2, `./PROJECT_STATE.md`
  - (Tier 2) `~/.gemini/knowledge-hub/inbox/CLAIM-YYYYMMDD-slug-PAT-xxx.md`
```

### 4.2 標準化知見原票フォーマット (`CLAIM-{YYYYMMDD}-{PROJECT_SLUG}-{PAT_ID}.md`)
PHASE 8 において `wiki-proposer` が生成し、`~/.gemini/knowledge-hub/inbox/` および `./promotions/` に出力する自己完結型 Markdown 原票。YAML Frontmatter（`schema_version: "2.3.0"`, `claim_id`, `pattern_id`, `source_project_profile`, `applicable_profiles`, `target_candidates`, `status`, `consolidated_from`）と5つの標準セクションで構成される（完全なスキーマ定義は [V2.3新知見フィードバック機構設計書.md](./V2.3新知見フィードバック機構設計書.md) 第3.2節を参照）。

## 5. エージェントの役割と知見フィードバック手順

### 5.1 サブエージェント返却サマリ（知見の吸い上げ）
各サブエージェント（`architect`, `backend-engineer`, `ui-designer`, `qa-engineer`）は、作業完了時にコンダクターへ返却する標準完了サマリ内の `💡 獲得した知見・落とし穴 (Lessons Learned)` にて、事象・根本原因・処方箋・推奨スコープ（Tier 1 / Tier 2）を報告する。

### 5.2 👑 コンダクターおよび 🛡️ QA による仕分け・監査・反映ワークフロー
1. **仕分けと一次記録 (`wiki-maintainer`)**:
   - 業務固有仕様なら **Tier 1**（`./wiki/patterns/local/`）、汎用技術・プロセス知見なら **Tier 2**（`./wiki/patterns/universal/`）へ記録。
2. **Tier 1 の即時フィードバック（ドキュメント正本化）**:
   - 当該フェーズの `./docs/` 設計書および `./PROJECT_STATE.md` へ即座に逆同期し、ステータスを `Synced-to-Docs` に更新する。
3. **Tier 2 の標準原票化と Knowledge Hub 投函 (`wiki-proposer`)**:
   - PHASE 8 にて `./TEMPLATE_PROMOTIONS.md` に昇格候補サマリをまとめるとともに、標準化知見原票 `CLAIM-*.md` を生成して `~/.gemini/knowledge-hub/inbox/` へ投函する。
4. **3段階意味的整合性監査と Overlay 即時再生成 (`qa-engineer` & `conductor`)**:
   - 🛡️ `qa-engineer` が新・複合検証ゲート（Stage 1: `CORE_INVARIANTS.md` 監査、Stage 2: 4分類相互矛盾監査、Stage 3: 過剰適合排除・履歴IDゼロ・絶対行数バジェット監査）を実行。
   - 👑 `conductor` が監査結果プレビューとともに `ask_question` モーダルを提示し、ユーザー承認を得て `active_claims/` への登録と `overlay/LOCAL_FEEDBACK_RULES.md` のクリーン再生成を実行する。
