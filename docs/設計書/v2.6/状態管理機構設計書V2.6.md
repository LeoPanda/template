## 1. 目的と基本思想 (V2.6 パラダイムシフト)

### 1.1 背景と課題
従来の Markdown 直接編集による状態管理（`PROJECT_STATE.md`）には以下の課題が存在していた：
1. **表記揺れと正規表現パース依存**: Markdown の手動編集による書式崩壊や表記揺れが発生し、`dev-metrics-collector` 等の自動解析ツールでパース失敗のリスクがあった。
2. **Single Writer 原則のプロンプト依存**: コンダクター専任の Single Writer 原則がプロンプト規律に依存しており、物理的な排他制御がなかった。

### 1.2 ハイブリッド状態台帳アーキテクチャ (Hybrid State Ledger)
V2.6 では、「機械正本（`project_state.json`）」と「人間可読ビュー（`PROJECT_STATE.md`）」を分離・同期するアーキテクチャを採用する：
- **機械正本 (`./project_state.json`)**: フェーズ進行、3大レビュー合否、改訂履歴、メトリクス数値を厳格な JSON スキーマで保持。
- **人間ビュー (`./PROJECT_STATE.md`)**: `scripts/state_manager.py` により 100% 決定論的に自動生成。
- **物理 Single Writer & チェックサム検証**: `state_manager.py` 実行時に SHA-256 チェックサムを検証し、手動改ざんやサブエージェントによる不正直接編集を物理遮断する（`--reconcile` オプションにより手動追記分は安全に逆マージ可能）。

## 2. state_manager.py CLI コマンド仕様

| コマンド | 用途 |
| :--- | :--- |
| `init` | 台帳と Markdown ビューの初期生成 |
| `set-phase` | フェーズ遷移（レビュー未合格時の進行拒否 Interlock 付き） |
| `complete-task` | タスク完了マーク |
| `record-review` | 3大レビュー合否判定と指摘件数の構造化登録 |
| `record-approval` | ユーザー承認日時の記録 |
| `sync-metrics` | メトリクス JSON から定量数値を自動同期 |
| `verify-integrity` | チェックサム整合性検証（`--reconcile` で手動追記マージ） |
| `start-revision` | 改訂起票、ステータス `ACTIVE` 遷移、改訂ブランチ作成 |
| `complete-revision` | 改訂完了、履歴記録、ステータス `IDLE` 復帰 |

## 3. 改訂ライフサイクル (Revision Lifecycle)

初期リリース後の機能追加や Hotfix は、以下の 5段階サイクルで運用する：
1. **改訂起票**: `state_manager.py start-revision --id REV-xxx`
2. **差分要件/設計**: `REQ-Fxx` 採番 ＆ `traceability_checker.py --mode design`
3. **差分実装**: `harness_guard.py --staged`（pre-commit フック）
4. **回帰/感覚センサー検証**: `traceability_checker.py --mode full`（異常系比率20%以上）＋ Chrome DevTools MCP
5. **改訂完了**: `state_manager.py complete-revision` ＆ `dev-git-release`
