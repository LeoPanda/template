## 1. 目的と基本思想 (V3.0.0 ハイブリッド状態台帳)

### 1.1 背景と課題
従来の Markdown 直接編集による状態管理（`PROJECT_STATE.md`）には以下の課題が存在していた：
1. **表記揺れと正規表現パース依存**: Markdown の手動編集による書式崩壊や表記揺れが発生し、`dev-metrics-collector` 等の自動解析ツールでパース失敗のリスクがあった。
2. **Single Writer 原則のプロンプト依存**: コンダクター専任の Single Writer 原則がプロンプト規律に依存しており、物理的な排他制御がなかった。

### 1.2 ハイブリッド状態台帳アーキテクチャ (Hybrid State Ledger V3.0.0)
V3.0.0 では、「機械正本（`project_state.json`）」と「人間可読ビュー（`PROJECT_STATE.md`）」を分離・同期するアーキテクチャを採用する：
- **機械正本 (`./project_state.json`)**: フェーズ進行、3大レビュー合否、セッションモード（`execution` / `specification_only`）、機能特性（`capability_traits`）、改訂履歴、メトリクス数値を厳格な JSON スキーマ（`schema_version: 3.0.0`）で保持。
- **人間ビュー (`./PROJECT_STATE.md`)**: `scripts/state_manager.py` により 100% 決定論的に自動生成。
- **物理 Single Writer & チェックサム検証**: `state_manager.py` 実行時に SHA-256 チェックサムを検証し、手動改ざんやサブエージェントによる不正直接編集を物理遮断する（`--reconcile` オプションにより手動追記分は安全に逆マージ可能）。

## 2. state_manager.py CLI コマンド仕様

| コマンド | 用途 |
| :--- | :--- |
| `init` | 台帳と Markdown ビューの初期生成 (`schema_version: 3.0.0`) |
| `set-phase` | フェーズ遷移（レビュー未合格時および `REV_4` 遷移時の `verify-review-readiness` 未通過時の進行拒否 Interlock 付き） |
| `set-mode` | セッションモード設定（`execution` / `specification_only`） |
| `set-traits` | 機能特性フラグの動的追加・削除（`--add`, `--remove`） |
| `complete-task` | タスク完了マーク |
| `record-review` | 3大レビュー合否判定と指摘件数の構造化登録 |
| `record-approval` | ユーザー承認日時の記録（`--phase REV_4` 等の改訂承認対応） |
| `sync-metrics` | メトリクス JSON から定量数値を自動同期 |
| `verify-integrity` | チェックサム整合性検証（`--reconcile` で手動追記マージ） |
| `verify-review-readiness` | REV-4 実機レビュー突入前の前提条件物理検査（E2E合格、証跡完全性 `[INV-QA-01]`、第1段階ドキュメント衛生、環境健全性） |
| `start-revision` | 6段階改訂（`REV-1`〜`REV-6`）起票、ステータス `ACTIVE` 遷移、改訂ブランチ作成 |
| `complete-revision` | 改訂完了時不変則検証（`[INV-REV-01]`〜`[INV-REV-04]`, `[INV-QA-01]` 証跡実在＆改ざん検証）、履歴記録、ステータス `IDLE` 復帰 |

## 3. 改訂ライフサイクル (Revision Lifecycle)

初期リリース後の機能追加や Hotfix は、以下の 6段階サイクルで運用する：
1. **REV-1: 要件・設計精査**: `state_manager.py start-revision --id REV-xxx` ＆ 差分要件 `REQ-Fxx` 採番 ＆ Executable Golden Fixtures 配置 ＆ `traceability_checker.py --mode design` PASS
2. **REV-2: 差分実装・静的検証**: `HG-002` 本番コードモック・ダミー記述完全排除、2段階行数制限（250/350行、400/550行）、`HG-010` 空実装遮断、Stage 1.5 実I/Oスモークテスト、`harness_guard.py --all` PASS
3. **REV-3: 契約テスト・深層アサーション検証**: Stage 2 実結合E2Eテスト、`traceability_checker.py --mode full`（異常系比率20%以上）による署名付き動的証跡 `metrics/qa_runtime_evidence.json` の決定論的自動生成、第1段階ドキュメント衛生・構造整理、`verify-review-readiness` PASS 検証
4. **REV-4: ユーザー実機・挙動確認**: 事前検査ゲート `verify-review-readiness` PASS をインターロック前提条件とした開発サーバー起動 ＆ ユーザー実機操作・挙動合意（`state_manager.py record-approval --phase REV_4`）
5. **REV-5: 本番総合監査・成果物ビルド**: 第2段階ドキュメント意味的相互整合性精査（Semantic Cross-Check）、コード品質・システム総合レビュー合否判定 ＆ 本番成果物ビルド検証
6. **REV-6: 定量メトリクス集計・知見昇格・リリース**: `metrics_collector.py --all --sync-state` ＆ `pipeline-reconciler.sh` ＆ 不変則検証（`[INV-REV-01]`〜`[INV-REV-04]` および `[INV-QA-01]` 証跡実在・SHA-256改ざん検証） ＆ `complete-revision` ＆ `dev-git-release`
