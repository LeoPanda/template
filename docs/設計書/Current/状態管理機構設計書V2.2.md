## 1. 目的と基本思想

### 1.1 目的
サブエージェント（`architect`, `backend-engineer`, `ui-designer`, `qa-engineer`）およびメインエージェント（`conductor`）が協調して自律開発を推進するにあたり、以下の課題を解決する：
1. **文脈の断絶防止**: コンテキスト長過大によるリセットやセッション再開時にも、現在のフェーズ・残タスク・決定事項・**選定されたシステム展開プロファイル（Profile A〜D）およびモック動作モード**を即座に復元できること。
2. **作業競合の排除**: 複数エージェントが同時に作業状態を更新することによるコンフリクトや破損を完全に防ぐこと（Single Writer原則）。
3. **客観的品質ゲートの可視化**: 3大レビュー（基本設計、コード品質、システム総合）の合否判定、重大度別指摘件数、**定常コア8項目およびプロファイル適合性**を確実に記録・追跡できること。
4. **Shift-Left スケルトン展開・標準コマンドの追跡**: 初期配置された静的スケルトン（`skeletons/`）の反映状況、Alembicマイグレーションリビジョン、型自動生成の実行履歴を一元把握できること。

### 1.2 設計基本原則
| 原則 | 内容 |
| :--- | :--- |
| **配置場所の分離** | `PROJECT_STATE.md` は **プロジェクトルート直下（`./PROJECT_STATE.md`）** に配置する。`docs/` 配下の一般仕様書と物理分離し、ドキュメント監査時のノイズ・誤判定を排除する。 |
| **Single Writer 原則** | `PROJECT_STATE.md` への書き込み・更新権限は **👑 プロジェクトコンダクター（メインエージェント）のみ** が保持する。サブエージェントは完了サマリを返すのみとし、状態ファイルを直接編集しない。 |
| **人間可読・直接編集性** | GitHub Flavored Markdown 形式を採用。ユーザーがVSCode等で直接メモやチェックを更新することも許容する。 |
| **明示的承認ゲートの記録** | ユーザーが承認を与えた日時、コミット、承認ステータスを状態ファイルに明記する。 |
| **Git / バージョン連動** | `Git運用基準書.md` および `.env`（`APP_VERSION`）と同期し、ブランチ名、改訂依頼番号を常時反映する。 |
