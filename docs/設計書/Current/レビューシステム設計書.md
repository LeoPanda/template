## 1. はじめに

### 1.1 背景と課題認識
従来のレビューシステムは事後的な検査に偏り、テストがパスしても実動環境で機能不全を起こす「見せかけの合格（Green Illusion）」や改訂時のユーザー実機確認の欠落を招いていた。V3.0.0 では、**「実行可能な契約（Executable Golden Fixtures / Contract-First MSW）、Stage 1.5/2 テストゲート、qa_runtime_evidence.json、および REV-4 ユーザー実機レビュー承認の機械的インターロック」** へと進化する。

## 3. 3大レビューゲート ＆ 実行証跡詳細仕様

### 3.1 【ゲート 1】基本設計レビュー (`dev-review-arch`)
- **実施フェーズ**: PHASE 3 / REV-1 完了ゲート
- **合否判定基準**: `PASS` または `CONDITIONAL PASS` 必須（`traceability_checker.py --mode design` PASS 必須）。
- **監査観点**: 定常コア規範、プロファイル・Trait適合要件、Executable Golden Fixtures（`tests/fixtures/golden/`）の配置と相対リンク参照、画面仕様書4列契約表。

### 3.2 【ゲート 2】コード品質レビュー (`dev-review-code`)
- **実施フェーズ**: PHASE 5.5 / REV-2 / REV-5 完了ゲート
- **合否判定基準**: `CLEAN` 必須（`harness_guard.py --all` PASS 必須）。
- **監査観点**: 2段階行数制限（FE 250/350行、BE 400/550行）、空実装遮断（`HG-010`）、直書きモック排除、Contract-First MSW型拘束、動的描画 O(1) キャッシュ。

### 3.3 【ゲート 3】システム総合レビュー (`dev-review-system`)
- **実施フェーズ**: PHASE 7 / REV-5 本番リリース直前ゲート
- **合否判定基準**: `RELEASE APPROVED` 必須。
- **監査観点**: 本番用 `VITE_ENABLE_MOCK=false` 二重防御、IAP JWT有効化、`traceability_checker.py --mode full` PASS（テスト関数直結、異常系比率20%以上、動的カバレッジ）、Stage 2 モックOFF実サーバー結合E2E、**`metrics/qa_runtime_evidence.json` の完全性検証**。

## 4. 改訂ライフサイクルにおけるユーザー実機レビュー承認 (REV-4 Gate)
- 改訂運用（`REV-1`〜`REV-6`）においては、自動テスト（`REV-3`）完了後に必ず **`REV-4: 開発サーバー起動・ユーザー実機レビュー・改修`** を実施する。
- ユーザーによる実機確認OKと `state_manager.py record-approval --phase REV_4` の記録がない限り、改訂完了（`complete-revision`）は `[INV-REV-04]` で機械遮断される。

---

## 5. 知見昇格における 3段階意味的整合性監査 (Semantic Auditor)

PHASE 8 / REV-6 において、🛡️ `qa-engineer` は投函された知見原票に対し、以下の 4大関門（Gate 1〜4）を機械的・意味的に監査する。

1. **Gate 1: CORE_INVARIANTS 整合性監査**: プラグイン不変則（INV-01〜10）との抵触がないこと。
2. **Gate 2: 4分類矛盾・競合監査**: 既存の Core 規約および他原票との意味的矛盾がないこと。
3. **Gate 3: 過剰適合排除 ＆ pattern_id 一意性保証**: 単発例外の混入を排除し、Knowledge Hub 全域で未使用の最新連番であること。
4. **Gate 4: 純度・絶対行数バジェット監査**: `pipeline-reconciler.sh --audit-budget` による全ファイル行数上限および履歴ID混入ゼロの検証。
