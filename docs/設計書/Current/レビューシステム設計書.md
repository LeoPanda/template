## 1. はじめに

### 1.1 背景と課題認識
従来のレビューシステムは事後的な検査に偏り、テストがパスしても実動環境で機能不全を起こす「見せかけの合格（Green Illusion）」や改訂時のユーザー実機確認の欠落を招いていた。本設計書では、**本番コードモック・ダミー記述完全排除（`HG-002`）、署名付き `qa_runtime_evidence.json` による改ざん検証（`[INV-QA-01]`）、2段階ドキュメント精査、および REV-4 事前物理検査ゲート（`verify-review-readiness`）** を導入し、品質監査とレビュー判定の機械的完全性を確立する。

### 2.2 コア Hard Gate 規約詳細

`harness_guard.py` を通じてコミット前（Pre-commit hook）および CI 上で機械的に執行される主要 Hard Gate の規約は以下の通りである。

1. **`HG-001`: 行数制限規約 (Line Count Limit)**
   - フロントエンド（`frontend/src/`）: WARN 250行 / BLOCK 350行
   - バックエンド（`backend/`）およびCLI（`src-tauri/`）: WARN 400行 / BLOCK 550行
2. **`HG-002`: 本番コードからのモック・ダミー記述・例外フォールバックの機械的遮断**
   - **検査対象の拡大**: フロントエンド（`frontend/src/`）に加え、バックエンド（`backend/`）およびCLI（`src-tauri/`）の本番コード全域を対象とする。
   - **禁止識別子**: `generate_mock_*`, `dummy_*`, `Mock[A-Z0-9_]+` 等のモック生成関数・クラス・変数。
   - **禁止メディア記述**: `testsrc`, `sine=`, `anoisesrc`, `color=black` 等のテスト・ダミーメディア生成記述。
   - **例外フォールバック遮断**: 外部呼出やDB処理の例外捕捉ブロック（`except` / `catch`）内でのサイレントなモックデータ・ダミー返却の完全禁止。
3. **`HG-009`: ドキュメント衛生・命名規則規約 (Document Hygiene)**
   - **対象範囲**: `docs/設計書/Current/` 配下の正本ドキュメント群。
   - **プレフィックス/サフィックス検査**: 作業用一時ファイル（`*_tmp.md`, `*_draft.md`, `*copy*` 等）の Current 領域への残存を遮断。
   - **直下未整理ファイルの遮断**: `docs/` 直下への無秩序な作業ファイル配置を禁止。
   - **見出しタイトル規約**: 見出しタイトル等への個別バージョン番号直書き（例: `# ... (V3.0.1)`）を排除し、システム SemVer による一元管理を維持。
4. **`HG-010`: 空実装・縮退実装の物理遮断**
   - `pass`, `...`, `raise NotImplementedError`, 空JSXハンドラ等の未実装・縮退コードのコミットを遮断。
5. **`HG-011`: 非開発モード時の操作パス監視と自律昇格**
   - コンテンツ制作モード時であってもシステム本体コード領域の編集試行を検知し、システム改訂パイプラインへ自律昇格させる。

## 3. 3大レビューゲート ＆ 実行証跡詳細仕様

### 3.1 【ゲート 1】基本設計レビュー (`dev-review-arch`)
- **実施フェーズ**: PHASE 3 / REV-1 完了ゲート
- **合否判定基準**: `PASS` または `CONDITIONAL PASS` 必須（`traceability_checker.py --mode design` PASS 必須）。
- **監査観点**: 定常コア規範、プロファイル・Trait適合要件、Executable Golden Fixtures（`tests/fixtures/golden/`）の配置と相対リンク参照、画面仕様書4列契約表。

### 3.2 【ゲート 2】コード品質レビュー (`dev-review-code`)
- **実施フェーズ**: PHASE 5.5 / REV-2 / REV-5 完了ゲート
- **合否判定基準**: `CLEAN` 必須（`harness_guard.py --all` PASS 必須）。
- **監査観点**: 2段階行数制限（FE 250/350行、BE 400/550行）、空実装遮断（`HG-010`）、直書きモック排除、Contract-First MSW型拘束、動的描画 O(1) キャッシュ。

### 3.3 【ゲート 3】システム総合レビュー (`dev-review-system`)
- **実施フェーズ**: PHASE 7 / REV-5 本番リリース直前ゲート
- **合否判定基準**: `RELEASE APPROVED` 必須。
- **監査観点**: 本番用 `VITE_ENABLE_MOCK=false` 二重防御、IAP JWT有効化、`traceability_checker.py --mode full` PASS（テスト関数直結、異常系比率20%以上、動的カバレッジ）、Stage 2 モックOFF実サーバー結合E2E、**`metrics/qa_runtime_evidence.json` の署名および改ざん検証（`[INV-QA-01]`）**、ならびに **第2段階ドキュメント意味的相互整合性精査（Semantic Cross-Check）** の合格確認。

### 3.4 【新設ゲート】REV-4 事前検査ゲート (`verify-review-readiness` / Stage 2 Live Probe)
- **実施フェーズ**: REV-3 完了時（REV-4 開発サーバー起動・ユーザー実機レビュー要請直前）
- **合否判定基準**: `state_manager.py verify-review-readiness` ALL PASS 必須（未通過時は `set-phase REV_4` が機械的インターロックにより実行不可）。
- **Live Invariant Probe 物理仕様 (`[REQ-F-310-01]`)**:
  1. **完全分離サブプロセス一時起動**:
     - Python `subprocess.Popen` を用い、本番起動コマンドと同等の `python3 -m uvicorn backend.app.main:app --port 8999` を独立プロセスとして一時起動する。テスト用フィクスチャやインプロセスモックの影響を物理隔離する。
  2. **ポート競合回避 ＆ 15秒タイムアウト保護**:
     - 既定ポート 8000 との衝突を防ぐポート（8999等）を使用し、最大 15 秒間起動ポーリングを実施。完了時および例外終了時には `terminate()` / `kill()` を呼び出し、プロセスを確実に回収する。
  3. **クリティカルパス実HTTPプローブ (Deep Health Probe)**:
     - 単なる静的応答ではなく、`http://127.0.0.1:8999/api/health?deep=true` に対して実 HTTP GET リクエストを送信。
     - サーバー内部で SQLAlchemy を経由して実DBに対して `SELECT 1` またはマスタ参照クエリが成功し、`{"status": "healthy", "database": "connected"}` かつ HTTP 200 が返ることを物理検証。
  4. **起動クラッシュ・例外トレースバックの完全捕捉**:
     - サーバー起動失敗（exit code != 0）または 500 エラー発生時、プロセスの `stderr` から完全なエラートレースバック（`sqlite3.OperationalError` 等）を捕捉してコンソールに出力し、即座に `[READINESS BLOCK]` としてパイプラインを停止する。
  5. **第1段階ドキュメント衛生 ＆ 署名付き証跡検証 (`[INV-QA-01]`)**:
     - `docs/設計書/Current/` の衛生整理、および最新の `metrics/qa_runtime_evidence.json` の署名・改ざん検証を同時執行。

## 4. 改訂ライフサイクルにおけるユーザー実機レビュー承認 (REV-4 Gate)
- 改訂運用（`REV-1`〜`REV-6`）においては、自動テスト（`REV-3`）完了後に必ず **`REV-4: 開発サーバー起動・ユーザー実機レビュー・改修`** を実施する。
- ユーザーによる実機確認OKと `state_manager.py record-approval --phase REV_4` の記録がない限り、改訂完了（`complete-revision`）は `[INV-REV-04]` で機械遮断される。

## 5. 知見昇格における 3段階意味的整合性監査 (Semantic Auditor)

PHASE 8 / REV-6 において、🛡️ `qa-engineer` は投函された知見原票に対し、以下の 4大関門（Gate 1〜4）を機械的・意味的に監査する。

1. **Gate 1: CORE_INVARIANTS 整合性監査**: プラグイン不変則（INV-01〜10）との抵触がないこと。
2. **Gate 2: 4分類矛盾・競合監査**: 既存の Core 規約および他原票との意味的矛盾がないこと。
3. **Gate 3: 過剰適合排除 ＆ pattern_id 一意性保証**: 単発例外の混入を排除し、Knowledge Hub 全域で未使用の最新連番であること。
4. **Gate 4: 純度・絶対行数バジェット監査**: `pipeline-reconciler.sh --audit-budget` による全ファイル行数上限および履歴ID混入ゼロの検証。
