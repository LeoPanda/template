## 1. はじめに

### 1.1 背景と課題認識
AI駆動システム開発ライフサイクルにおいて、レビュー・監査システムは「アプリケーション開発における品質保証（3大レビュー）」と「開発パイプライン自身の健全な自己進化（3段階意味的整合性監査）」の二大統制を担う。

V2.4 においては、実稼働プロジェクトの運用実績および Central Knowledge Hub から本流統合された 6 大知見（PAT-CODE-001, PAT-UI-001, PAT-MOCK-001, PAT-TEST-001, PAT-REV-001, PAT-002）と、公式セマンティックバージョニング（SemVer 2.0.0）に基づき、監査基準を高度に刷新する。

## 3. 3大レビューゲート詳細仕様

### 3.1 【ゲート1】基本設計レビュー (`dev-review-arch`) [PHASE 3 完了ゲート]
- **主担当**: 🛡️ `qa-engineer`
- **合否判定基準**: `PASS` または `CONDITIONAL PASS` 必須（`REJECT` 時は設計修正ループへ差し戻し）。
- **主要監査項目**:
  1. **定常コア8項目適合性**:
     - フロントエンド 250行制限方針、バックエンド DTO 分離方針が設計されているか。
     - OpenAPI からの Codegen、Pydantic Settings、Aware UTC が明記されているか。
     - モック切替仕様（案C＋案A）および Fail-Fast 原則が規定されているか。
     - 画面仕様書がグランドデザイン規格、システムバージョンバッジ（`v1.0.0`）、デイライト視認性明暗ペア規約に準拠しているか。
  2. **展開プロファイル別適合性**:
     - Profile A: `max-instances=1`、Litestream WAL、IAP JWT 二重防御、Alembic 前提。
     - Profile D: Local SQLite WAL、Frameless TitleBar、IStorageAdapter、実ファイルDB結合テスト。

### 3.2 【ゲート2】コード品質レビュー (`dev-review-code`) [PHASE 5.5 完了ゲート]
- **主担当**: 🛡️ `qa-engineer`
- **合否判定基準**: 判定 `CLEAN` 必須（CRITICAL: 0件, MAJOR: 0件）。
- **主要監査項目**:
  1. **1ファイル最大250行制限（フロントエンド）**: コンポーネントの肥大化を機械的検査。超過時は即座にリファクタリング提案。
  2. **1ファイル最大400行制限 ＆ DTO・パーサー物理分離（バックエンド / PAT-CODE-001）**: DTO 構造体およびパーサーが独立モジュール（`schemas/`, `*_dto.rs` 等）に分離され、Controller 層がオーケストレーションに専念しているか。
  3. **直書きモックの完全排除**: コンポーネント内にダミー配列やスタブがハードコードされていないか（MSW 集約必須）。
  4. **デイライト視認性担保（PAT-UI-001）**: ダーク前提の淡色・透過カラー（`text-blue-200` 等）が単独で直書きされていないか。Tailwind 明暗ペア（`dark:` 併記）またはセマンティックデザイントークンが指定されているか。
  5. **SemVer 形式監査**: `.env`、`package.json`、`Cargo.toml` 等のバージョン表記が純粋数値3桁（`1.0.0`、先頭 `v` なし）であるか。

### 3.3 【ゲート3】システム総合レビュー (`dev-review-system`) [PHASE 7 リリース直前ゲート]
- **主担当**: 🛡️ `qa-engineer`
- **合否判定基準**: 判定 `RELEASE APPROVED` 必須。
- **主要監査項目**:
  1. **本番用モックOFF二重防御 & Fail-Fast 監査**: 本番環境で `VITE_ENABLE_MOCK=false` が強制され、実結合時に通信エラーが発生した際サイレントフォールバックせず例外をスローすること。
  2. **IAP JWT 署名検証ミドルウェア有効化**: 本番環境で JWT 検証バイパスが存在しないこと。
  3. **起動時 Alembic 自動実行保証**: `entrypoint.sh` により、起動時に確実に `alembic upgrade head` が実行されること。
  4. **Litestream 同期監視**: `/api/internal/litestream/status` が正常に同期ラグを返却すること。
  5. **平文シークレット完全排除**: リポジトリ内に `.env` や認証情報ファイルが存在しないこと。
  6. **Git リリース保護**: `dev-git-release` により、二重プレフィックス（`vV2.0`）が発生せず、正しく `vMAJOR.MINOR.PATCH` がタグ付けされること。

## 4. パイプライン自己進化 3段階意味的整合性監査 (PHASE 8 新複合検証ゲート)

PHASE 8 において、標準化知見原票（`CLAIM-*.md`）が Central Knowledge Hub に投函された際、🛡️ `qa-engineer` (Semantic Auditor) は以下の 4 大関門を実行する。

| 関門 | 監査種別 | 判定基準 |
| :--- | :--- | :--- |
| **新関門 1** | **コア不変原則監査** | `CORE_INVARIANTS.md`（INV-01〜INV-10）を侵害していないこと。 |
| **新関門 2** | **4分類意味的矛盾監査** | 既存ルールおよび承認済み他知見と意味的矛盾（Direct, Conditional, Redundant, Inversion）がないこと。 |
| **新関門 3** | **過剰適合排除 ＆ 構造整合監査** | 特定案件のローカル事情に偏っておらず汎用性があること。マークダウン構造が崩れていないこと。 |
| **新関門 4** | **純度 ＆ 絶対行数バジェット監査** | 原票本文に履歴ID（`[PAT-xxx]`）が混入していないこと。Local Overlay バジェット（上限80行）に収まること。 |

全関門を通過した知見のみがユーザー承認（`ask_question`）へ提示され、`pipeline-reconciler.sh` により Local Overlay へ即時反映される。
