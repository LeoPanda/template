## 1. 採択された基本方針 (V2.3 決定事項)

AI駆動システム開発ライフサイクル V2.3 におけるエージェント設計の基本方針は以下の通りである。

| 検討項目 | 採択方針 | 詳細内容 |
| :--- | :--- | :--- |
| **1. 開発思想** | **Shift-Left 前倒し組み込み** | 事後修正ではなく、初期スケルトン展開・設計・実装の初期段階から標準パターン（Alembic, IAP JWT, 責務分離, グランドデザイン, MSW等）を各エージェントが自律的に組み込む。 |
| **2. プロファイル適応** | **2層プロファイル体系の厳格遵守** | 📐 `architect` が第1層（定常コア8項目）および第2層（Profile A〜D）を設計し、各実装エージェントおよび 🛡️ `qa-engineer` が一貫してプロファイル仕様に準拠する。 |
| **3. フロントエンド規約** | **Anti-God Component & 直書きモック禁止** | 🎨 `ui-designer` に対し、**1ファイル最大250行制限（INV-03）**、Custom Hooks/Servicesへの物理分離、**コンポーネント内直書きモックの原則禁止（INV-04）**を強制適用する。 |
| **4. バックエンド規約** | **Alembic厳格運用 & 標準コマンド順守** | 💻 `backend-engineer` に対し、生SQL手動DDLの絶対禁止（INV-05）、Alembicマイグレーション自動生成・適用、IAP JWT署名検証（INV-06）、二重キャッシュ実装を義務付ける。 |
| **5. 統括・状態管理** | **スケルトン展開 & Single Writer** | 👑 `conductor` が初期スケルトン（`skeletons/`）を展開し、標準コマンドシーケンスと外部CLI非対話実行を管理、`PROJECT_STATE.md` を一元更新する（INV-01）。 |
| **6. レビュー・監査統制** | **機械的監査とZero Tolerance** | 🛡️ `qa-engineer` が250行制限、直書きモック排除、本番モックOFF、IAP検証有効化を機械的・厳格に合否判定する（INV-07）。 |
| **7. 知見フィードバック** | **Central Knowledge Hub & 3段階意味的監査** | 👑 `conductor` が標準化知見原票（`CLAIM-*.md`）を `~/.gemini/knowledge-hub/inbox/` へ投函し、🛡️ `qa-engineer` が 3段階意味的整合性監査（New Gate 1〜4）を実行。`ask_question` 承認を経て `overlay/LOCAL_FEEDBACK_RULES.md` をクリーン再生成する。 |

## 4. 各エージェントの詳細定義

### 4.1 👑 プロジェクトコンダクター（メインエージェント）

- **種別**: メインエージェント（Main Agent）
- **役割識別名 / 定義ファイル**: `conductor` / `.agents/plugins/system-dev-pipeline/agents/conductor.md`（絶対行数上限: 120行）
- **推奨モデル**: `pro` または `inherit`
- **パーソナリティ / 責務**:
  - ユーザーとの対話窓口であり、開発フェーズ（PHASE 1〜8）およびタスク進捗を常時統制する。
  - **PHASE 1 初期化と Hub 未処理検知**: `dev-phase1-setup` を通じて静的スケルトン（`skeletons/`）と `.env` を展開するとともに、`~/.gemini/knowledge-hub/inbox/` および `pending_approval/` の未処理原票を検知してユーザーへ決裁を案内する。
  - **標準コマンドシーケンス＆非対話CLI実行の統括**: Alembic マイグレーション、OpenAPI 型自動生成、CI同等検証を実行。外部CLI実行時は確認プロンプト待ちハングを防ぐため非対話フラグ（`--quiet`, `--yes` 等）を強制し、バックグラウンド移行時は `schedule` タイマーを併用する。
  - **`PROJECT_STATE.md` の Single Writer 専任（INV-01）**: プロファイル選定結果、モック状態、レビューゲート合否、Knowledge Hub 昇格ステータスを一元記録。
  - **PHASE 8 Knowledge Hub オーケストレーション**: `wiki-proposer` で標準化知見原票（`CLAIM-*.md`）を `inbox/` へ投函し、`qa-engineer` の3段階意味的監査結果を受けて **`ask_question` モーダル**でユーザー承認・裁定を取得し、`overlay/LOCAL_FEEDBACK_RULES.md` をクリーン再生成する。
  - **サブエージェント動的登録フォールバック**: 未定義サブエージェントの動的登録・呼び出しを保証。
  - 手続き的な Git 操作（`dev-git-init`, `dev-git-release`）およびデプロイ操作（`dev-db-overwrite`）を専任で実行。

### 4.2 📐 設計・立案スペシャリスト（サブエージェント）

- **種別**: サブエージェント（Subagent）
- **役割識別名 / 定義ファイル**: `architect` / `.agents/plugins/system-dev-pipeline/agents/architect.md`（絶対行数上限: 120行）
- **適用モデル**: `pro`
- **ワークスペース**: `inherit`
- **パーソナリティ / 責務**:
  - ソフトウェアアーキテクトおよびビジネスアナリストとして振る舞う。
  - **2層プロファイル体系の設計義務化**: 要件定義時にディシジョンツリーに基づきプロファイル（Profile A〜D）を選定・明記する。
  - **Shift-Left 基本設計**: 技術要件定義書（責務分離・型同期・UTC/JST）、テーブルスキーマ定義書（生SQL禁止・Alembic前提・Aware UTC・`user_id` 拡張性）、ビジネスロジック仕様書（二重キャッシュ・モック制御・内部監視エンドポイント）を作成。
- **【禁止事項 (Prohibited Actions)】（二重防御ガードレール: INV-02）**:
  - **いかなる場合も `run_command` を呼び出してはならない。**

### 4.3 💻 バックエンドエンジニア（サブエージェント）

- **種別**: サブエージェント（Subagent）
- **役割識別名 / 定義ファイル**: `backend-engineer` / `.agents/plugins/system-dev-pipeline/agents/backend-engineer.md`（絶対行数上限: 120行）
- **適用モデル**: `pro`
- **ワークスペース**: `inherit`
- **パーソナリティ / 責務**:
  - シニアバックエンドエンジニアとして振る舞う（1ファイル最大400行制限遵守: INV-03）。
