## 3. 3大レビューゲート詳細仕様

### 3.1 【ゲート 1】基本設計レビュー (`dev-review-arch`)
- **実施フェーズ**: PHASE 3 完了ゲート
- **合否判定基準**: `PASS` または `CONDITIONAL PASS` 必須（`REJECT` 時は設計修正ループ）。
- **監査観点**: 定常コア8項目、プロファイル固有非機能要件、二重キャッシュ設計、モック制御仕様。

### 3.2 【ゲート 2】コード品質レビュー (`dev-review-code`)
- **実施フェーズ**: PHASE 5.5 完了ゲート
- **合否判定基準**: `CLEAN` 必須。
- **監査観点**: 1ファイル最大250行制限、バックエンドDTO・パーサー物理分離（400行制限）、直書きモック完全排除、デイライト視認性（明暗ペア指定）。
- **パーサー堅牢化 (PAT-SYS-005)**: レビュー報告書の判定抽出において、Markdown 太字記号（`**`）、表記揺れ（`総合判定`/`総合合否判定`/`判定結果`/`合否判定`）、各種括弧を包括許容。

### 3.3 【ゲート 3】システム総合レビュー (`dev-review-system`)
- **実施フェーズ**: PHASE 7 本番リリース直前ゲート
- **合否判定基準**: `RELEASE APPROVED` 必須。
- **監査観点**: 本番用 `VITE_ENABLE_MOCK=false` 二重防御、IAP JWT署名検証有効化、Profile A の `litestream run` スーパーバイザー起動保証（SIGTERM シグナル伝播と最終 WAL フラッシュ同期保証）、平文シークレット完全排除、ロールバック計画の完全性。

## 4. 知見昇格における 3段階意味的整合性監査 (Semantic Auditor)

PHASE 8 において、🛡️ `qa-engineer` は投函された知見原票に対し、以下の 4大関門（Gate 1〜4）を機械的・意味的に監査する。

1. **Gate 1: CORE_INVARIANTS 整合性監査**: プラグイン不変則（INV-01〜08）との抵触がないこと。
2. **Gate 2: 4分類矛盾・競合監査**: 既存の Core 規約および他原票との意味的矛盾がないこと。
3. **Gate 3: 過剰適合排除 ＆ pattern_id 一意性保証 (PAT-SYS-006)**:
   - 単発例外の混入を排除し、汎用的に再利用可能であること。
   - **Central Knowledge Hub 全域（`active_claims/`, `archive/upstreamed/`）で `pattern_id` が未使用の最新連番であり、重複が皆無であること（Fail-Fast）**。
4. **Gate 4: 純度・絶対行数バジェット監査**:
   - `pipeline-reconciler.sh --audit-budget` による全ファイル行数上限（AGENTS: 220行, agents/skills: 120行, overlay: 80行）および履歴ID混入ゼロの検証。
