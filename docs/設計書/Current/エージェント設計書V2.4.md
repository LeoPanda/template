## 1. 採択された基本方針 (V2.4 決定事項)

AI駆動システム開発ライフサイクル V2.4 におけるエージェント設計の基本方針は以下の通りである。

| 検討項目 | 採択方針 | 詳細内容 |
| :--- | :--- | :--- |
| **1. 開発思想** | **Shift-Left 前倒し組み込み** | 事後修正ではなく、初期スケルトン展開・設計・実装の初期段階から標準パターン（Alembic, IAP JWT, 責務分離, グランドデザイン, MSW等）を各エージェントが自律的に組み込む。 |
| **2. プロファイル適応** | **2層プロファイル体系の厳格遵守** | 📐 `architect` が第1層（定常コア8項目）および第2層（Profile A〜E）を設計し、各実装エージェントおよび 🛡️ `qa-engineer` が一貫してプロファイル仕様に準拠する。 |
| **3. フロントエンド規約** | **Anti-God Component & デイライト視認性** | 🎨 `ui-designer` に対し、**1ファイル最大250行制限（INV-03）**、Custom Hooks/Servicesへの物理分離、**コンポーネント内直書きモックの原則禁止（INV-04）**、および **Tailwind明暗ペアによるデイライト視認性担保（PAT-UI-001）** を強制適用する。 |
| **4. バックエンド規約** | **DTO・パーサー物理分離 & Alembic厳格運用** | 💻 `backend-engineer` に対し、**1ファイル最大400行制限およびDTO・パーサーの独立モジュール物理分離（PAT-CODE-001）**、生SQL手動DDLの絶対禁止（INV-05）、Alembicマイグレーション自動生成・適用、IAP JWT署名検証（INV-06）、二重キャッシュ実装を義務付ける。 |
| **5. 統括・状態管理** | **Single Writer & SemVer 2.0.0 統一** | 👑 `conductor` が初期スケルトン（`skeletons/`）を展開し、標準コマンドシーケンスと外部CLI非対話実行を管理、`PROJECT_STATE.md` を一元更新する（INV-01）。SemVer 3桁管理および改訂履歴表除外（PAT-REV-001）を徹底する。 |
| **6. レビュー・監査統制** | **機械的監査とZero Tolerance** | 🛡️ `qa-engineer` が250行/400行制限、直書きモック排除、実結合時サイレントモックフォールバック厳格禁止（Fail-Fast / PAT-MOCK-001）、本番モックOFF、IAP検証有効化を機械的・厳格に合否判定する（INV-07）。 |
| **7. 知見フィードバック** | **Central Knowledge Hub & 3段階意味的監査** | 👑 `conductor` が標準化知見原票（`CLAIM-*.md`）を `~/.gemini/knowledge-hub/inbox/` へ投函し、🛡️ `qa-engineer` が 3段階意味的整合性監査（New Gate 1〜4）を実行。`ask_question` 承認を経て `overlay/LOCAL_FEEDBACK_RULES.md` をクリーン再生成する。 |

## 4. エージェント別プロンプト定義と振る舞い規範 (V2.4)

### 4.1 👑 プロジェクトコンダクター (`conductor`)
- **役割**: オーケストレーション、フェーズ統括、Single Writer、標準コマンドシーケンス自動実行。
- **改定点**:
  - `PROJECT_STATE.md` を SemVer 3桁（`vMAJOR.MINOR.PATCH`）で管理し、システム改訂ルールの改定履歴表から除外（現在状態インジケータに特化）。
  - `dev-git-release` 発動時の先頭サニタイズにより、二重プレフィックス（`vV2.0`）を完全防御。

### 4.2 📐 設計・立案スペシャリスト (`architect`)
- **役割**: 2層プロファイル体系設計、4大基本設計書策定、API仕様書同期。
- **改定点**:
  - 画面仕様書におけるシステムバージョンバッジ例示を `v1.0.0` へ改定。
  - バックエンド DTO・パーサー物理分離（PAT-CODE-001）および外部API二重キャッシュ、モック透過制御（Fail-Fast）を基本設計書に明記。
  - **【二重防御ガードレール】いかなる場合も `run_command` を呼び出してはならない。**

### 4.3 💻 バックエンドエンジニア (`backend-engineer`)
- **役割**: FastAPI/Rust 実装、SQLAlchemy モデル、Alembic マイグレーション。
- **改定点**:
  - **DTO・パーサー物理分離と Anti-God Module (400行制限) 遵守 (PAT-CODE-001)**: DTO構造体およびパーサーを独立モジュールへ物理分離し、Controller層はオーケストレーションに専念。直書きモックを保持せずDBアクセス層やヘルパーへ委譲。
  - 環境変数 `APP_VERSION` は先頭 `v` なしの数値3桁（`1.0.0`）を厳守。

### 4.4 🎨 UI/UXデザイナー (`ui-designer`)
- **役割**: 画面仕様書策定、フロントエンド画面実装、MSW モック制御。
- **改定点**:
  - **デイライトモード視認性担保 (PAT-UI-001)**: Tailwind 明暗ペア（`dark:` 併記）またはデザイントークンを指定し、ダーク前提淡色カラーの単独直書きを禁止。
  - Anti-God Component（最大250行制限）および MSW モックハンドラー（直書きダミーデータ完全排除）の厳格運用。
  - システムバージョンバッジは `v1.0.0` 形式を表示。

### 4.5 🛡️ 品質監査スペシャリスト (`qa-engineer`)
- **役割**: 3大レビューゲート監査、ドキュメント相互整合性チェック、シナリオテスト自動実行、Wiki Maintainer (RCA)、Semantic Auditor。
- **改定点**:
  - PHASE 5.5 コード品質レビュー（`dev-review-code`）において、250行/400行制限に加え、DTO・パーサー分離検査（PAT-CODE-001）およびデイライト視認性検査（PAT-UI-001）を機械的実施。
  - PHASE 6 シナリオテストにおいて、Profile D 一時実ファイルDB動的プロビジョニング（PAT-TEST-001）を検証。
  - PHASE 7 システム総合レビュー（`dev-review-system`）において、Fail-Fast モック二重防御および起動時 Alembic 保証を監査。
  - **【コード直接改変禁止】** システム本体のプログラムコードに不具合を発見した場合は勝手に修正せず、原因調査結果とUnified Diff案をコンダクターへ報告する。
