## 1. 概要と目的

### 1.1 背景
LeoPanda 開発統合管理システム（LIDM）の開発・ウォークスルー検証（PHASE 5）において、登録プロジェクト一覧画面およびダッシュボード上のバージョン表示に以下の差異が観測された。

- `bicycle-maintenance` や `gps-overlay`: **`v2.0.0`** や **`v1.0.0`**（3桁セマンティックバージョニング形式）
- `garden-log` や `movie-log`: **`V1.0`** や **`V2.0`**（2桁メジャー・マイナー形式、大文字 `V`）

この表記差異の根本原因を調査した結果、単なる個別プロジェクトのタイポではなく、**公式パイプラインテンプレート（`system-dev-pipeline`）内の規約・テンプレート・改訂ルール間にセマンティックバージョニングとの多重な二重基準と表記揺れが存在すること**が判明した。

### 1.2 目的
本報告書は、公式セマンティックバージョニング（SemVer 2.0.0）を基準として、現行テンプレート（V2.3）および実稼働プロジェクトにおけるバージョニング規則の乖離を網羅的に分析し、**次期テンプレート本体（V2.4 / V3.0）のバージョンアップに向けた統一整理案および移行ロードマップを策定すること**を目的とする。

## 3. 公式セマンティックバージョニング (SemVer 2.0.0) の仕様原則

統一の基準となる [Semantic Versioning 2.0.0 (semver.org)](https://semver.org/lang/ja/) の基本原則を整理する。

1. **基本構造**: バージョン番号は **`X.Y.Z`** の形式をとる。
   - `X` (MAJOR): 後方互換性のない破壊的変更が行われた場合。
   - `Y` (MINOR): 後方互換性のある機能追加が行われた場合。
   - `Z` (PATCH): 後方互換性のあるバグ修正が行われた場合。
2. **数値形式**: 各要素は非負の整数であり、先頭に余分なゼロを配置してはならない（例: `1.0.0` は正常、`1.00.01` は不可）。
3. **プレフィックスの除外**: SemVer 仕様本体において、バージョン番号自体にプレフィックス（`v` や `V`）は含まれない（バージョンは純粋に `1.0.0`）。
4. **Git タグの慣習**: Git タグとして運用する場合は、小文字の **`vX.Y.Z`**（例: `v1.0.0`）を付与することが業界の事実上の標準（De facto Standard）である。

## 4. セマンティックバージョニングとの乖離分析（5大要因）

現行パイプラインテンプレート（`system-dev-pipeline`）を精査した結果、SemVer 仕様と乖離している箇所が以下の5点特定された。

```
【パイプラインにおけるバージョン表記の二重構造】
┌───────────────────────────────────────┬────────────────────────────────────────┐
│ 公式 SemVer (MAJOR.MINOR.PATCH: 3桁)  │ 独自規則 (Vn.m / n.m: 2桁)              │
├───────────────────────────────────────┼────────────────────────────────────────┤
│ ・package.json / Cargo.toml (1.0.0)   │ ① 改訂依頼番号の採番 (n.m.xxx)         │
│ ・FastAPI FastAPI(version="1.0.0")    │ ② 改訂ログ・レポートファイル名 (Vn.m)   │
│ ・Gitタグ・コミット (v1.0.0)          │ ③ 画面仕様書バッジ例示 (v1.0)          │
│ ・.env.template (APP_VERSION=1.0.0)   │ ④ 一部 .env の値 (APP_VERSION=V2.0/1.0)│
│ ・PIPELINE_MANIFEST.json (2.3.0)      │ ⑤ ドキュメント管理フォルダ (docs/Vn.m/) │
└───────────────────────────────────────┴────────────────────────────────────────┘
```

### 4.1 要因①: 改訂依頼番号の採番ルール (`システム改訂ルール.md` §2.3.2)
- **現行規則**: 改訂依頼番号のフォーマットを **`n.m.xxx`**（例: `1.2.001`, `2.0.003`）と規定。
  - `n.m`: システムバージョン番号（2桁）
  - `xxx`: 通し番号（連番3桁）
- **乖離点**:
  システムバージョンを「2桁（`n.m`）」と固定定義している。もしシステムバージョンが SemVer（`1.0.0`）の場合、`1.0.0.001` と4階層になってしまうため、エージェントが改訂時に `.env` や `PROJECT_STATE.md` を強制的に `1.0` や `V2.0`（2桁）へと書き換える構造的誘因となっていた。

### 4.2 要因②: 改訂作業ログ・成果物のファイル命名規則 (`システム改訂ルール.md` §2.3.2, §2.4, §2.5)
- **現行規則**: すべて **`Vn.m`**（大文字 `V` ＋ 2桁）を強制。
  - 改訂ログディレクトリ: `/revise-log/Vn.m/`
  - 改訂レビュー文書: `Vn.m_revise-review_xxx.md`
  - シナリオテストレポート: `docs/plans/scenario-test/Vn.mシナリオテスト結果レポート.md`
  - 改訂完了レポート: `docs/Vn.m改訂レポート.md`
- **乖離点**:
  パッチバージョン（`.PATCH`）の概念がファイル名体系から完全に排除されており、メジャー・マイナー（`V1.0`, `V2.0`）単位でのみ管理する前提となっている。

### 4.3 要因③: ドキュメント管理規約のバージョン別フォルダ名 (`AGENTS.md` 第10項)
- **現行規則**:
  > 「**バージョン別フォルダ分離 (Vn.m)**: サブフォルダはバージョン単位（`V1.0`, `V2.0`, `V2.1`, `V2.2`, `V2.3` 等）に分離して管理する。」
- **乖離点**:
  ドキュメントのライフサイクル管理において 2桁形式（`Vn.m`）が例示・規定されているため、Conductor や Architect がプロジェクト全体のバージョン表記もこれに倣って `V1.0` や `V2.0` と設定する引き金となった。

### 4.4 要因④: 画面仕様書テンプレートのシステムバージョンバッジ例示 (`templates/画面仕様書.md` §134)
- **現行規則**:
  > 「左端: アプリケーションロゴ + システム名称 + システムバージョンバッジ (`v1.0`)」
- **乖離点**:
  UI 設計書の基準仕様において `v1.0`（2桁）が指定されている。一方で、実装スケルトンコード（`Header.tsx` や `FramelessTitleBar.tsx`）では `v1.0.0`（3桁）がデフォルト値となっており、設計書とコード間で齟齬があった。

### 4.5 要因⑤: 環境変数 `.env` の値の揺れと Git タグ二重プレフィックスリスク (`dev-git-release`)
- **現行規則**:
  - `templates/.env.template`: `APP_VERSION=1.0.0`（数値3桁）
  - `dev-git-release/SKILL.md`:
    ```bash
    VERSION=$(grep -E '^(APP_)?VERSION=' .env | cut -d '=' -f2 | tr -d '"' | tr -d "'")
    git commit -m "Release v${VERSION}"
    git tag -a "v${VERSION}" -m "Release v${VERSION}"
    ```
- **乖離点とリスク**:
  `dev-git-release` は環境変数の値の先頭に `v` を自動付与して Git タグを生成する。もし `.env` に `APP_VERSION=V2.0`（大文字 `V` 付き）と記述されていると、Git タグが **`vV2.0`** という不正な二重プレフィックスになる脆弱性を抱えている。

## 5. 乖離が生じた歴史的背景と構造的原因

なぜテンプレート内でこのような二重構造が発生したのか、その理由を分析した。

1. **エコシステムの要請（SemVer 厳格主義）**:
   `npm`、`cargo`、`pip`、Dockerイメージタグ、GitHub Releases 等のツールチェーンは、SemVer（`1.0.0`）でなければバリデーションエラーを起こすため、コード側は厳格に 3桁を採用した。
2. **人間・ドキュメント運用の簡便性（2桁への丸め）**:
   フォルダ名やファイル名、日々の改訂番号において、パッチバージョンまで含めると `docs/設計書/V1.0.0/` や `1.0.0.001` と冗長になり可読性が落ちるため、ドキュメント管理および改訂ルールでは意図的にメジャー・マイナー（`Vn.m`）に丸めて運用を簡略化した。
3. **二系統のルールの未統合**:
   「システムのソフトウェアバージョン」と「ドキュメント・改訂単位の呼称」の境界線が曖昧なままルールが起票されたため、エージェントがドキュメント規則（`Vn.m`）をシステム全体のバージョン（`APP_VERSION`）に逆流させてしまった。

## 6. テンプレート本体 (system-dev-pipeline) 統一整理案

次期テンプレート改訂に向け、以下の3案を比較検討した。

### 6.1 比較検討

| 観点 | 案1: 完全 SemVer 3桁統一案 | 案2: 2層分離維持案 | 案3: SemVer基準・改訂番号拡張案（推奨） |
| :--- | :--- | :--- | :--- |
| **システムバージョン** | `1.0.0` (SemVer) | `1.0.0` (SemVer) | **`1.0.0` (SemVer)** |
| **Git タグ** | `v1.0.0` | `v1.0.0` | **`v1.0.0`** |
| **PROJECT_STATE** | `v1.0.0` | `v1.0.0` | **`v1.0.0`** |
| **改訂依頼番号** | `1.0.0.001` (4桁化・冗長) | `1.0.001` (変則) | **`1.0.001`**（`MAJOR.MINOR` + 通番） |
| **ドキュメントフォルダ** | `docs/設計書/v1.0.0/` | `docs/設計書/V1.0/` | **`docs/設計書/v1.0/`**（小文字統一） |
| **評価** | フォルダ名や改訂番号が過度に長くなり可読性が低下する。 | 二重基準が残り、エージェントの誤認リスクが残る。 | **最も自然で、システムは厳格なSemVer、ドキュメント・通番はマイナー束ねとして両立可能。** |

### 6.2 推奨案（案3）の標準仕様マッピング

次期テンプレートにおいて採用すべき標準仕様を以下のように明確化する。

#### ① システム・ソフトウェアバージョン
- **標準形式**: **`MAJOR.MINOR.PATCH`**（数値3桁、先頭に `v` は付けない）
- **適用場所**:
  - `.env`: `APP_VERSION=1.0.0`
  - `package.json`: `"version": "1.0.0"`
  - `Cargo.toml`: `version = "1.0.0"`
  - `main.py` (FastAPI): `version="1.0.0"`

#### ② プロジェクト管理・Git・UI 表示
- **標準形式**: **`vMAJOR.MINOR.PATCH`**（小文字の `v` ＋ 数値3桁）
- **適用場所**:
  - `PROJECT_STATE.md`: `- **現行バージョン**: v1.0.0`
  - Git コミット: `Release v1.0.0`
  - Git タグ: `v1.0.0`
  - UI バッジ（ヘッダー / タイトルバー）: `v1.0.0`

#### ③ 改訂依頼番号の採番
- **標準形式**: **`MAJOR.MINOR.xxx`**（例: `1.0.001`, `1.0.002`, `2.0.001`）
  - パッチ改訂であっても、メジャー・マイナーのリリースライン（`1.0` 系）に対する通番として `xxx`（3桁連番）を割り当てる。
  - これにより、番号の肥大化（`1.0.0.001`）を防ぎつつ、改訂履歴の整然としたソート性を維持する。

#### ④ ドキュメント管理・改訂ログの命名
- **標準形式**: **`vMAJOR.MINOR`**（小文字 `v` ＋ 2桁）
  - 大文字 `V` を廃止し、すべて小文字 **`v`** に統一する。
  - 適用場所:
    - `docs/設計書/v1.0/`, `docs/設計書/v2.0/`
    - `/revise-log/v1.0/v1.0_revise-review_001.md`
    - `docs/plans/scenario-test/v1.0シナリオテスト結果レポート.md`
    - `docs/v1.0改訂レポート.md`

## 7. ダッシュボード (LIDM) における先行対応策（過渡期吸収）

テンプレート本体のバージョンアップ前に、LIDM ダッシュボード側で過去プロジェクトの表記揺れを吸収し、画面上を公式 SemVer 準拠の美しい表示で統一するためのパーサー拡張仕様を策定する。

### 7.1 正規化パーサーロジック (`src-tauri/src/core/parser.rs`)
`PROJECT_STATE.md` から抽出した `app_version` に対して、以下の正規化フィルタ（Normalize）を適用する。

```rust
pub fn normalize_version_string(raw: &str) -> String {
    let trimmed = raw.trim();
    if trimmed.is_empty() {
        return "v1.0.0".to_string();
    }

    // 1. 先頭の "v" または "V" を除去して純粋なバージョン番号部分を抽出
    let clean = trimmed.strip_prefix('v')
        .or_else(|| trimmed.strip_prefix('V'))
        .unwrap_or(trimmed);

    // 2. ドット分割
    let parts: Vec<&str> = clean.split('.').collect();
    match parts.len() {
        1 => {
            // 例: "1" -> "v1.0.0"
            format!("v{}.0.0", parts[0])
        }
        2 => {
            // 例: "1.0" -> "v1.0.0"
            format!("v{}.{}.0", parts[0], parts[1])
        }
        _ => {
            // 例: "1.0.0" -> "v1.0.0" (先頭に小文字vを付与して整形)
            format!("v{}", clean)
        }
    }
}
```

### 7.2 期待される効果
- `garden-log` (`V1.0`) ➔ **`v1.0.0`**
- `movie-log` (`V2.0`) ➔ **`v2.0.0`**
- `gps-overlay` (`v1.0.0`) ➔ **`v1.0.0`**
- `bicycle-maintenance` (`v2.0.0`) ➔ **`v2.0.0`**
- 過去プロジェクトの元ファイルを一切改変することなく、LIDM 上の表示が完全に統一される。

## 9. 結論

本調査により、プロジェクト間のバージョン表記差異は偶発的なものではなく、**「SemVer 3桁のソフトウェアエコシステム」と「Vn.m 2桁のドキュメント・改訂運用規則」の二重構造**に起因することが明らかとなった。

本報告書で提示した「**システム・Git は厳格 SemVer（`vX.Y.Z`）、改訂通番・ドキュメントはマイナー集約（`vX.Y`）**」という整理方針を採用することで、システムの互換性とドキュメント運用の簡潔さを両立した美しい標準規約を実現できる。

本検討結果を `docs/reports/` に永続化し、次期テンプレートバージョンアップ時の確実なインプットとする。
