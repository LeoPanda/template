# V2.0 設計の評価と課題

本文書は、AI駆動システム開発ライフサイクル V2.0（マルチエージェント協調・状態一元管理・自己進化型ナレッジループ）の確定設計全体を俯瞰し、アーキテクチャとしてのストロングポイント（構造的強み）および弱点・潜在的リスク（課題と緩和策）を客観的・多角的に評価・集約した技術評価書・課題整理書である。

---

## 1. 総合評価サマリー

V2.0 アーキテクチャは、従来の「単一エージェント＋手順的スキル」によるパイプライン運用から、**「コンダクター＋専門サブエージェント（architect, ui-designer, qa-engineer）＋一元管理状態票（PROJECT_STATE.md）」** によるマルチエージェント協調体制へと抜本的に進化している。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           V2.0 設計全体の評価サマリー                       │
├──────────────────────────────────────┬──────────────────────────────────────┤
│ 🏆 ストロングポイント (Strengths)     │ ⚠️ 弱点・潜在的リスク (Weaknesses)   │
├──────────────────────────────────────┼──────────────────────────────────────┤
│ 1. コンテキストノイズの徹底隔離      │ 1. コンダクターへの責務集中 (SPOF)   │

│ 4. 動的登録フォールバックの耐障害性  │ 4. コンテナ内外の実行境界の曖昧さ    │
```

## 2. ストロングポイント（設計の強み）

### 2.1 コンテキストノイズの徹底隔離（Context Pollution Prevention）
- **詳細**:
  - 画面のCSS/UI微調整やスタイリング試行錯誤（`ui-designer`）、テスト実行ログの解析と自律修復反復（`qa-engineer`）、長文のテーブルスキーマやロジック仕様設計（`architect`）といった、大量のトークンを消費しコンテキストを汚染しやすい専門作業をサブエージェントへ完全に委譲・局所化している。
- **効果**:
  - メインエージェント（コンダクター）のコンテキスト履歴を常にコンパクトかつ高抽象度に保つことができる。
  - AI開発において致命的となる「トークン長過大による以前の指示忘れ」「幻覚（Hallucination）」「誤認・脱線」を構造的に排除している。

### 2.2 Single Writer 原則による状態管理の破綻防止
- **詳細**:
  - プロジェクト進行状態を管理する `PROJECT_STATE.md` への書き込み権限を **コンダクター1人の専任（Single Writer）** とし、サブエージェントは標準完了サマリ（メッセージ）を返却するのみとした。
- **効果**:
  - 複数エージェントが同時にファイルを上書きすることによる競合（コンフリクト）、不完全な書き込み、チェックボックスや履歴の破損を原理的に防いでいる。
  - セッションの中断・再開時にも、コンダクターが `PROJECT_STATE.md` を1ファイル読み込むだけで、直ちに正確な進行フェーズと未決事項（Open Questions）を復元できる。

### 2.3 プラットフォーム仕様に即した二重防御ガードレール
- **詳細**:
  - Antigravity ランタイムの仕様上、ドキュメント編集のために `enable_write_tools: true` を付与すると `run_command` も物理的に利用可能となってしまう制約を特定。
  - これに対し、フラグレベルの許可とシステムプロンプト最上位での厳格な禁止命令（Prohibited Actions）を組み合わせた「二重防御ガードレール」を採用した。
- **効果**:
  - `architect` による不用意なコマンド実行を確実に遮断し、`ui-designer` や `qa-engineer` に対しても破壊的操作（Git不正コミット、本番デプロイ、DB強制上書き、プログラムコード直接改変）を厳格に封殺している。

### 2.4 耐障害性を担保する動的登録フォールバック（Dynamic Fallback）機構
- **詳細**:
  - プラグイン静的定義（`plugin.json`）の読み込み不良、セッションキャッシュの遅延、環境差異などにより、エージェントが `<subagents>` 一覧に未登録である場合を想定。
  - コンダクターが自律的に `.agents/plugins/system-dev-pipeline/agents/*.md` を読み込んで Frontmatter をパースし、`define_subagent` を発行して動的登録する自律リカバリ機構を仕様化した。
- **効果**:
  - 実行環境やセッション状態の差異によって開発パイプラインが停止するリスクを排除し、極めて高いレジリエンス（障害回復力）を実現している。

### 2.5 二層分離型の自己進化ナレッジサイクル（Two-Tier Knowledge Architecture）
- **詳細**:
  - エージェントが開発・改訂を通じて獲得した知見を、「プロジェクト固有知見（Tier 1）」と「全プロジェクト共通のテンプレート昇格候補（Tier 2）」に厳密に仕分け。
  - 開発中は一時バッファ（`./TEMPLATE_PROMOTIONS.md`）に蓄積し、PHASE 8（初回リリース）および改訂完了時にユーザーの明示的承認ゲートを経てテンプレート（`.agents/plugins/system-dev-pipeline/`）へ反映する運用基準を確立した。
- **効果**:
  - 個別プロジェクトの特殊事情がテンプレートに混入してルールが汚染されるのを防ぎつつ、エージェントプロンプトの肥大化を抑え、開発を重ねるごとにテンプレート自体が賢く進化するループを構築した。

### 2.6 Docker再構成ルールの徹底によるデバッグロスの排除
- **詳細**:
  - ソースコードや設定ファイルの修正後は、必ず `docker compose down` → `docker compose up --build -d` を実行してコンテナを再構成することを全フェーズ・改訂手順・ルールファイルに明文化・規約化した。
- **効果**:
  - AI開発で最も頻発する「コードを修正したがコンテナに反映されておらず、古い状態で動作確認して延々と無駄なデバッグや試行錯誤を繰り返す」という重大な時間的損失を未然に防止している。

## 3. 弱点・潜在的リスクと緩和策（課題と処方箋）

### 弱点 1: コンダクターへの責務集中と単一障害点（Single Point of Failure）
- **潜在的リスク**:
  - 全体進行、ユーザー対話、状態一元管理（`PROJECT_STATE.md` 更新）、Docker環境構築、**バックエンドAPIおよびビジネスロジック実装（PHASE 4）**、Git操作、デプロイがすべてコンダクターに集中している。
  - バックエンド実装が大規模または複雑なシステムの場合、コンダクター自身のコンテキストトークンが肥大化し、オーケストレーションや進行管理の推論精度が低下する懸念がある。
- **緩和策・処方箋**:
  1. **タスクの細分化と段階的コミット**: PHASE 4 のバックエンド実装時、一度に全体を実装せず、データモデル → リポジトリ → サービス → エンドポイントと細かく分割して実装・検証を進める。
  2. **コンテキストリフレッシュの運用指針**: 長時間の実装作業でコンテキストが逼迫した際は、コンダクターが `PROJECT_STATE.md` を最新状態に保存した上で、セッションを安全にリフレッシュできる手順を確立する。
  3. **将来構想（V2.1以降）**: バックエンド実装の規模に応じて、専門の `backend-engineer` サブエージェントの新設を検討する。

### 弱点 2: 多数の承認ゲートによる「承認疲労（Approval Fatigue）」
- **潜在的リスク**:
  - 新規開発（PHASE 2, 3, 5, 6, 7, 8）および改訂サイクルの各ターン（Plan作成、テスト結果、本番デプロイ、知見昇格）において、厳格な「明示的承認ゲート」を要求している。
  - ユーザーが確認すべきポイントが多すぎると、内容を精査せずに形骸的に「承認」と即答してしまい、ゲート本来の品質担保機能が失われる恐れがある。
- **緩和策・処方箋**:
  1. **「3行要約サマリ」の提示規約**: コンダクターがユーザーに承認を求める際、長大な設計書やログをそのまま見せるのではなく、必ず冒頭に **「①何を変更したか」「②残存するリスク・未決事項」「③ユーザー判断を仰ぎたい論点」** を3〜5行で要約提示するプロンプト規約を策定する。
  2. **軽微修正のスキップ指針**: 誤植修正やスタイル調整など極めて軽微な改訂ターンでは、シナリオテストを省略可能とするなど、運用の柔軟性を認める。

### 3.3 サブエージェント呼び出し時の引数解決における誤解リスク
- **潜在的リスク**:
  - 「Frontmatter の `default_*` が自動適用される」という記述があると、コンダクターが引数を省略して呼び出し、Antigravity ランタイムがプラットフォーム既定の `'inherit'`（親エージェントの設定）にフォールバックしてしまう。親が Flash で動作している場合、`architect` や `qa-engineer` が意図せず Flash で動いて推論精度が落ちるリスクがある。
- **緩和策・処方箋**:
  1. **引数明示渡しの義務付け**: コンダクターのプロンプトおよび仕様書において、「`invoke_subagent` 実行時、コンダクターは Frontmatter の `default_model`（`pro` 等）および `default_workspace`（`inherit`）を読み取り、**必ず明示的に引数として渡す**」ことをルール化・徹底する。

### 3.4 ホストOSとDockerコンテナ内のコマンド実行境界の曖昧さ
- **潜在的リスク**:
  - `ui-designer` や `qa-engineer` がビルドやテストのコマンドを実行する際、ホストOS側で実行するのかコンテナ内（`docker compose exec`）で実行するのかが不明確な場合、Node.js や Python のバージョン不一致やパスの不整合が生じる可能性がある。
- **緩和策・処方箋**:
  1. **コンテナ内実行の原則化**: テスト実行（`pytest`, `npm test` 等）および依存関係インストールは、原則として `docker compose exec <service> <command>` を通じて実行することを推奨・明文化する。

## 4. 今後のロードマップと改善課題

本設計（V2.0）の実装完了後、実際の開発プロジェクトへの適用を通じて検証し、将来のバージョン（V2.1以降）に向けて以下の改善を検討する：

1. **実案件でのパイプライン試行と測定**:
   - サブエージェント導入前後でのコンテキスト消費量（トークン効率）およびエラー発生率の定量比較。
2. **コンダクター専用プロンプト（`conductor.md`）の独立化**:
   - 現在はルールファイル群（`.agents/rules/` や `rules/dev-process-standards.md`）に分散しているコンダクターの動作規範を、より洗練されたオーケストレーション仕様として体系化。
3. **バックエンド専門エージェントの要否判定**:
   - 複雑なビジネスロジックや大規模マイクロサービス開発における `backend-engineer` の新設検討。
