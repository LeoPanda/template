# サブエージェント活用の検討課題

## 1. 背景と目的

これまでの開発プロジェクトでは、フェーズ分け（PHASE 1〜8）、スキル（Skills）、およびテンプレートを活用したパイプライン化を推進し、開発プロセスの標準化と自動化を試行してきた。

この取り組みをさらに一段階進化させるため、**「サブエージェント（Subagent）」** を導入・活用し、責務の分散と知見の蓄積、対話コンテキストの最適化を図る方策を検討する。

---

## 2. エージェント活用のメリット

サブエージェントアーキテクチャの導入により期待される主要なメリットは以下の通りである。

1. **システム間・プロジェクト間の統一感**
   - 共通定義された専門エージェントを各プロジェクトで再利用することで、成果物のトーン＆マナーや設計・実装基準に一貫性を担保できる。
2. **作業ごとの知見蓄積（ラーニング＆ナレッジ化）**
   - 役割（ロール）ごとに過去の誤りやベストプラクティスをプロンプト・ルール・参照資料としてフィードバック・蓄積でき、成果物の品質向上と生産性の向上が見込める。
3. **対話コンテキスト（履歴）のノイズ分離と精度向上（最大の効果）**
   - 画面のCSS/UI微調整、テスト実行ログ、Gitコマンド実行履歴など、トークン消費が激しくノイズになりやすい作業をサブエージェントに隔離・局所化する。
   - メインエージェントのコンテキストをクリーンに保ち、コンテキスト長過大による指示忘れ・誤認を予防する。
4. **タスクの並列処理**
   - 独立した作業（例: 画面実装とAPI仕様レビュー、複数観点でのドキュメント監査）の同時並行実行が可能となる。

## 3. サブエージェントの役割候補と再編方針

### 3.1 当初の役割候補（9つの役割）

- **品質管理**: ドキュメント整合性チェック、システム冗長性チェック、リスクチェック
- **画面デザイナー**: UI/UX設計、フロントエンドコンポーネント実装
- **プロジェクトの進捗管理**: 現在作業中のフェーズと作業内容の管理
- **git管理**: ブランチ運用、コミット、リリース作業
- **デプロイ管理**: 本番環境適用、インフラ設定検証
- **立案ヘルパー**: 構想立案、技術要件、スキーマデザイン、ビジネスロジック等の主要文書作成
- **スルーテストの実施と管理**: シナリオテスト計画、テスト実行、ログ解析・修復ループ
- **プロジェクトコンダクター**: 全体状況の把握、タスクの示唆、実行漏れ防止
- **Q&A対応アドバイザー**: 仕様確認、アイデア収集、壁打ち

### 3.2 役割の再編・集約方針

役割を細分化しすぎると、エージェント間の文脈引き継ぎコスト（オーケストレーションオーバーヘッド）が増大し、ユーザーが対話先や指示経路に迷うリスクが生じる。
そのため、「自律的推論・対話が必要な領域（エージェント）」と「決定論的・手順通りの領域（スキル/ツール）」を切り分け、以下のように**4〜5のコア役割**へ集約・再編することを基本方針とする。

```
                    ┌────────────────────────────┐
                    │ 👑 1. プロジェクトコンダクター   │
                    │    (メイン対話 / 進行 / Q&A) │
                    └──────────────┬─────────────┘
                                   │ 指示 / 委譲
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
    ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
    │ 📐 2. 設計・立案  │   │ 🎨 3. UI/UX      │   │ 🛡️ 4. 品質・テスト│
    │   スペシャリスト │   │   デザイナー     │   │   & QA          │
    │(要件/スキーマ/    │   │(画面設計/コンポ  │   │(整合性/スルー    │
    │ ロジック設計)    │   │ ーネント実装)    │   │ テスト/リスク)   │
    └──────────────────┘   └──────────────────┘   └──────────────────┘
            │                      │                      │
            └──────────────────────┼──────────────────────┘
                                   ▼ 成果物反映
                           ┌──────────────────┐
                           │ ⚙️ ツール/スキル   │
                           │ ・Git管理        │
                           │ ・デプロイ管理   │
                           └──────────────────┘
```

| 集約後の役割 | 内包する元の役割 | 形態 | 特徴・期待される動作 |
| :--- | :--- | :--- | :--- |
| **👑 プロジェクトコンダクター** | ・プロジェクトコンダクター<br>・進捗管理<br>・Q&A対応アドバイザー | メインエージェント | ユーザーと直接対話する司令塔。現在のフェーズ・タスクを把握し、壁打ちに応じつつ、重い作業をサブエージェントに委譲する。 |
| **📐 設計・立案スペシャリスト** | ・立案ヘルパー | サブエージェント | 要件定義、DBスキーマ（ER図）、API設計、ビジネスロジック等のドキュメント作成に特化。高精度な推論モデルを適用。 |
| **🎨 画面デザイナー / FE** | ・画面デザイナー | サブエージェント | UIデザイン、コンポーネント実装、CSS調整に特化。大量のデザイン試行錯誤トークンを隔離。 |
| **🛡️ 品質・テスト・監査 (QA)** | ・品質管理<br>・スルーテスト実施と管理 | サブエージェント | ドキュメント相互整合性チェック、テスト自動実行・ログ解析・修復ループ、批判的コード監査を担当。 |
| **⚙️ Git / デプロイ運用** | ・git管理<br>・デプロイ管理 | スキル / ツール | 決定論的（Deterministic）な手順・コマンド実行。コンダクターまたは各エージェントが必要に応じて呼び出す。 |

### 課題2: プロジェクト状態（State）の一元管理機構 【完了】

- 状態管理用ファイル（プロジェクトルート直下の `PROJECT_STATE.md`）の仕様策定。
- Single Writer 原則（コンダクター専任）によるライフサイクル・更新ロジックの定義。
