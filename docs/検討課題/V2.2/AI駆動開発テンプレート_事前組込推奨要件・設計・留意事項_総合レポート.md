# AI駆動開発テンプレート 事前組込推奨要件・設計・留意事項 総合レポート

## 1. エグゼクティブサマリ

本レポートは、AI駆動テンプレート（Antigravity 2.0 / system-dev-pipeline）を利用して生成・運用された複数のシステム評価レポート（`bicycle-log`、`Movie Log`、`Gardening Log`、`bicycle-maintenance`）を横断的に分析し、**「新規システム生成時点でテンプレートにあらかじめ組み込んでおくべき技術要件、設計パターン、および運用上の留意事項」** を整理・体系化したものです。

分析の結果、生成されたシステムはいずれも「Cloud Run × Litestream × SQLite」という高コストパフォーマンスな構成や、整然としたドキュメントガバナンス、洗練されたUI/UXなど非常に高い初期品質を誇っています。一方で、全プロジェクトに共通して以下の**「AI駆動開発特有の技術的負債・課題」**が後工程で顕在化していることが判明しました。

1. **フロントエンドの「God Component」化**: 1ファイルへのロジック・UIの集中（数百〜数千行）。
2. **データベース運用の脆弱性**: マイグレーションツール（Alembic等）の未導入による手動DDLリスク、SQLite特有の型・タイムゾーン差異、単一ライター制約。
3. **セキュリティ・認可層の形骸化**: IAP前提によるバックエンド側トークン検証（JWT検証）やテナント/ユーザー分離の欠如。
4. **型安全性・スキーマ同期の断片化**: バックエンド（Pydantic）とフロントエンド（TypeScript）の手動型同期によるタイポ・不整合リスク。
5. **テスト・CI/CDパイプラインの不足**: ローカル実行・手動デプロイ依存による自動回帰防止の欠如。

これらを初期生成テンプレートに「標準機能・ガードレール」としてあらかじめ組み込むことで、AIエージェントによるコード生成の品質を劇的に高め、リビルドや運用初期のトラブルを未然に防止します。

## 3. テンプレートに事前組込すべき「技術要件・アーキテクチャ設計」

テンプレートが生成する初期コードベースに対し、最初から組み込んでおくべき主要なアーキテクチャ要件です。

### 3.1 データベース層：Alembic統合 & SQLite接続安全化

1. **Alembicマイグレーションのビルトイン**:
   - `create_all()` や手動SQLによるテーブル初期化を禁止し、最初から `alembic init` された構成を標準配備。
   - `entrypoint.sh` において、「Litestreamリストア ➔ `alembic upgrade head` ➔ アプリ起動」の起動シーケンスを完全テンプレート化。
2. **SQLite堅牢化設定**:
   - WALモードの同時アクセス競合を防ぐため、接続パラメータに `timeout=5000`（5秒）および外部キー制約有効化（`PRAGMA foreign_keys = ON;`）をデフォルトで強制。
   - Datetime型は常に「UTC / ISO8601文字列」として扱い、Pydantic v2での `NaiveDatetime` 変換エラーを防止する共通カスタム型を用意。

### 3.2 セキュリティ & 認証層：IAP JWT二重防御

1. **IAP認証ミドルウェア / 依存性注入の標準化**:
   - アプリケーション側で `X-Goog-IAP-JWT-Assertion` ヘッダーを検証する `get_current_user` を最初から実装（ローカル開発環境では `DEBUG=True` 時のみモックに自動切替）。
2. **シークレット & 環境変数の厳格バリデーション**:
   - Pydantic Settings に `@field_validator` をあらかじめ仕込み、Secret Manager から注入された値にプレースホルダー文字列や `[...]` などの不要記号が含まれていた場合、起動時に明快なエラーを出してフェイルセーフに停止する機構を標準化。

### 3.3 型安全性 & APIクライアント：OpenAPI同期自動化

1. **TypeScript型定義自動生成パイプライン**:
   - `package.json` に `openapi-typescript`（または `orval`）をプリセット。
   - バックエンドの FastAPI ルーティングから `npm run codegen` 一発でフロントエンド側の TypeScript 型および API クライアントコードを生成する仕組みを初期配備。

### 3.4 外部APIキャッシング & レジリエンス

1. **二重キャッシュ機構（DBキャッシュ ＆ インメモリTTLキャッシュ）**:
   - 外部連携（Google Places, TMDb, Open-Meteo, Strava等）が発生するシステム向けに、`cachetools`（TTLキャッシュ）またはキャッシュ用テーブルを共通モジュールとして事前組み込み。
   - 同一クエリの重複リクエストを抑止し、外部APIコストの削減とレスポンス高速化、レート制限回避を保証。

## 4. テンプレートに事前組込すべき「フロントエンド設計規範」

AIエージェントが最も陥りやすい **「単一巨大ファイル（God Component）の生成」** を構造的に防ぐためのガイドラインとディレクトリテンプレートです。

### 4.1 ディレクトリ構造と責務分離ルール

テンプレート生成時点で、以下のディレクトリ構成と「1ファイル最大250行ルール」を明文化して配置します。

```text
frontend/src/
├── components/
│   ├── layout/          # TopBar, Navigation, Sidebar
│   ├── common/          # Button, Modal, WearGauge, Badge, ThemeToggle
│   └── domain/          # 各業務ドメイン固有のプレゼンテーションコンポーネント
├── hooks/               # 状態管理・副作用・ビジネスロジック（カスタムフック）
│   ├── useAuth.ts
│   ├── useModal.ts
│   └── use[Domain].ts   # 例: useBikes, useMovies, usePlants
├── services/            # API通信・データ加工（Fetchラッパー）
│   └── apiClient.ts
├── types/               # 自動生成型定義 (api.d.ts)
└── utils/               # 画像圧縮(Canvas WebP)、日付フォーマット等
```

### 4.2 フロントエンド共通機能の事前実装

1. **クライアントサイド画像事前最適化ユーティリティ (`useImageCompressor`)**:
   - HTML5 Canvas を用いた WebP 変換、リサイズ、正方形クロップ処理を共通関数として提供。
2. **3モードテーマ切り替え (`useTheme`)**:
   - Tailwind CSS の `dark` クラスと OS 設定追従（`prefers-color-scheme`）を制御する共通フック。
3. **PWA (Progressive Web App) 基盤**:
   - `vite-plugin-pwa` を標準導入し、Web App Manifest と Service Worker の雛形を組み込んでおく（屋外利用やオフライン下書き保存への容易な拡張性）。

## 5. テンプレートに事前組込すべき「テスト・CI/CD・運用要件」

### 5.1 CI/CD パイプライン（GitHub Actions ワークフロー）

リポジトリ生成時に `.github/workflows/` 配下へ以下のワークフローをあらかじめ同梱します。

1. **`ci.yml`（PR / Push 検証）**:
   - **Backend**: `ruff check` + `pytest`（単体・APIテスト）
   - **Frontend**: `npm run lint` + `npm run type-check` + `npm run build`
   - **E2E**: Playwright（ヘッドレスモード実行、主要シナリオ）
2. **`deploy.yml`（本番自動デプロイ）**:
   - `main` ブランチマージ時に、Google Artifact Registry への Docker ビルドプッシュおよび Cloud Run への安全デプロイを自動実行。

### 5.2 バックエンド単体テストテンプレート

- `tests/test_api_smoke.py`: 全エンドポイントに対するステータスコード 200/401/422 のスモークテスト。
- `conftest.py`: テスト用インメモリ SQLite または隔離 DB を自動生成・ロールバックする pytest フィクスチャ。

### 5.3 運用・可観測性（Litestream ヘルスチェック）

- `GET /api/internal/health`: コンテナ死活監視。
- `GET /api/internal/litestream/status`: 最新の WAL レプリケーションラグ（最終同期時刻）を検査し、GCS への同期サイレント障害を早期検知するエンドポイントの標準化。
