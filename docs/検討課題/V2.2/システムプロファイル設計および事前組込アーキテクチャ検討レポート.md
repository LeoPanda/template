## 1. 背景と目的

### 1.1 背景
AI駆動システム開発テンプレート V2.1 では、開発の節目に3大レビューシステム（基本設計レビュー、コード品質レビュー、システム総合レビュー）を配置し、品質低下やAI特有の局所最適パッチを防止する仕組みを整備した。その際、[レビューシステム設計書.md](../../v2.1/レビューシステム設計書.md) において、システムの規模や稼働環境に応じた **「定常的観点（普遍的コア）」** と **「可変的観点（展開プロファイル別観点）」** の二層モデルを提唱した。

しかしながら、V2.1 におけるプロファイルは主に **「レビュー（後工程の監査・合否判定）」** での利用に留まっており、要件定義書での宣言や技術要件書での概況記述にとどまっていた。そのため、実際に設計やコード生成を行う段階（PHASE 2 要件定義、PHASE 3 基本設計、PHASE 4 環境・システム構築）では、各エージェントの自律生成に委ねられる部分が大きく、生成されるコードや設計にばらつきが生じていた。

### 1.2 総合評価レポートから得られた教訓
実際にこのテンプレートを用いて開発・運用された4つの小規模Webシステム（`bicycle-log`、`Movie Log`、`Gardening Log`、`bicycle-maintenance`）の横断分析レポート（[AI駆動開発テンプレート_事前組込推奨要件・設計・留意事項_総合レポート.md](./AI駆動開発テンプレート_事前組込推奨要件・設計・留意事項_総合レポート.md)）によれば、「Cloud Run × Litestream × SQLite」という高コストパフォーマンスな構成で高い初期品質を達成した反面、全プロジェクトで共通する以下の**「後工程・運用期に顕在化する技術的負債」**が確認された：

1. **フロントエンドの「God Component」化**: 1ファイルへのUI・状態・通信の集中（数百〜数千行）。
2. **データベース運用の脆弱性**: Alembicマイグレーション未導入（手動DDL乱立）、SQLiteの型・タイムゾーン差異、単一ライター競合。
3. **セキュリティ・認可層の形骸化**: IAP前提によるバックエンド側JWT署名検証の未実装、ローカル用モックの放置、環境変数の不備。
4. **型安全性・スキーマ同期の断片化**: PydanticとTypeScriptの手動型定義による二重管理・タイポ。
5. **テスト・CI/CDパイプラインの不足**: バックエンド単体テスト（pytest）の不足、GitHub Actions自動CI/CD未整備。
6. **可観測性・外部連携耐性の不足**: Litestream同期ラグの死活監視エンドポイント欠如、外部APIキャッシュ層不足。

### 1.3 V2.2の狙い
これらの知見を「事後レビューでの指摘と手戻り修正」で解決するのではなく、**設計・スケルトン生成の段階から標準パターンとして組み込んでおく（Shift-Left：前倒し）** ことが極めて重要である。

本文書は、総合レポートの知見をどのように体系化して「システムプロファイル」として落とし込み、テンプレートのどの構成要素（スケルトン、設計書雛形、エージェント定義、パイプラインスキル）に組み込むべきか、V2.2策定に向けた設計のアウトラインと検討課題を整理し、議論の叩き台とするものである。

### 2.1 第1層: 定常的コア設計規範（全プロファイル共通）
いかなる規模・環境であっても、現代的なAI駆動開発において技術的負債化を防止するために**無条件で事前組み込みする規約・ベースコード**である。

1. **フロントエンド責務分離構造（Anti-God Component）**:
   - ディレクトリを `components/`, `hooks/`, `services/`, `types/`, `utils/` に事前分割。
   - 1コンポーネント最大250行ルール、状態管理・副作用のカスタムフック（`use[Domain].ts`）集約。
2. **型定義同期パイプライン（Schema Synchronization）**:
   - バックエンドの FastAPI (OpenAPI) スキーマから、フロントエンドの TypeScript 型定義をワンコマンドで生成する基盤（`openapi-typescript` 等）。
3. **環境変数・シークレット厳格バリデーション**:
   - Pydantic Settings にて、未設定・ダミー文字列（`[YOUR_KEY]` 等）を起動時に検知し即座に安全停止するバリデータ。
4. **自動CIパイプライン（GitHub Actions）**:
   - PRおよびPush時に、フロント/バックの静的解析（`ruff`, `npm run lint`）、型チェック（`npm run type-check`）、およびAPIスモークテスト（`pytest`）を自動実行する標準ワークフロー。

### 2.2 第2層: システム展開プロファイルの具体化

#### Profile A: サーバーレス極小コストWeb型（主要ターゲット）
今回分析された4つのシステムが該当する、最も実績が厚く実用性の高いプロファイル。
- **インフラ**: Google Cloud Run（マルチステージビルド単一コンテナ、React SPA + FastAPI配信）。
- **データ層**: SQLite (WALモード, `timeout=5000`, `PRAGMA foreign_keys=ON`) + Litestream (GCS非同期レプリケーション)。
- **マイグレーション**: **Alembic標準統合**。起動スクリプト（`entrypoint.sh`）で「Litestreamリストア ➔ `alembic upgrade head` ➔ アプリ起動」を確定シーケンス化。
- **スケーリング制約**: Cloud Run `max-instances=1`（Litestreamの単一ライター制約保護）。
- **認証・セキュリティ**: **IAP JWT二重防御**。Cloud Run IAP 前段認証に加え、FastAPI の `get_current_user` 依存性で `X-Goog-IAP-JWT-Assertion` ヘッダーの署名検証を標準実装（ローカル環境では `DEBUG=True` 時のみ透過的モック）。
- **画像・ストレージ**: GCS一括バケット管理 + ブラウザ側 Canvas WebP 事前圧縮（700×700px, 80%品質）。
- **可観測性**: `/api/internal/health` および `/api/internal/litestream/status`（レプリケーション最終同期ラグ監視）。
- **外部APIレジリエンス**: 外部API連携時の二重キャッシュ機構（TTLメモリキャッシュ ＋ DBキャッシュ）。

#### Profile B: ローカル常駐・閉鎖環境型
- **インフラ**: Docker Compose によるローカルホスト常駐。
- **データ層**: ホストボリュームマウントによる SQLite 永続化（Litestream不要）。
- **ネットワーク**: 外部クラウド通信を排除した完全閉鎖動作。
- **認証**: ローカル専用（認証なし、またはベーシックなローカルセッション認証）。

#### Profile C: 個人利用・超軽量プロトタイプ型
- **インフラ**: Dockerレスまたは極小単一コンテナ。
- **データ層**: 単一SQLiteファイル、またはJSON/YAMLファイルストレージ。
- **設計指針**: 過剰な抽象化（リポジトリパターンや高度なDI）を完全排除し、可読性と改変の容易性を最優先。

#### Profile D: モバイル・PWAクライアント型
- **フロントエンド**: `vite-plugin-pwa` による Service Worker / Web App Manifest 標準同梱。
- **オフライン動作**: IndexedDB を用いたオフライン下書き保存とオンライン復帰時の自動同期。
- **最適化**: 省電力・通信量極小化、ローカル画像圧縮の必須化。

│   ├── 技術要件定義書.md ─────────────► プロファイルA標準構成 (Alembic/Litestream/IAP) の明文化

### 3.1 スケルトン層（新規追加：静的ボイラープレート基盤）
AIエージェントにゼロからコードを書かせるのではなく、検証済みの「足場（Scaffolding）」を最初から配置する。

| 対象ディレクトリ / ファイル | 組み込む具体的な内容 | 主な目的・防ぐ課題 |
| :--- | :--- | :--- |
| `.github/workflows/ci.yml` | `ruff check`, `pytest`, `npm run lint`, `npm run type-check`, `npm run build` | 回帰バグの早期検知、PR時の品質自動担保 |
| `backend/core/config.py` | Pydantic Settings による環境変数ロード ＋ 特殊記号・空文字の `@field_validator` | シークレット設定不備（角括弧混入等）による起動時クラッシュ防止 |
| `backend/core/auth.py` | `X-Goog-IAP-JWT-Assertion` の署名検証ロジック ＋ `DEBUG=True` 時のモック自動切替 | IAP認証のバックエンド層での二重防御、モック本番漏れ防止 |
| `backend/db/session.py` | SQLite WAL設定、`timeout=5000`、`PRAGMA foreign_keys=ON` の標準セッション生成器 | SQLiteのロック競合防止、参照整合性担保 |
| `backend/alembic/` & `alembic.ini` | 初期マイグレーション環境一式（モデル自動検出設定済みの `env.py`） | 手動ALTER TABLEの乱立防止、確実なスキーマ履歴管理 |
| `backend/api/internal/` | `/health` および `/litestream/status`（GCS同期ラグ監視エンドポイント） | コンテナ死活監視、バックアップサイレント障害の早期検知 |
| `frontend/src/hooks/` | `useTheme.ts`（3モードテーマ）、`useImageCompressor.ts`（Canvas WebP圧縮） | 共通UIロジックの重複実装防止、画像転送の軽量化 |
| `frontend/src/services/` | `apiClient.ts`（認証ヘッダー付与、エラーハンドリング共通化） | フェッチ処理の乱立防止 |
| `docker/entrypoint.sh` | `litestream restore` ➔ `alembic upgrade head` ➔ `uvicorn` 起動スクリプト | 起動時シーケンスの完全標準化 |

### 3.2 ドキュメント雛形層（`templates/`）
設計を担当する `architect` が参照する雛形文書を更新する。

- **`要件定義書.md`**:
  - システム展開プロファイル（Profile A〜D）の選定チェックリストを冒頭に配置。
  - プロファイルごとの必須非機能要件（バックアップ方式、認証方式、スケーリング制約）を自動誘導。
- **`技術要件定義書.md`**:
  - Profile A 選定時の「標準起動シーケンス（Litestream ➔ Alembic ➔ App）」と「タイムゾーン方針（UTC保存・JST表示）」の明記。
  - フロントエンド責務分離ルール（1ファイル250行制限、ディレクトリ構造規約）の義務化。
- **`テーブルスキーマ定義書.md`**:
  - 全テーブル共通カラム（`created_at`, `updated_at` のUTC ISO8601規約）の標準化。
  - 将来のマルチテナント・複数ユーザー拡張を視野に入れた `user_id` カラムの設計方針。
- **`ビジネスロジック仕様書.md`**:
  - 外部API連携時のキャッシュ戦略（TTLメモリキャッシュ ＋ DBキャッシュ）の記述欄を標準追加。

### 3.3 エージェント定義・プロンプト層（`subagents/`）
各スペシャリストエージェントの行動規範を強化する。

- **`architect` (設計担当)**:
  - 選定されたプロファイルに基づき、技術スタック、起動シーケンス、認可設計、キャッシュ設計を漏れなく設計書に反映することを義務付ける。
- **`backend-engineer` (実装担当)**:
  - **生SQL（`sqlite3.Row`）の直接記述を禁止**し、SQLAlchemy / Alembic を経由した実装を徹底。
  - 認可依存性（`get_current_user`）において、IAP JWT検証を省略せず実装すること。
  - 日時データは常に Aware UTC または ISO8601 文字列として扱い、Pydanticの型バリデーションを通すこと。
- **`ui-designer` (フロントエンド実装担当)**:
  - **1コンポーネント最大250行ルール**の厳格遵守。
  - 状態管理と副作用は `hooks/` に抽出し、API通信は `services/apiClient.ts` を経由すること。
  - 共通フック（`useTheme`, `useImageCompressor`）を活用し、車輪の再発明を行わないこと。
- **`qa-engineer` (監査担当)**:
  - 基本設計レビュー (`dev-review-arch`)、コード品質レビュー (`dev-review-code`)、システム総合レビュー (`dev-review-system`) において、これらの事前組込要件が遵守されているかを機械的・批判的に検査。

### 3.4 ライフサイクルスキル層（`skills/`）
開発パイプラインの各スキルへ組み込む制御。

- **`dev-phase1-setup`**:
  - 従来のリポジトリ受皿準備に加え、選定プロファイルに応じたスケルトンファイル群を初期展開するオプション/ステップの追加。
- **`dev-phase3-design`**:
  - `architect` がプロファイル固有の設計項目（Alembic構成、IAP仕様、外部APIキャッシュ等）を網羅しているかをセルフチェックするガイドを追加。
- **`dev-phase4-env-build`**:
  - スケルトンを元に初期Dockerビルド・DBマイグレーション適用・起動確認を一連のフローとして自動実行。
- **`dev-phase6-testing`**:
  - APIスモークテスト（`tests/test_api_smoke.py`）を標準実行し、全エンドポイントの死活・ステータスコードを自動検証。

## 4. 知見の事前組込マッピングマトリクス

総合レポートに記載された各課題と、テンプレートにおける組込先・解決手段の対照表。

| 総合レポートの指摘課題 | 主な発生原因 | V2.2 テンプレート組込先 | 解決アプローチ・ガードレール |
| :--- | :--- | :--- | :--- |
| **フロントエンドの God Component 化** | 画面単位で1ファイルにUI・状態・通信を丸ごとAIが記述してしまう | ・スケルトン (`frontend/src/`)<br>・`ui-designer` 規約<br>・`dev-review-code` | ディレクトリ責務分離構造の初期配置、1ファイル250行制限、カスタムフック分離の強制 |
| **Alembic未導入・手動ALTER TABLE** | 初期構築時に `create_all()` で済ませ、後から追加しにくくなる | ・スケルトン (`alembic/`)<br>・`entrypoint.sh`<br>・`backend-engineer` 規約 | 最初から `alembic init` 済みスケルトンを同梱、起動シーケンスへ `alembic upgrade head` を完全組込 |

| **環境変数の不備（角括弧混入等）** | Secret Manager登録時のプレースホルダー文字列がアプリを壊す | ・スケルトン (`core/config.py`) | Pydantic Settings で起動時にプレースホルダー記号を検知・即座に異常終了 |
| **型定義の手動二重管理・タイポ** | バックエンドとフロントエンドで別々に型を手書きしている | ・スケルトン (`package.json`)<br>・`dev-phase4-env-build` | `openapi-typescript` によるワンコマンド型自動生成スクリプトの標準配備 |

## 5. 議論の叩き台となる検討課題 (Discussion Points)

本設計アウトラインを V2.2 として正式策定・実装するにあたり、合意形成が必要な主要な論点を整理する。

### 検討課題 1: プロファイルの粒度と「Profile A」の特定技術スタック依存性
- **論点**:
  - 現在の Profile A は「クラウド公開・Webサービス型」という一般的な名前でありながら、実態は「Cloud Run × Litestream × SQLite × IAP × FastAPI × React」に高度に特化している。
  - これを **「Profile A-1: サーバーレス極小コストWeb (Cloud Run + SQLite + Litestream)」** のように明示的にサブプロファイル化すべきか、あるいは Profile A 自体をこのスタックの決定版として定義すべきか？
  - また、仮にユーザーが「Next.js + Supabase」や「Go + PostgreSQL」を希望した場合、テンプレートの柔軟性をどこまで担保すべきか？
- **検討案**:
  - V2.2 ではまず **「Profile A (Cloud Run + Litestream + SQLite + FastAPI + React)」をテンプレートの最優先リファレンススタック（ゴールデンパス）** として完全整備する。
  - 他のスタック（例: フルマネージドRDB型）は将来的な拡張プロファイル（Profile E等）として位置付け、まずは小規模Web開発の成功率を極限まで高めるアプローチを推奨する。

### 検討課題 2: スケルトン事前配置（静的ファイル） vs エージェント動的生成のトレードオフ
- **論点**:
  - テンプレートに最初から大量のボイラープレート（Alembic設定、FastAPIミドルウェア、Reactカスタムフック等）を持たせると、新規プロジェクト生成時の初期品質は跳ね上がるが、テンプレート自体の保守コストが増大する。
  - 逆に、エージェント（`backend-engineer`, `ui-designer`）にプロンプトやスキル経由で都度生成させると、柔軟性は高いが記述漏れやAI特有のブレ（God Component化、生SQL採用等）が再発しやすい。
- **検討案**:
  - **ハイブリッド方式の採用**:
    - 事故が起きやすい基盤部分（Alembic初期化、GitHub Actionsワークフロー、SQLiteセッション設定、IAP認証DI、画像圧縮フック）は **「静的スケルトン」として初期展開** する。
    - 業務ドメインに依存するロジックやコンポーネントのみをエージェントに生成させる。

### 検討課題 3: Alembicマイグレーションの自律実行手順と安全ガードレール
- **論点**:
  - エージェント（`backend-engineer`）に `alembic revision --autogenerate` や `alembic upgrade head` を自律実行させる際、環境変数（`DATABASE_URL`）の解決やマイグレーションスクリプトの正当性確認をどう安全に行うか。
  - コンテナ内実行とローカル環境実行の差異（Docker Compose内での実行 vs ホストでの実行）。
- **検討案**:
  - `skills/dev-phase4-env-build` 内に、Docker Compose 経由で Alembic を安全に実行する標準コマンドシーケンス（`docker compose exec backend alembic revision --autogenerate -m "..."`）を定義し、エージェントが迷わず実行できるように標準化する。

### 検討課題 4: IAP認証・JWT検証とローカル開発環境の透過性
- **論点**:
  - IAP の JWT 署名検証（Google公開鍵の取得と検証）はローカル環境（`localhost:3000` / `localhost:8000`）では Google の IAP プロキシが存在しないため動作しない。
  - ローカル開発時と本番稼働時でコードを書き換えることなく、どのように透過的かつ安全に切り替えるか。
- **検討案**:
  - FastAPI の依存性注入（`Depends(get_current_user)`）において、環境変数 `ENVIRONMENT=local` かつ `DEBUG=True` の場合のみ、ダミーのテストユーザー（`test-user@example.com`）を返却する安全なフォールバック機構をスケルトンに仕込む。
  - `ENVIRONMENT=production` の場合は、ヘッダーが存在しないか検証に失敗した時点で確実に 401 Unauthorized を返す二重防御とする。

### 検討課題 5: 既存プロジェクトへの適用と V2.1 からの移行パス
- **論点**:
  - 既に V2.1（またはV1.0/V2.0）で開発・運用されている既存の小規模Webシステムに対し、これらの事前組込要件（Alembic化、Hooks分割、IAP JWT検証等）をどのように後追いで適用・リファクタリングするか。
- **検討案**:
  - 定型スキルによる自動移行はカバー限界を超えるため、旧来のアップグレードスキル（`dev-upgrade-v1-to-v2`）は廃止とし、既存プロジェクトの移行はプロジェクト別個別計画として策定する。
  - 既存プロジェクトに対して、Alembicの初期ベースライン作成（`alembic stamp head`）やコンポーネント分割提案を行う専用手順を個別計画内で整備する。
