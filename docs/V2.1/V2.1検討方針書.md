## 1. はじめに

### 1.1 背景と位置づけ
本システム開発ライフサイクルテンプレートは、V2.0においてコンダクター（Main）、設計（architect）、UI（ui-designer）、QA（qa-engineer）の協調体制、Single Writer原則、二重防御ガードレールによる安全な自動開発・改訂プロセスを確立した。

一方、先行検討としてまとめられた [V2.1へ向けた検討課題.md](../検討課題/V2.1/V2.1へ向けた検討課題.md) では、以下の6つの構造的課題が提示されている：
1. システム全体弱点分析レビュアーの設計と統合（マクロ視点）
2. コード整合性・冗長性レビュアーの設計と統合（ミクロ視点）
3. コンダクター専用プロンプト（`conductor.md`）の独立化
4. バックエンド専門エージェント（`backend-engineer`）の要否判定
5. 実案件における定量測定・フィードバック機構の整備
6. WikiSkill型 永続ナレッジ自己進化ループの構築

### 1.2 V2.1 検討の目的
本フェーズ（V2.1）では、上記6課題の解決とライフサイクル全体の進化を目指し、特にコアとなる **「3つの重点システムの実装」** を中核に据える。
これら3点の実装を検討・具体化していく過程において、**AIエージェントの適切な役割と配置、スキルおよびテンプレートの再構成** を有機的に図っていく。

### テーマ 1: レビューシステムの構築
生成される成果物の品質を確実に担保し、AI特有の局所最適や全体視点の欠落を防止するため、開発パイプラインの各節目にレビューセクションを新設し、成果物の客観的評価を実施する。

#### 想定する3大レビュー
1. **基本設計レビュー (PHASE 3 / 設計完了ゲート)**:
   - **対象**: 要件定義書、基本設計書（アーキテクチャ、DB設計、API設計）、画面仕様書
   - **観点**: 可用性・耐障害性（SPOF、タイムアウト、コネクションプール）、認可・セキュリティ境界、拡張性・性能ボトルネック、データ整合性。
2. **コードレビュー (PHASE 5.5 / 実装完了・テスト前ゲート)**:
   - **対象**: フロントエンド・バックエンドの実装ソースコード
   - **観点**: DRY原則（重複排除）、単一責任の原則（SRP）、デッドコード・未使用依存の排除、コード規約・型安全性・命名の一貫性、可読性。
3. **システム総合レビュー (PHASE 7 / 本番リリース直前ゲート)**:
   - **対象**: 本番デプロイ構成、IAM/IAPポリシー、環境変数、セキュリティ設定、テスト網羅性
   - **観点**: 本番稼働耐性、インフラセキュリティ、ロールバック手順の完全性、監視・ログ可観測性。

#### パイプライン統合と評価基準
- 各レビューにおいて明確な **評価基準（合否判定チェックリスト / 採点指標）** を策定する。
- レビュー結果をパイプラインの進行条件（承認ゲート）として組み込み、不合格時のフィードバックと修正ループを標準化する。

### テーマ 2: WikiSkill型 永続ナレッジ自己進化ループシステムの導入
[WikiSkill導入評価書.md](../検討課題/V2.1/WikiSkill導入評価書.md) および [wikiskill.md](../検討課題/V2.1/wikiskill.md) に示された知見をベースに、開発パイプラインへWikiSkillアーキテクチャを本格導入する。

#### コア思想とアーキテクチャ
1. **永続Wiki層の設置 (`wiki/patterns/`, `wiki/logs.md`)**:
   - スキルや手順書の改善がテスト不合格でロールバックされた場合でも、試行錯誤ログや失敗原因は破棄されず、永続Wiki層に蓄積される（Catastrophic Forgettingの防止）。
2. **推論とWikiの分離原則 (Context Isolation)**:
   - 通常の開発推論エージェントには生のWikiを直接見せず、蒸留・検証済みのスキル・ルールのみを参照させることで、コンテキスト消費の肥大化と過学習を防止する。
3. **安全な自己進化ループ**:
   - 失敗パターンの検知・Wiki蓄積（Wiki Maintainer）→ 汎用スキル改善案の立案（Skill Proposer）→ 複合検証テスト（Gating）→ 正式スキルへの昇格と反映。

### テーマ 3: 本テンプレート自身に対する定量測定・フィードバックシステムの構築
テンプレートの設計品質や開発効率を客観的・定量的に可視化し、本テンプレートを利用して行われた実システム開発から得られたメトリクスと知見を、テンプレート自体の進化へ循環・還元させるフィードバック機構を構築する。

#### 主な検討項目
1. **テンプレート評価基準・メトリクスの策定**:
   - **トークン消費効率**: メインコンテキストの寿命、サブエージェント委譲によるコンテキスト節約率。
   - **品質・手戻り指標**: スルーテスト初回合格率、改訂ターンのリグレッション発生率、レビュー指摘件数の推移。
   - **コード健全性指標**: リファクタリングによる重複行削減率、モジュール凝集度。
   - **開発リードタイム**: 各フェーズの所要ターン数、自動修復ループの収束速度。
2. **フィードバック収集・還元機構**:
   - 案件完了時（PHASE 8）において、開発メトリクスと発生課題を自動集計する仕組みの整備。
   - 集計結果をテンプレートリポジトリへフィードバックし、プロンプト、規約、スキルの改善を促す継続的サイクル。

## 3. エージェント体制・スキル・テンプレートの再構成方針

上記3点の実装を具体化する中で、以下の通りエージェントの役割と配置、スキルおよびテンプレート群を再構成する。

### 3.1 AIエージェントの役割と配置
- **コンダクターの純化**:
  - オーケストレーションおよび状態管理（Single Writer）に専念できるよう、専用プロンプト（`conductor.md`）の独立化を進める。
- **レビュアー機能の配置設計**:
  - 基本設計レビュー、コードレビュー、システム総合レビューを担当するエージェント形態（専任エージェントの新設 vs 既存エージェントのモード拡張）を精査する。
- **バックエンド実装の責務分離検討**:
  - バックエンド専門エージェント（`backend-engineer`）の要否および委譲条件を整理し、コンダクターのコンテキスト圧迫を防止する。
- **WikiSkillロールのマッピング**:
  - Wiki Maintainer（永続化担当）および Skill Proposer（進化提案担当）の責務を適切なエージェント・スキルへ割り振る。

### 3.2 スキルとテンプレートの再構成
- **新設・改訂スキルの整備**:
  - レビュー実行スキル（設計レビュー、コードレビュー、総合レビュー）の新設。
  - WikiSkill管理スキル（Wiki更新、パターン抽出、Compactor）の整備。
  - 定量測定・メトリクス集計スキルの組み込み。
- **テンプレート・規約の更新**:
  - 『AI駆動システム開発フェーズ定義書』への新設フェーズ（例: PHASE 5.5 コードレビュー、レビューゲート）の組み込み。
  - 『AI駆動システム開発プロセス標準規約』への評価基準およびフィードバックサイクルの明文化。
