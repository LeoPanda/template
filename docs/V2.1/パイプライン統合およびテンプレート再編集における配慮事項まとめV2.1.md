## 1. 目的と位置付け

これまでの検討により確定した基盤設計：
1. **[エージェント設計書V2.1.md](./エージェント設計書V2.1.md)**: 5つの役割（`conductor`, `architect`, `backend-engineer`, `ui-designer`, `qa-engineer`）の責務・権限・入出力形式。

5. **[WikiSkill統合設計書.md](./WikiSkill統合設計書.md)**: 3層ストレージモデル、Context Isolation、複合検証ゲート、ロールバック設計。

### 配慮事項 1: スキルの実行主体（Who）と委譲・完了サマリフローの整合性再定義

#### 背景と課題
V2.0以前のスキルは単一エージェント実行前提の記述が一部に残っていた。またV2.1では `backend-engineer` の新設や `qa-engineer` へのレビュー・Wiki・Gating責務の付加が行われたため、スキルの手順書とエージェントの動作に乖離が生じるリスクがある。

#### 配慮・対応方針
- **各 `SKILL.md` のメタデータと手順書の改訂**:
  - 全スキルの冒頭に「**主担当エージェント**」を明記する。
  - スキル完了時の出力先について、「ユーザー向けArtifacts出力」と記述されていた箇所を、**「呼び出し元エージェント（コンダクター）に対する標準完了サマリの返却」** へ改訂する。
- **実行主体の明確なマッピング**:
  - `dev-phase1-setup`, `dev-phase7-release`, `dev-phase8-rules`, `wiki-proposer`, `wiki-compactor`, `dev-metrics-collector`, `dev-git-*`, `dev-db-overwrite`: **👑 コンダクター主担当手順**。
  - `dev-phase2-requirements`, `dev-phase3-design`: **📐 `architect` 主担当手順**。
  - `dev-phase4-env-build`: **👑 コンダクター (統括) ＋ 💻 `backend-engineer` (BE) ＋ 🎨 `ui-designer` (FE) 並行分担手順**。
  - `dev-phase5-walkthrough`: **👑 コンダクター (対話統括) ＋ 📐 `architect` (API仕様同期) ＋ 💻 BE / 🎨 UI (修正)**。
  - `dev-review-arch`, `dev-review-code`, `dev-review-system`, `dev-phase6-testing`, `dev-doc-reviewer`, `wiki-maintainer`: **🛡️ `qa-engineer` 主担当手順**。

### 配慮事項 2: プラグイン仕様に基づくエージェント定義と動的ロード保証

#### 背景と課題
`.agents/plugins/system-dev-pipeline/` に `agents/` ディレクトリを新設し、`plugin.json` にエージェント名を登録した際、Antigravity の実行環境やセッション状態によってはサブエージェントが自動的に利用可能として認識されない、あるいは定義内容の更新が反映されないリスクがある。

#### 配慮・対応方針
- **二重担保（プラグイン登録 ＋ 動的登録フォールバック）の組み込み**:
  1. `plugin.json` への `"agents": ["conductor", "architect", "backend-engineer", "ui-designer", "qa-engineer"]` の正規記述。
  2. メインエージェント（コンダクター）の初期動作ルールに、**「セッション開始時または委譲時に、該当サブエージェントが未定義の場合は `.agents/plugins/system-dev-pipeline/agents/<agent-name>.md` を読み込み、`define_subagent` ツールで動的定義して呼び出す」** というフォールバック手順を明記する。詳細仕様は [動的登録フォールバック仕様書V2.1.md](./動的登録フォールバック仕様書V2.1.md) にて策定。
- **エージェント定義 Markdown（YAML Frontmatter）の標準化**:
  - 各 `agents/*.md` において、Frontmatterのキー名を `define_subagent` の引数名（`enable_write_tools`, `enable_subagent_tools`, `enable_mcp_tools`）と完全一致させる。
  - `default_model` や `default_workspace` をメタデータとして内包し、呼び出し側での個別指定を不要としつつ、明示指定時は最優先適用するルールを統一する。

### 配慮事項 3: ツール・コマンド権限の厳格な分離とガードレール（二重防御方式の採用）

#### 背景と課題
Antigravity の仕様上、コード編集のために `enable_write_tools: true` を付与すると、物理的に `run_command` も利用可能となってしまう。サブエージェントが不用意に Git 操作や本番デプロイ、DB強制上書きを実行すると重大な障害につながる。また、コード品質レビューやテスト不具合時に、QAがプログラムコードを勝手に書き換えてしまうと動作デグレを招く。

#### 配慮・対応方針（二重防御ガードレール）
- **プロンプトレベルでの厳格ブロック**:
  - 📐 `architect`: `enable_write_tools: true` を付与しつつ、システムプロンプト最上部に **「【禁止事項】いかなる場合も `run_command` を呼び出してはならない」** と明記して推論レベルで確実にブロックする。
- **破壊的・インフラ系操作のコンダクター専任化**:
  - `git commit`, `git push`, `git merge`, `git checkout`
  - `gcloud run deploy`, `firebase deploy` 等の本番デプロイ
  - `dev-db-overwrite`（DB強制上書き）
  上記操作は **「👑 コンダクター専任」** とし、全サブエージェント（`architect`, `backend-engineer`, `ui-designer`, `qa-engineer`）のプロンプト内に **「明示的な禁止事項（Prohibited Actions）」** として記載する。
- **サブエージェントのシェルコマンド実行範囲の厳格な限定**:
  - 💻 `backend-engineer`: バックエンド構文チェック・単体テスト（`uv run`, `pytest`, `ruff check` 等）に限定。
  - 🎨 `ui-designer`: パッケージインストール（`npm install` 等）、ローカルUIビルド（`npm run build` 等）に限定。
  - 🛡️ `qa-engineer`: テスト実行コマンド（`pytest`, `npm test` 等）、リンター・静的解析、テスト用コンテナ起動に限定。
- **コード直接改変の禁止（QA・レビュアー向け）**:
  - 🛡️ `qa-engineer` は、コードレビューやテスト不具合時にプログラムコード本体を勝手に修正せず、提案書（`docs/plans/コード品質レビュー及びリファクタリング提案書.md`）と Unified Diff を作成してコンダクターに反映を委ねる。

### 配慮事項 4: PROJECT_STATE.md の Single Writer 原則とレビューゲート追跡の徹底

#### 背景と課題
複数エージェントが直接 `PROJECT_STATE.md` を編集すると、コンテキストの競合（同時書き込みや不完全な上書き）が発生し、チェックリストや進捗ステータスが破損する。また、3大レビューゲートの判定結果が記録されないと品質監査が形骸化する。

#### 配慮・対応方針
- **物理的・規範的なアクセス制御**:
  - `PROJECT_STATE.md` への書き込み権限を持つのは **👑 コンダクターのみ** とする。
  - サブエージェントは `PROJECT_STATE.md` を **「参照（Read-only）」** のみ行い、作業完了時はコンダクターへ所定フォーマットでサマリを返送する。
  - コンダクターがサマリを受け取った時点で、該当タスクやレビューゲートの判定（`PASS` / `REJECT`）、指摘件数を `PROJECT_STATE.md` に即時反映する。
- **ユーザー直接編集との共存**:
  - ユーザーが手動で編集した場合でもフォーマットが崩れないよう、Markdownのセクション構造をシンプルに保つ。

### 配慮事項 5: テンプレート雛形とルールファイル（rules/）のクロスリファレンス整合性

#### 背景と課題
現在 `templates/` にあるドキュメント雛形や `rules/dev-process-standards.md` は、旧来の仕様をベースに記載されている。
新体制エージェント、3大レビューゲート、WikiSkill、定量測定機構を導入したにもかかわらず、プロジェクト展開後のドキュメント内に旧仕様の記述が残っていると、ユーザーやエージェントが混乱する。

#### 配慮・対応方針
- **`templates/` 配下ドキュメントの改訂**:
  - 各設計書テンプレートの冒頭に、どのサブエージェントが主作成者であるかを明記する。
  - `templates/PROJECT_STATE.md.template` を改訂し、展開プロファイル、3大レビューゲート、WikiSkillステータス、メトリクス集計欄を反映する。
  - `templates/基本設計レビュー結果報告書.md.template`, `templates/コード品質レビュー及びリファクタリング提案書.md.template`, `templates/システム総合レビュー結果報告書.md.template` を新規追加する。
- **`rules/` 配下の改訂とコンダクター動作規範のビルトイン指針**:
  - `rules/dev-process-standards.md` および `.agents/rules/dev-process-standards.md` に、「新エージェント協調ルール」「Single Writer原則」「3大レビューゲート通過規約」「PHASE 4以降のシステム修正後のDockerコンテナ再構成ルール」を明確に反映する。
  - コンダクターの基本動作規範を独立ファイル `conductor.md` と共通ルールファイル群に確実に同期させる。

### 配慮事項 6: 既存プロジェクト（旧方式）からの段階的移行・後方互換性

#### 背景と課題
新テンプレートが完成した後、すでに旧パイプライン方式で進行しているプロジェクトや、既存のレガシーリポジトリに新方式を適用したいケースが発生する。

#### 配慮・対応方針
- **途中フェーズからの導入（マイグレーション）対応**:
  - `dev-phase1-setup` が走っていない既存プロジェクトでも、`PROJECT_STATE.md` を後から配置・初期化できるようにする。
  - メインエージェント（コンダクター）は、プロジェクト直下に `PROJECT_STATE.md` が存在しない場合、既存の `docs/` や Git ログを走査して「現在のフェーズ」を推定し、`PROJECT_STATE.md` を動的生成して追随できる運用手順を確立する。
- **下位互換性の維持**:
  - サブエージェント機能が無効化されている環境や単一エージェントモードで動作させる場合でも、既存のスキル手順単体で開発を続行できるようにフォールバックパスを残す。

### 配慮事項 7: WikiSkill永続層と推論層の分離 (Context Isolation) およびメトリクス循環

#### 背景と課題
過去のエラー事例やトラブルログを生のままエージェントの推論プロンプトへ注入すると、コンテキスト長を浪費するだけでなく、過剰適合（Overfitting）した場当たり的な分岐コードを記述し始め、コード品質が著しく劣化する。

#### 配慮・対応方針
- **Wiki層と推論層の完全分離 (Context Isolation)**:
  - 通常の開発推論エージェント（`conductor`, `architect`, `backend-engineer`, `ui-designer`）には、**`wiki/patterns/` や生ログを一切見せない**。
  - 推論エージェントが参照するのは、検証・蒸留された `skills/SKILL.md` および `rules/` のみとする。
- **Tier 1 / Tier 2 二層分離**:
  - **Tier 1 (プロジェクト固有知見)**: `wiki/patterns/local/` に記録し、`docs/` および `PROJECT_STATE.md` を正本としてプロジェクト内で即時逆同期・消費する（共通スキルへは昇格させない）。
  - **Tier 2 (全体共通知見)**: `wiki/patterns/universal/` に蓄積し、PHASE 8 での Skill Proposer と複合検証ゲート（Gating）を経て、テンプレート側の `skills/` や `rules/` へ安全に昇格させる。
- **定量メトリクスの集計と還元**:
  - `dev-metrics-collector` により集計されたメトリクス（トークン効率、レビュー指摘推移、不具合収束率）を `development-metrics-summary.json` に出力し、テンプレート自身の改善に還元する。

### 配慮事項 8: ドキュメント内相対リンク強制とパーサー誤認防止ファイル命名規約

#### 背景と課題
Markdownドキュメント内で絶対パス（`file:///` や `/Users/...`）を用いると、プロジェクトの可搬性や別環境での共有時にリンク切れを起こす。また、ファイル名に半角丸括弧 `(` `)` 等を含めると、Markdownリンクの正規表現パーサーや一部のレンダラーにおいて、URL内部の最初の閉じ括弧がリンク終端と誤認され、リンク切れやパースエラーを引き起こすリスクがある。

#### 配慮・対応方針
- **相対パスリンクの絶対強制**:
  - 全ドキュメント内の内部リンクは、環境非依存性を担保するため、すべて対象ファイル間の相対パス（例: `./エージェント設計書V2.1.md`, `../docs/`）を使用する。
- **パーサー誤認文字の排除（ファイル命名規約）**:
  - 新規作成・改訂されるドキュメントのファイル名には、半角丸括弧 `(` `)` などのパーサーが誤認する記号を用いず、**全角括弧 `（` `）`** を用いる（例: `再編集・統合詳細実行計画書（Step4-B〜D）.md`）。
  - やむを得ず半角特殊記号を含む外部資産や既存ファイルへリンクする場合は、**URLエンコード（`%28`, `%29` 等）** または山括弧 `<>` による囲み構文を用いる。
