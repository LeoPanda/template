## 1. 目的と位置付け

本文書は、Antigravity環境におけるAI駆動システム開発ライフサイクル（新規開発 PHASE 1〜8、および本番リリース後の継続的システム改訂プロセス）において、**メインエージェント（コンダクター）、4つの専門サブエージェント（architect, backend-engineer, ui-designer, qa-engineer）、決定論的スキル群、およびユーザー（開発者/PO）** が協調して開発・改訂を完遂するためのフェーズ定義と役割分担を規定するものである。

V2.1においては、[V2.1検討方針書.md](./V2.1検討方針書.md)、[エージェント設計書V2.1.md](./エージェント設計書V2.1.md)、[レビューシステム設計書.md](./レビューシステム設計書.md)、および [WikiSkill統合設計書.md](./WikiSkill統合設計書.md) に基づき、以下の重大な機能拡張をパイプラインに標準統合する：
1. **二層型レビューシステム（定常的普遍コア ＋ 規模・環境適応型プロファイル）の導入**
2. **新設フェーズ「PHASE 5.5: コード品質レビューとリファクタリング」の組み込み**
3. **明示的承認ゲートと連動する3大レビュー（基本設計レビュー / コードレビュー / システム総合レビュー）の品質ゲート化**
4. **WikiSkill型 永続ナレッジ自己進化ループシステム（3層ストレージモデル、Context Isolation、複合検証ゲート）の統合**
5. **バックエンド専門エージェント（`backend-engineer`）の新設による実装責務の完全分離**

## 2. 採用された基本方針（V2.1 決定事項）

| 検討項目 | 採択方針 | 詳細内容 |
| :--- | :--- | :--- |
| **1. フェーズ移行ゲート** | **明示的承認ゲート ＋ レビュー合格必須** | 各重要フェーズ完了時、レビュー合格（PASS / CLEAN / RELEASE APPROVED）を前提条件とし、必ずユーザーの明示的な「承認」プロンプトを受けて次フェーズへ移行する。 |
| **2. システム展開プロファイル** | **要件定義での宣言と動的観点合成** | PHASE 2 において「Profile A: クラウド公開」「Profile B: ローカル常駐」「Profile C: 個人小規模」「Profile D: モバイル」を確定し、設計レビュー・総合レビューの観点を適応させる（過剰設計・YAGNI違反の防止）。 |
| **3. コードクオリティ工程** | **PHASE 5.5 の新設** | ウォークスルー（PHASE 5）で機能Fixした直後、テストコード構築（PHASE 6）の前にコードのエントロピー（重複・乱雑さ）を除去・整流化する。 |
| **4. 非破壊的レビュー原則** | **提案型ガードレール** | レビュアーはコードや設計書を直接書き換えない。指摘報告書およびUnified Diffを作成し、コンダクターの適用・再ビルド確認を経て反映する。 |
| **5. 状態管理の一元化** | **Single Writer 原則 (`PROJECT_STATE.md`)** | 状態管理ファイルへの書き込みは 👑 コンダクターのみが集中実行。レビュー結果やプロファイル状態もコンダクターが一元記録する。 |
| **6. 永続ナレッジ自己進化** | **WikiSkill 3層構造 ＋ Context Isolation** | 実行ログ（Raw）、永続Wiki（Wiki）、実行手順（Skills）の3層分離。推論エージェントにはWikiを直接見せず（過学習・トークン浪費防止）、検証不合格時もWiki層の失敗知見（根本原因・棄却理由）は決して破棄しない。 |
| **7. 複合検証ゲート** | **Composite Gating ＋ Skills層限定ロールバック** | 静的解析0件、ドキュメント整合性0件、シナリオテスト100%パス、トークン効率上限内の全関門クリア時のみスキルを確定昇格。不合格時はSkills層のみロールバックしWikiは完全維持する。 |
| **8. BE/FE実装の完全分離** | **backend-engineer 新設** | PHASE 4 におけるバックエンドAPI・DBモデル・ビジネスロジック実装を独立サブエージェント `backend-engineer` へ委譲し、コンダクターのコンテキスト枯渇を防止する。 |

## 3. エージェントおよびユーザーの役割体系

開発パイプラインおよびシステム改訂プロセスは、以下の6つのアクター（人間1名＋エージェント5名）と決定論的スキル群によって運用される。

```
                    ┌────────────────────────────────────────┐
                    │               👤 ユーザー              │
                    │      (要件提示 / ゲート承認 / 操作検証) │
                    └──────────────────┬─────────────────────┘
                                       │ 対話 / 指示 / 明示的承認
                                       ▼
                    ┌────────────────────────────────────────┐
                    │ 👑 1. プロジェクトコンダクター (Main)    │
                    │      (全体進行 / オーケストレーション / │
                    │       状態一元管理 Single Writer)       │
                    └──────────────────┬─────────────────────┘
                                       │ 委譲 (invoke_subagent)
         ┌─────────────────────────────┼─────────────────────────────┬─────────────────────────────┐
         ▼                             ▼                             ▼                             ▼
┌──────────────────────────┐  ┌──────────────────────────┐  ┌──────────────────────────┐  ┌──────────────────────────┐
│ 📐 2. 設計・立案          │  │ 💻 3. バックエンド        │  │ 🎨 4. UI/UX              │  │ 🛡️ 5. 品質・監査 & QA    │
│    スペシャリスト        │  │    エンジニア            │  │    デザイナー / FE       │  │ (レビュー・テスト・監査)   │
│ (architect)              │  │ (backend-engineer)       │  │ (ui-designer)            │  │ (qa-engineer)            │
│ [Model: pro]             │  │ [Model: pro]             │  │ [Model: flash / pro]     │  │ [Model: pro]             │
└────────────┬─────────────┘  └────────────┬─────────────┘  └────────────┬─────────────┘  └────────────┬─────────────┘
             │                             │                             │                             │
             └─────────────────────────────┴─────────────────────────────┼─────────────────────────────┘
                                                                         ▼ 成果物反映
                                                             ┌──────────────────────────┐
                                                             │ ⚙️ 決定論的ツール / スキル │
                                                             │ ・Git管理 (dev-git-*)    │
                                                             │ ・レビュー (dev-review-*)│
                                                             │ ・テスト (dev-phase6-*)  │
                                                             │ ・DB反映 (dev-db-*)      │
                                                             │ ・Wiki (wiki-*)          │
                                                             │ ・メトリクス (dev-metrics)│
                                                             └──────────────────────────┘
```

### 3.1 アクター詳細

1. **👤 ユーザー (`user` / 人間)**:
   - システム要求の提示、設計プロファイル選定、レビュー結果の確認、各ゲートの明示的承認、ウォークスルーでのUI操作検証、知見昇格・自己進化の承認、本番リリースの最終判断。
2. **👑 プロジェクトコンダクター (`conductor` / メインエージェント / Model: `pro` または `inherit`)**:
   - 全体進捗管理、`PROJECT_STATE.md` の一元更新（Single Writer）、サブエージェントへのタスク委譲、Docker/環境構築統括、レビュー指摘Diffの適用・再ビルド確認、Git/デプロイスキル呼び出し。
   - **サブエージェント動的登録フォールバック**: 委譲前に未登録サブエージェントを検知した際、`define_subagent` により自律登録して呼び出す。
   - **WikiSkill Skill Proposer 統括**: PHASE 8 知見昇格時に、蓄積された Wiki パターンをもとに `SKILL.md` の改善パッチおよび `PURPOSE.md` を起案。
   - **Wiki Compactor 統括**: 肥大化した Wiki パターンの定期要約・統合（Consolidation）および退避（Archiving）を実行。
   - **定量メトリクス集計**: `dev-metrics-collector` により開発健全性メトリクスを集計・出力。
3. **📐 設計・立案スペシャリスト (`architect` / サブエージェント / Model: `pro`)**:
   - 要件定義書（プロファイル設定含む）、基本設計書3種（技術・スキーマ・ロジック）の作成、レビュー指摘（ARCH-*）の設計反映、API仕様書の同期。
   - ※ 推論エージェントとして Wiki 層は直接参照せず、蒸留された `SKILL.md` および `rules/` のみに基づいて設計する（Context Isolation）。
   - ※ 二重防御ガードレール: `run_command` の実行は厳禁。
4. **💻 バックエンドエンジニア (`backend-engineer` / サブエージェント / Model: `pro`)**:
   - PHASE 4 におけるバックエンドAPI、データベースモデル・マイグレーション、ビジネスロジックの実装を担当。
   - 基本設計書に完全準拠したコード生成、コード品質レビュー指摘（DRY、SRP、型安全）の修正。
   - ※ 推論エージェントとして Wiki 層は直接参照しない（Context Isolation）。
   - ※ コマンド実行はバックエンド構文チェック・単体テスト（`uv run`, `pytest`, `ruff check` 等）に限定（Git/デプロイ/DB上書きは厳禁）。
5. **🎨 UI/UXデザイナー (`ui-designer` / サブエージェント / Model: `flash` または `pro`)**:
   - `画面仕様書.md` の作成、フロントエンド画面・コンポーネント実装、UI微修正。
   - ※ 推論エージェントとして Wiki 層は直接参照せず、標準規約と手順書に準拠する（Context Isolation）。
   - ※ コマンド実行はパッケージ導入・UIローカルビルド（`npm install`, `npm run build` 等）に限定（Git/デプロイは厳禁）。
6. **🛡️ 品質・監査 & QA (`qa-engineer` / サブエージェント / Model: `pro`)**:
   - 以下の監査モード、テスト、および WikiSkill 保守・検証を担当：
     - 🏛️ **基本設計レビューモード** (`dev-review-arch`): 定常コア ＋ プロファイル適応型アーキテクチャ監査（YAGNI抑止含む）。
     - 🧹 **コード品質レビューモード** (`dev-review-code`): DRY、SRP、デッドコード、型安全性の整流化監査・Diff提案。
     - 🛡️ **本番リリース統括監査モード** (`dev-review-system`): 稼働耐性、シークレット排除、ロールバック可能性監査。
     - 🧪 **テスト自動実行モード** (`dev-phase6-testing`): シナリオテスト自動実行・修復ループ。
     - 📝 **Wiki Maintainer モード** (`wiki-maintainer`): レビュー不合格、コード指摘、テスト失敗、自律修復ログから根本原因（RCA）を即座に抽出し、`wiki/patterns/` へ永続記録（Tier 1 / Tier 2 仕分け実施）。
     - ⚖️ **複合検証ゲート判定モード**: スキル自己進化パッチの適用時に複合検証ゲート（静的解析・整合性・テスト・トークン効率）を実行し、合否判定およびロールバック制御を実施。
     - ※ プログラムコード直接改変の禁止（提案書とDiff出力に留める）。Git/デプロイコマンドは厳禁。
7. **⚙️ 決定論的スキル (`system-dev-pipeline`)**:
   - `dev-phase1-setup` 〜 `dev-phase8-rules`, `dev-git-init`, `dev-git-release`, `dev-db-overwrite`, `dev-doc-reviewer`, `dev-review-*`。
   - **WikiSkill & メトリクス管理スキル群**: `wiki-maintainer`, `wiki-proposer`, `wiki-compactor`, `dev-metrics-collector`。

## 4. 新規開発フェーズ定義（PHASE 1 〜 PHASE 8）

新規プロジェクト立上げから初回本番リリースまでの工程を定義する。

```
PHASE 1: 準備 ──► PHASE 2: 要件定義 (プロファイル決定) ──► PHASE 3: 基本設計 & 設計レビュー
                                                                      │
┌─────────────────────────────────────────────────────────────────────┘
▼
PHASE 4: 環境・システム構築 ──► PHASE 5: ウォークスルー ──► PHASE 5.5: コード品質 & リファクタリング
                                                                      │
┌─────────────────────────────────────────────────────────────────────┘
▼
PHASE 6: スルーテスト ──► PHASE 7: 総合レビュー & 本番リリース ──► PHASE 8: 保守改訂管理移行
```

---

### 4.1 PHASE 1: プロジェクトの準備
- **目的**: ディレクトリ構成、`.env`、各種ドキュメント雛形、永続ナレッジ基盤（Wiki層 `./wiki/`）、メトリクス集計領域（`metrics/`）、および知見昇格バッファの自動展開、実行環境に応じた動作モード識別と状態管理の初期化。
- **主担当**: 👑 コンダクター（スキル: `dev-phase1-setup`）
- **初期化および適応メカニズム**:
  - **テンプレート参照パス解決**: ローカル `./.agents/plugins/system-dev-pipeline/templates/` を優先探索し、存在しない場合はグローバルプラグイン配下（`~/.gemini/config/plugins/.../templates/`）へ自動フォールバック。
  - **動作モード自動判定**: プロジェクト内 `./.agents/plugins/` の有無に基づき、`EXECUTION_MODE: [GLOBAL_PLUGIN | LOCAL_STANDALONE]` および `TEMPLATE_SOURCE` を判定し、`PROJECT_STATE.md` メタデータへ自動記録。
  - **受皿ディレクトリ・ファイルの完全確保**:
    - `docs/`, `docs/plans/scenario-test/`, `docs/plans/metrics/`
    - `wiki/`, `wiki/patterns/local/`, `wiki/patterns/universal/`, `wiki/patterns/rejected/`, `wiki/archive/`, `wiki/logs.md`, `wiki/skill-impact.md`
    - `metrics/turns/` (`.gitignore` 対象、`.gitignore` への自動登録・追記)
    - `rules/dev-process-standards.md`, `.env`, `PROJECT_STATE.md`, `TEMPLATE_PROMOTIONS.md`
- **完了判定条件（ゲート）**:
  - [x] ディレクトリ構造（`docs/`, `docs/plans/`, `.env`, `rules/`）が正常配置されていること。
  - [x] 永続ナレッジ領域（`./wiki/patterns/{local,universal,rejected}`, `wiki/archive/`, `wiki/logs.md`, `wiki/skill-impact.md`）が初期化されていること。
  - [x] メトリクス集計領域（`metrics/turns/`）が初期化され、`.gitignore` に除外登録されていること。
  - [x] `PROJECT_STATE.md` が初期化され、`EXECUTION_MODE` および `TEMPLATE_SOURCE` が正しく記録されていること（Status: `PHASE_1_COMPLETED`）。
  - [x] 知見昇格提示用バッファ（`TEMPLATE_PROMOTIONS.md`）が初期配置されていること。

### 4.2 PHASE 2: 要件定義
- **目的**: ユーザー要求を精査し、`docs/要件定義書.md` を作成・確定する。**システム展開プロファイルを確定する**。
- **主担当**: 📐 `architect`（委譲元: 👑 コンダクター）
- **必須要件**:
  - `docs/要件定義書.md` 冒頭に以下の「システム展開プロファイル」を明記すること：
    - 稼働環境: [クラウド公開 / クラウド閉域 / ローカル常駐 / 個人スタンドアローン / モバイル / CLI]
    - ユーザー規模: [個人 (1名) / チーム (2〜20名) / パブリック (不特定多数)]
    - 最優先トレードオフ: [シンプルさ・低コスト優先 / リソース消費極小優先 / 高可用性・厳格セキュリティ優先]
    - 適用プロファイル: [Profile A: クラウド公開 / Profile B: ローカル常駐 / Profile C: 個人小規模 / Profile D: モバイル]
- **完了判定条件（明示的承認ゲート）**:
  - [x] システム展開プロファイルが確定していること。
  - [x] 機能・非機能要件、ユースケースが網羅され、未決事項（Open Questions）が0件であること。
  - [x] **【ゲート】ユーザーによる「要件定義完了」の明示的承認を受領していること。**

### 4.3 PHASE 3: 基本設計書の作成と整合性チェック・設計レビュー
- **目的**: 基本設計書4種を作成し、ドキュメント整合性チェックおよび基本設計レビューを実施・合格する。
- **主担当**:
  - 技術 / スキーマ / ロジック設計: 📐 `architect`
  - 画面仕様: 🎨 `ui-designer`
  - 相互整合性監査: 🛡️ `qa-engineer`（ツール: `dev-doc-reviewer`、※`docs/plans/` 配下およびルート管理・Wiki・メトリクス領域は `ignore_paths` としてハードコード除外）
  - 基本設計レビュー: 🛡️ `qa-engineer` (監査モード / スキル: `dev-review-arch`)
  - Wikiナレッジ記録: 🛡️ `qa-engineer` (Wiki Maintainer / スキル: `wiki-maintainer`)
- **レビュー観点**:
  - **定常コア**: データ保全・破壊防止、入力境界値防御、リソースリーク防止、設定分離、例外クラッシュ防止、**過剰設計抑止（YAGNI）**。
  - **可変適応**: 指定されたプロファイル（Profile A〜D）に応じた耐障害性、認可、OSポータビリティ、ゼロコスト等の検証。
- **完了判定条件（明示的承認ゲート）**:
  - [x] 4大設計書が作成され、相互整合性エラーが0件であること。
  - [x] **基本設計レビューが合格（PASS または 承認済み CONDITIONAL PASS）であり、`docs/plans/基本設計レビュー結果報告書.md` が作成されていること。**
  - [x] 設計レビューで顕著な設計欠陥・是正指摘があった場合、`wiki/patterns/PAT-ARCH-xxx.md` に再発防止パターンが記録されていること。
  - [x] **【ゲート】ユーザーによる「基本設計完了」の明示的承認を受領していること。**

### 4.4 PHASE 4: 開発環境とシステム構築
- **目的**: ローカル開発環境の構築、BE/FE並行実装、Gitリポジトリ初期化。
- **主担当**:
  - 環境構築統括・Docker設定: 👑 コンダクター
  - バックエンドAPI・DBモデル・ビジネスロジック実装: 💻 `backend-engineer`
  - フロントエンド画面・コンポーネント実装: 🎨 `ui-designer`
  - Git初期化: ⚙️ `dev-git-init`（`.gitignore` に `metrics/turns/` 等が含まれていることを確認しコミットに包含）
- **完了判定条件（ゲート）**:
  - [x] 実行環境（コンテナ等）が正常起動し、初期画面・APIが疎通可能であること。
  - [x] Git管理が初期化され、`.gitignore`（`metrics/turns/` 除外等）を含めて `main` 初回コミットおよび `feature` 作業ブランチが作成されていること。

### 4.5 PHASE 5: ウォークスルー動作確認とデバッグ
- **目的**: 実際の画面操作による動作確認、不具合修正、および設計書への逆同期。
- **主担当**:
  - 操作検証: 👤 ユーザー
  - デバッグ修正統括: 👑 コンダクター
  - バックエンド修正: 💻 `backend-engineer`
  - UI微調整: 🎨 `ui-designer`
  - API仕様同期: 📐 `architect`
- **完了判定条件（明示的承認ゲート）**:
  - [x] ユーザーによるウォークスルーが完了し、指摘された機能不具合が改修されていること。
  - [x] 最新コードに基づきAPI仕様書および設計書が同期更新されていること。
  - [x] **【ゲート】ユーザーによる「ウォークスルー完了・コード品質レビュー移行」の明示的承認を受領していること。**

### 4.6 PHASE 5.5: コード品質レビューとリファクタリング 【新設フェーズ】
- **目的**: ウォークスルーで反復修正されたコードのエントロピー（乱雑さ・重複・デッドコード）を除去し、テストコード構築前にコードベースを美しく整流化する。
- **主担当**:
  - コード品質レビュー & Diff立案: 🛡️ `qa-engineer` (品質モード / スキル: `dev-review-code`)
  - Diff適用 & 環境再ビルド確認: 👑 コンダクター (統括) ＋ 💻 `backend-engineer` / 🎨 `ui-designer` (修正)
  - Wikiナレッジ記録: 🛡️ `qa-engineer` (Wiki Maintainer / スキル: `wiki-maintainer`)
- **レビュー観点**:
  - DRY原則（重複排除）、単一責任（SRP / ファイル行数≤400行、関数行数≤50行）、デッドコード・残存ログの根絶、型安全性・命名の一貫性。
- **完了判定条件（明示的承認ゲート）**:
  - [x] `docs/plans/コード品質レビュー及びリファクタリング提案書.md` が作成され、判定が `CLEAN` または適用完了であること。
  - [x] 提案Diff適用後、環境再ビルド（`docker compose up --build -d` 等）および疎通確認が完了していること。
  - [x] 検出されたコードアンチパターンや共通リファクタリング知見が `wiki/patterns/PAT-CODE-xxx.md` に記録されていること。
  - [x] **【ゲート】ユーザーによる「コード品質確認完了・テスト構築移行」の明示的承認を受領していること。**

### 4.7 PHASE 6: スルーテスト環境の構築と実施
- **目的**: 整流化されたコードに対して自動テストコードを構築し、全テストケースがPASSするまで自律修復ループを実行する。
- **主担当**:
  - テスト構築・自動修復: 🛡️ `qa-engineer`（ツール: `dev-phase6-testing`）
  - 障害分析・Wiki記録: 🛡️ `qa-engineer`（Wiki Maintainer / スキル: `wiki-maintainer`)
- **完了判定条件（明示的承認ゲート）**:
  - [x] `docs/plans/シナリオテスト計画書.md` の全テストがPASS（成功率100%）していること。
  - [x] テスト実行ログが保存され、未解決エラーが0件であること。
  - [x] 自動修復ループで解決されたエラーの根本原因・回避策が `wiki/patterns/PAT-TEST-xxx.md` に永続記録されていること。
  - [x] **【ゲート】ユーザーによる「テスト完了・リリース準備移行」の明示的承認を受領していること。**

### 4.8 PHASE 7: システム総合レビューと本番リリース
- **目的**: 手順書を作成し、本番投入直前の総合セキュリティ・環境適合性監査を実施・合格した上で、本番環境へのデプロイまたは配布を実施する。
- **主担当**:
  - 手順書策定 & デプロイ実行: 👑 コンダクター（ツール: `dev-phase7-release`）
  - システム総合レビュー: 🛡️ `qa-engineer` (リリース監査モード / スキル: `dev-review-system`)
- **レビュー観点**:
  - 平文シークレット皆無、プロファイル別セキュリティ境界の遵守、ロールバック手順の完全性、スルーテスト100%パス（Zero Tolerance）。
- **完了判定条件（明示的承認ゲート）**:
  - [x] **システム総合レビューが合格（RELEASE APPROVED）であり、`docs/plans/システム総合レビュー結果報告書.md` が作成されていること。**
  - [x] **【ゲート】ユーザーによる「本番デプロイ/配布実行」の明示的承認を受領していること。**
  - [x] 本番デプロイ/配布が正常完了し、稼働確認が取れていること。

### 4.9 PHASE 8: ドキュメント改訂管理の開始と自己進化ループの実行
- **目的**: 初回リリースのGitHub本番反映（Squash Merge）、改訂運用規約ファイル群の配置、WikiSkill型自己進化サイクル（知見昇格・スキル更新・複合検証ゲート）の実行、動作モード（`EXECUTION_MODE`）に応じた知見昇格ルーティング、定量メトリクス集計、状態管理を保守モードへ移行。
- **主担当**:
  - リリース・改訂移行: 👑 コンダクター（スキル: `dev-git-release`, `dev-phase8-rules`）
  - 自己進化パッチ立案: 👑 コンダクター (Skill Proposer / スキル: `wiki-proposer`)
  - 複合検証ゲート判定: 🛡️ `qa-engineer` (Gating)
  - Wiki統合・アーカイブ: 👑 コンダクター (Compactor / スキル: `wiki-compactor`)
  - 定量メトリクス集計: 👑 コンダクター (スキル: `dev-metrics-collector`)
- **WikiSkill 自己進化サイクルの実行要件**:
  1. 蓄積された `wiki/patterns/universal/` から Tier 2（テンプレート昇格候補）を抽出し、`./TEMPLATE_PROMOTIONS.md` へ集約・提示。
  2. ユーザーによる知見昇格レビュー承認を受領後、`PROJECT_STATE.md` の `EXECUTION_MODE` を参照。
  3. `wiki-proposer` により `SKILL.md` の更新パッチを作成し、`PURPOSE.md` を更新。
  4. `qa-engineer` により複合検証ゲート（静的解析0件、ドキュメント整合性0件、全テストパス、トークン効率上限内）を実行。
     - **合格時**:
       - **`LOCAL_STANDALONE` モード**: プロジェクトローカルの `.agents/plugins/system-dev-pipeline/skills/` を正式採用として Git コミット。
       - **`GLOBAL_PLUGIN` モード**: エクスポート先ディレクトリ（`./promotions/`）が存在しない場合は自動生成（`mkdir -p ./promotions`）した上で、プロジェクト直下に `./promotions/v2.1_universal_patterns.patch` をエクスポートし、グローバルプラグイン（`~/.gemini/...`）またはテンプレート本流への反映手順を案内。
       - `wiki/logs.md` に採択記録 (`[Adopted]`)。
     - **不合格時**: Skills層のみ直前の状態にロールバックし、`wiki/logs.md` に棄却記録 (`[Rejected]`)（Wiki層は完全維持）。
  5. `wiki-compactor` により、類似パターンの統合および陳腐化パターンのアーカイブ退避を実施。
- **完了判定条件（ゲート）**:
  - [x] **【ゲート】ユーザーによる知見昇格レビュー（`./TEMPLATE_PROMOTIONS.md`）が承認されていること。**
  - [x] WikiSkill 自己進化サイクルが実行され、結果（採択または安全なロールバック）が `wiki/logs.md` に記録されていること。
  - [x] `EXECUTION_MODE` に応じた知見昇格（パッチ出力または直接反映）が完了していること。
  - [x] `dev-metrics-collector` による開発定量メトリクスサマリが `docs/plans/metrics/development-metrics-summary.json` に出力されていること。
  - [x] `dev-git-release` により `feature` が `main` へ Squash Merge され、タグ付きPushが完了していること。
  - [x] 次期 `feature` ブランチが切り直され、改訂運用ルールファイル群が配置されていること。
  - [x] `PROJECT_STATE.md` が「本番稼働中 / 保守・改訂運用モード」へ更新されていること。
